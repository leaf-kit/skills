# 0.3 이 책을 읽는 법

300쪽을 앞에서부터 읽을 사람은 거의 없다. 깃허브에서 읽는 책이라 더 그렇다. 링크를 타고 들어와 한 장만 읽고 나가는 것이 정상적인 사용법이고, 그래서 장마다 독립적으로 읽히게 썼다.

## 목적별 경로

### 스킬을 처음 만든다

[1부](../README.md#1부--스킬이란-무엇인가)로 가서 개념을 잡고 [3부](../README.md#3부--스킬-작성법)로 넘어간다. 2부(프롬프트 작성법)는 건너뛰어도 된다. 다만 만든 스킬이 자꾸 트리거되지 않으면 [3.2 description 설계](../part3/02-description.md)로 돌아온다. 스킬이 안 불리는 문제의 대부분이 거기서 결정된다.

평가를 건너뛰고 싶은 마음이 들면 [3.7 평가 만들기](../part3/07-evals.md)만 읽어 본다. 평가 없이 만든 스킬은 잘 되는지 아닌지를 영원히 모른다.

### 쓸 스킬을 고르고 있다

[5부](../README.md#5부--스타수-전체-순위)에서 전체 지형을 보고, 필요한 도메인만 [8부](../README.md#8부--도메인별-리뷰)에서 읽는다. 보안이면 [8.1](../part8/01-security.md), 코드리뷰면 [8.2](../part8/02-code-review.md)다.

설치하기 전에 [9.3 공급망 위험](../part9/03-supply-chain.md)을 읽는 쪽을 권한다. 스킬은 에이전트가 읽고 그대로 따르는 지시문이고, 설치가 쉬운 만큼 확인은 덜 하게 된다.

### 생태계 전체를 보고 싶다

[0부](01-this-repository.md) → [5.4 순위에서 읽히는 패턴](../part5/04-patterns.md) → [9부](../README.md#9부--생태계를-읽는-눈) 순서가 가장 짧은 경로다. 개별 저장소 리뷰(6, 7, 8부)는 필요할 때 사전처럼 찾아 쓴다.

### 프롬프트부터 다듬고 싶다

[2부](../README.md#2부--프롬프트-작성법)만 읽어도 독립적으로 쓸모가 있다. 스킬을 만들 계획이 없어도 된다. 특히 [2.3 길게 쓰면 해결된다는 오해](../part2/03-length-myth.md)는 프롬프트를 계속 늘리고 있는 사람을 위한 장이다.

### 남이 만든 스킬을 믿어도 되는지 알고 싶다

[9.3 공급망 위험](../part9/03-supply-chain.md)과 [9.4 라이선스와 출처](../part9/04-licensing.md) 두 장이면 된다.

## 이 책의 표기 규칙

읽을 때 알고 있으면 편한 몇 가지다.

**순위표에는 수집 날짜가 붙는다.** 날짜 없는 스타수는 쓰지 않는다. 현재 데이터는 2026-10-04 수집분이다.

**저장소는 `owner/repo` 형식으로 적는다.** `obra/superpowers`처럼 쓴다. 같은 이름의 저장소가 여럿이라서 저장소 이름만으로는 특정되지 않는다.

**리뷰에는 확인 수준이 표시된다.** 두 종류가 있다.

| 표시 | 뜻 |
|---|---|
| 정밀 리뷰 | `README`와 실제 `SKILL.md`를 열어 보고 썼다 |
| 요약 리뷰 | 저장소 설명과 메타데이터만 보고 썼다 |

요약 리뷰를 정밀 리뷰처럼 쓰지 않는다. 458개를 다 열어 볼 수는 없으므로, 열어 보지 않은 것은 열어 보지 않았다고 적는다.

**확인하지 못한 사실은 `[확인 필요: ...]`로 남긴다.** 빈칸을 추측으로 채우지 않는다. 이 책에서 추측으로 채운 숫자가 한 개라도 나오면 나머지 숫자도 믿을 수 없게 된다.

**스킬 이름과 코드 식별자는 원문 그대로 쓴다.** `SKILL.md`, `description`, `progressive disclosure`처럼 번역하면 검색이 안 되는 말은 번역하지 않는다.

## 데이터를 직접 확인하는 방법

이 책의 모든 숫자는 다시 만들 수 있다.

```bash
# gh CLI 인증
gh auth login

# 스타수 수집 (458개 저장소, 몇 분 소요)
cd data && ./collect.sh

# 스킬 저장소 판정 (상위 150개 파일 트리 조회)
./classify.sh stars-$(date +%Y-%m-%d).tsv 150
```

출력은 TSV라서 스프레드시트로 열거나 `awk`로 바로 가공할 수 있다. 스키마는 [부록 A](../appendix/a-data.md)에 있다.

숫자가 책과 다르면 그건 오류가 아니라 날짜 차이다. 이 생태계에서 가장 빠른 저장소는 하루에 1,000개 넘게 스타가 붙는다.

## 이 책이 틀렸을 때

리뷰는 시간이 지나면 틀린다. 저장소가 구조를 바꾸거나, 관리가 끊기거나, 더 나은 대안이 나온다. 틀린 것을 발견하면 이슈로 알려 주면 된다. 고칠 때는 조용히 덮어쓰지 않고 무엇이 어떻게 바뀌었는지 남긴다. 갱신 규칙은 [9.6](../part9/06-update-policy.md)에 있다.

판단에 동의하지 않는 경우는 조금 다르다. 이 책의 리뷰에는 근거를 같이 적어 두었으니, 근거가 사실과 다르면 고칠 일이고 근거는 맞는데 결론이 다르면 그건 관점 차이다. 관점 차이를 지우려고 근거를 바꾸지 않는다.
