# 9.2 스킬 품질을 재는 방법

생태계에 공통 품질 벤치마크가 없다. 그래서 이 책이 스타수를 축으로 쓸 수밖에 없었다([0.2](../part0/02-why-stars.md)).

다만 도구가 없는 것이 아니다. **흩어져 있다.** 세 저장소가 각각 다른 축을 재고, 셋을 다 갖춘 곳이 없다. 이 장은 세 축을 정리하고 합치는 방법을 제시한다.

## 세 축이 각각 다른 저장소에 있다

| 축 | 재는 것 | 구현한 저장소 | 스타 |
|---|---|---|---|
| **A. 라우팅** | 스킬이 불려야 할 때 불리는가 | `addyosmani/agent-skills` | 100,755 |
| **B. 기여** | 스킬이 없을 때보다 나은가 | `DietrichGebert/ponytail` | 152,808 |
| **C. 평가 신뢰도** | 이 측정을 믿을 수 있는가 | `dotnet/skills` | 5,543 |

(수집 날짜: 2026-10-04)

여기에 두 축이 더 있다.

| 축 | 재는 것 | 구현 |
|---|---|---|
| D. 형식 | 규격을 지켰는가 | `skills-ref`, `github/awesome-copilot`의 `.schemas/` |
| E. 안전 | 악성, 취약 패턴이 있는가 | `NVIDIA/SkillSpector` |

**다섯 축이 다섯 곳에 흩어져 있다.**

## 축 A — 라우팅

`addyosmani/agent-skills`의 3단 체계 중 Tier 2다([7.2](../part7/02-addyosmani.md)).

### 재는 것

| 항목 | 방법 |
|---|---|
| 과소 트리거 | 양성 프롬프트가 해당 스킬을 top-k에 올리는가 |
| 과잉 트리거 | 음성 프롬프트가 올리지 않는가 |
| **충돌** | 두 스킬의 `description`이 근접 충돌하지 않는가 |

세 번째가 다른 어디에도 없다. 번들 규모가 커지면 스킬끼리 트리거를 경쟁하고([1.5](../part1/05-triggering.md)), 그걸 측정하는 유일한 구현이다.

### 어떻게 구현했나

어간 추출 TF-IDF로 라우팅을 근사한다. 의미를 판단하지 못하지만 **결정적이고 공짜다.** 모든 커밋에서 CI로 돌린다.

음성 케이스에 `owner` 필드가 있다.

```json
"negative": [
  {"prompt": "Add a feature flag system to the app", "owner": "incremental-implementation"},
  {"prompt": "Diagnose why the build broke overnight", "owner": "debugging-and-error-recovery"}
]
```

**어느 형제 스킬이 처리해야 하는지를 명시한다.** 무관한 반례는 아무것도 측정하지 않는다. `owner`가 지정된 반례는 경계를 측정한다([2.5](../part2/05-examples.md)).

그리고 하한을 CI로 강제한다.

```bash
node scripts/run-evals.js --min-rank1 95
```

### 직접 쓰는 방법

스킬 두 개 이상을 만들면 이 축이 필요하다. 최소 구현은 이렇다.

1. 스킬마다 양성 프롬프트 3개, 음성 프롬프트 2개를 쓴다
2. 음성 프롬프트에 `owner`를 적는다
3. 모든 `description`을 모아 유사도를 계산한다
4. 양성이 1순위인 비율과, `description` 쌍의 최대 유사도를 기록한다

TF-IDF는 수십 줄로 구현된다. **LLM 호출이 없어서 비용이 0이다.**

## 축 B — 기여

`DietrichGebert/ponytail`의 `benchmarks/arms/`다([7.3](../part7/03-single-purpose.md)).

### 세 팔이 필요한 이유

```
benchmarks/arms/
├── baseline.js          기준선 (스킬 없음)
├── caveman.js           조악한 대조군
├── caveman-SKILL.md
└── ponytail.js          스킬 적용
```

기준선 하나만 두면 남는 질문이 있다. 스킬이 좋아서 결과가 나아진 것인가, **아무 스킬이나 붙여도 달라지는 것인가.**

조악한 대조군을 두면 그 질문에 답한다.

| 비교 | 답하는 질문 |
|---|---|
| 스킬 vs 기준선 | 스킬이 기여하는가 |
| 스킬 vs **조악한 대조군** | **설계가 기여하는가** |

두 번째가 핵심이다. `ponytail`이 `caveman`보다 나으면 설계가 기여한 것이고, 비슷하면 "간결하게 쓰라고 말하기만 해도 되는" 것이다.

### 다중 모델

```
promptfooconfig.gemini.yaml
promptfooconfig.gpt.yaml
promptfooconfig.gpt-newest.yaml
```

세 모델에서 돌린다. **한 모델에서만 재면 그 모델에 과적합된 스킬인지 알 수 없다.**

### 측정 가능한 대리 지표

`loc.js`가 코드 줄 수를 센다. "가장 게으른 해법"이라는 주장을 직접 셀 수 있는 숫자로 잰다.

**주관적 스킬에서 이 방법이 중요하다.** 품질을 직접 재지 못하면 주장과 연결된 숫자를 찾는다.

| 스킬의 주장 | 대리 지표 |
|---|---|
| 가장 간결한 해법 | 코드 줄 수 |
| AI 티를 없앤다 | 패턴 출현 빈도 |
| 답을 묻지 않는다 | 결론까지의 거리 |
| 검증 가능한 다이어그램 | 코드 구조와의 일치율 |

마지막 줄은 `Agents365-ai/drawio-skill`이 구현했다 — 드리프트 디프다([8.7](../part8/07-design.md)).

## 축 C — 평가 신뢰도

`dotnet/skills`의 `eng/eval-quality/`다([6.5](../part6/05-microsoft.md)). **평가를 평가한다.**

### 왜 필요한가

`README` 첫 단락이 그 이유를 적는다.

> 대부분은 **평가가 자기 기준선에게 알 수 없이 패배했거나, 모든 시행에서 이겼는데도 실패한 뒤에야** 발견된 것들이다.

축 A와 B를 구현했다고 끝이 아니다. **그 측정 자체가 깨져 있을 수 있다.**

### 막는 결함

| 검사 | 막는 상황 |
|---|---|
| 참조된 픽스처가 없음 | 설정 실패인데 **스킬 실패로 기록된다** |
| 픽스처가 git에 없음 | 로컬에서는 되고 CI에서는 안 된다 |
| 빈 픽스처 디렉터리 | git이 빈 디렉터리를 보존하지 않는다 |

첫 번째가 교활하다. 입력 파일이 없어서 실패한 것을 "스킬이 못했다"로 기록하면 평가 결과 전체가 거짓이 된다. **수동 채점으로는 거의 발견되지 않는다.**

### 통계적 검정력

`underpowered-allowlist.txt`의 주석이다.

> 서로 다른 자극 하나가 게이트 투표 하나를 준다. **반복 실행은 그 자극의 신뢰도를 재는 것이고 독립 과제 표본을 늘리지 않는다.** 자극이 5개 미만이면 부호 검정이 어떤 효과 크기에서도 p ≤ 0.05에 도달할 수 없으므로, 어댑터는 이를 **검정력 부족**으로 보고한다 — 합격도 회귀도 아니다.

두 가지가 중요하다.

**반복 실행과 독립 표본을 구분한다.** 같은 테스트를 세 번 돌리면 분산을 알게 되지만 테스트가 세 개가 되지는 않는다.

**검정력 부족을 따로 분류한다.** 합격도 실패도 아닌 제3의 상태를 둔다. 자극 3개로 "100% 대 71%"를 측정했다면 그건 결론이 아니다.

### 이 책의 측정도 검정력 부족이다

[10.2](../part10/02-validation.md)에서 다룰 측정은 테스트 케이스가 3개였다. 이 기준으로는 검정력 부족이다.

**통과율 100% 대 71%를 "유의하다"고 쓸 수 없다.** 그 사실을 적어 두는 것이 정직한 처리다.

### 부채 장부

> 이 파일은 **부채 장부**이고 기계적으로 **축소 전용**이다. 게이트는 낡았거나 중복이거나 더 이상 필요 없는 항목에 오류를 내므로, 면제가 다른 평가에 조용히 재사용될 수 없다.

기준을 당장 다 만족시킬 수 없을 때 쓰는 현실적인 방법이다. 예외를 허용하되 목록으로 관리하고, **목록은 줄어들기만 한다.**

## 축 D — 형식

가장 싸고 가장 많이 구현됐다.

```bash
skills-ref validate ./my-skill
```

프런트매터 유효성과 이름 규칙을 검사한다([1.2](../part1/02-anatomy.md)). `name`이 디렉터리 이름과 다른 실수를 잡는다.

`github/awesome-copilot`의 `.schemas/`도 같은 층이다([6.7](../part6/07-github.md)). 444개 규모에서 기계로 형식 하한을 유지한다.

**한계가 분명하다.** 형식이 맞아도 스킬이 작동하지 않을 수 있다. 그리고 `Graphify-Labs/graphify`처럼 **규격을 따르지 않고도 12만 스타를 받는 저장소가 있다**([8.9](../part8/09-code-understanding.md)) — 형식 준수가 품질과 상관없다는 증거이기도 하다.

## 축 E — 안전

`NVIDIA/SkillSpector`다([6.8](../part6/08-others.md)). 71개 패턴, 17개 범주.

이 축은 품질이 아니라 **위험**을 재므로 다른 축과 성격이 다르다. 통과해도 좋은 스킬이라는 뜻이 아니고, 실패하면 설치하지 말아야 한다.

**다른 축보다 먼저 돌려야 한다.** 악성 스킬의 품질을 측정하는 것은 의미가 없다.

## 다섯 축을 합치는 순서

비용과 차단력을 함께 고려한 순서다.

| 순서 | 축 | 비용 | 실행 시점 | 실패하면 |
|---|---|---|---|---|
| 1 | E. 안전 | 낮음 | 설치, 배포 전 | **중단** |
| 2 | D. 형식 | 0 | 모든 커밋 | 중단 |
| 3 | C. 평가 신뢰도 | 0 | 모든 커밋 | 측정을 믿지 않는다 |
| 4 | A. 라우팅 | 0 | 모든 커밋 | `description`을 고친다 |
| 5 | B. 기여 | **높음 (토큰)** | 필요시 | 스킬을 고친다 |

**1~4번이 전부 공짜이거나 싸다.** 토큰을 쓰는 것은 5번뿐이다.

이 순서가 중요한 이유가 있다. 평가를 돌리는 비용 때문에 평가를 안 돌리는 것이 생태계의 현실이다. `addyosmani/agent-skills`가 Tier 1, 2를 CI에 두고 Tier 3를 필요시로 뺀 것이 그 문제를 구조로 푼 설계다([7.2](../part7/02-addyosmani.md)).

### 실패 해석표

측정 결과를 어떻게 읽는지가 중요하다. [3.7](../part3/07-evals.md)의 표를 확장한다.

| 상황 | 뜻 | 조치 |
|---|---|---|
| 스킬만 통과 | 변별력 있음 | 유지 |
| 양쪽 다 통과 | **변별력 없음** | 어서션 강화 또는 폐기 |
| 양쪽 다 실패 | 어서션이 틀렸거나 너무 어렵다 | 어서션 재검토 |
| **기준선만 통과** | **스킬이 해를 끼친다** | 스킬을 고친다 |
| 스킬 ≈ 조악한 대조군 | 설계가 기여하지 않는다 | 스킬을 단순화한다 |
| 모델에 따라 갈린다 | 과적합 | 지시를 일반화한다 |
| 자극 5개 미만 | **검정력 부족** | 결론을 내지 않는다 |

마지막 두 줄이 축 B와 C에서만 나온다. 축 A, D만 돌리면 보이지 않는다.

## 최소 평가 세트

스킬 하나를 만들었을 때 현실적으로 할 수 있는 최소한이다.

### 1. 형식 (0분)

```bash
skills-ref validate ./my-skill
```

### 2. 라우팅 (30분, 토큰 0)

| 항목 | 개수 |
|---|---|
| 양성 프롬프트 | 3개 (실제 사용자 문장으로) |
| 음성 프롬프트 | 2개 (**아슬아슬한 것**) |

음성 프롬프트에 `owner`를 적는다. 스킬이 하나면 `owner`는 "스킬 없이 처리"로 둔다.

### 3. 기여 (토큰 소모)

| 항목 | 내용 |
|---|---|
| 테스트 케이스 | 3개 — 전형적 성공 / 재료 부족 / **개입하면 안 되는 경우** |
| 팔 | 스킬 적용 / 기준선 (가능하면 조악한 대조군) |
| 어서션 | 금지선 중심 + **양성 어서션 1개 이상** |

세 번째 케이스와 양성 어서션이 빠지면 "아무것도 안 한 결과가 만점"을 받는다([3.7](../part3/07-evals.md)).

### 4. 기록 (5분)

| 기록할 것 | 왜 |
|---|---|
| 통과율 + 표준편차 | 평균만으로는 안정성을 모른다 |
| 소요 시간 | 스킬이 느려지게 하는가 |
| 토큰 | 스킬이 비싸게 하는가 |
| **자극 개수** | 5개 미만이면 결론을 내지 않는다 |
| 측정 날짜 | 모델이 바뀌면 결과가 바뀐다 |

마지막 줄이 생태계에서 거의 지켜지지 않는다. **평가 결과에 날짜가 없으면 그 결과는 재현 불가능하다.** 스타수에 날짜를 붙이는 것과 같은 이유다([0.1](../part0/01-this-repository.md)).

## 왜 공통 벤치마크가 안 생기는가

도구가 다 있는데 합쳐지지 않는다. 이유가 셋이다.

**1. 유형마다 평가가 다르다.** 실행형은 객관적이고 방법론형은 주관적이다([4.2](../part4/02-three-types.md)). 하나의 벤치마크로 둘을 재면 어느 쪽도 제대로 측정되지 않는다.

**2. 기준선 비교가 비싸다.** 테스트 케이스 하나에 두 번 이상 실행해야 하고, 모델 여러 개면 그 배수다. 공통 벤치마크를 돌리는 비용을 누가 부담할지가 정해지지 않았다.

**3. 측정할 동기가 약하다.** 스타수가 품질과 무관하게 붙는다면([9.1](01-star-traps.md)) 측정은 비용만 추가한다. `dotnet/skills`가 평가 인프라를 가장 잘 갖추고 1위의 1.9%인 것이 그 증거다.

세 번째가 근본적이다. **평가가 보상받지 않는 구조에서는 평가가 확산되지 않는다.**

바뀔 조건이 하나 있다. `NVIDIA/SkillSpector`가 보여 준 숫자 — 스킬 26.1%에 취약점, 5.2%가 악성 — 가 알려지면 **설치 전 검사가 관례가 될 수 있다.** 안전 검사가 관례가 되면 품질 검사도 따라올 여지가 생긴다. 보안이 품질 측정의 입구가 되는 경로다.
