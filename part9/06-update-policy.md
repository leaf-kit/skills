# 9.6 이 저장소의 갱신 규칙

이 저장소는 **leaf meta가 직접 관리하는 스킬 메타인지 저장소다**([0.1](../part0/01-this-repository.md)). 한 번 쓰고 닫는 원고가 아니다.

이 장은 갱신 규칙을 적는다. 규칙이 없으면 갱신이 안 되고, 갱신이 안 되는 큐레이션 저장소가 이 생태계에 흔하다([7.4](../part7/04-awesome-lists.md)).

## 왜 규칙이 필요한가

[7.4](../part7/04-awesome-lists.md)에서 확인한 것이다.

| 저장소 | 스타 | 마지막 푸시 |
|---|---|---|
| `travisvn/awesome-claude-skills` | 15,253 | 2026-04-28 |
| `Orchestra-Research/AI-Research-SKILLs` | 13,219 | 2026-06-16 |
| `heilcheng/awesome-agent-skills` | 6,257 | 2026-04-05 |

(수집 날짜: 2026-10-04)

스타 1만 5천 저장소가 5개월째 멈춰 있다.

**멈추는 이유가 구조적이다.** 모으는 비용은 0이고 유지하는 비용은 0이 아니다. 처음 만들 때는 검색 결과를 옮기면 되고, 유지하려면 매번 전체를 다시 확인해야 한다.

그래서 유지되는 큐레이션 저장소는 둘 중 하나다. **자동 생성되거나, 조직이 운영하거나.**

이 저장소는 둘 다 아니다. 개인이 운영하고 리뷰는 사람이 쓴다. **그래서 멈출 수 있다.**

이 사실을 숨기지 않는 쪽을 택한다. 멈추지 않겠다고 약속하는 대신 **낡았을 때 독자가 알 수 있게** 만든다.

## 설계 원칙 — 낡았을 때 보이게 한다

다섯 가지를 지킨다.

### 1. 모든 숫자에 수집 날짜를 붙인다

본문의 모든 순위표 머리에 날짜가 있다. 날짜 없는 스타수는 쓰지 않는다.

**하루에 1,000개 넘게 스타가 붙는 저장소가 있는 생태계에서**([0.2](../part0/02-why-stars.md)) 날짜 없는 숫자는 숫자가 아니다.

### 2. 숫자를 손으로 적지 않는다

모든 순위는 [`data/collect.sh`](../data/collect.sh)의 출력에서만 가져온다. 누구든 같은 스크립트를 돌려 같은 표를 다시 만들 수 있다.

**숫자가 책과 다르면 오류가 아니라 날짜 차이다.**

### 3. 확인 수준을 표시한다

| 표시 | 뜻 |
|---|---|
| 정밀 리뷰 | `README`와 실제 `SKILL.md`를 열어 보고 썼다 |
| 요약 리뷰 | 저장소 설명과 메타데이터만 보고 썼다 |

요약 리뷰는 메타데이터만 본다. **메타데이터에 폐기 사실이 없다**([9.1](01-star-traps.md)). 그래서 구분이 필요하다.

### 4. 확인하지 못한 것은 `[확인 필요: ...]`로 남긴다

빈칸을 추측으로 채우지 않는다. 추측으로 채운 숫자가 한 개라도 나오면 나머지 숫자도 믿을 수 없게 된다.

현재 `[확인 필요]` 항목이 본문에 여럿 있다. 그게 미완의 표시이고, 지워야 할 부채다.

### 5. 틀린 것을 기록으로 남긴다

조용히 덮어쓰지 않는다. 리뷰를 고칠 때 무엇이 어떻게 바뀌었는지 남긴다.

**리뷰는 시간이 지나면 틀린다.** 저장소가 구조를 바꾸거나 관리가 끊기거나 후속으로 대체된다. 고치는 것이 정상이고, 고친 내역이 남아야 독자가 무엇이 바뀌었는지 안다.

## 재수집 절차

```bash
cd data

# 1. 스타수 수집 (458개 규모, 몇 분)
./collect.sh

# 2. 스킬 저장소 판정 (상위 150개 파일 트리 조회)
./classify.sh stars-$(date +%Y-%m-%d).tsv 150
```

이전 수집분을 지우지 않는다. `snapshots/2026-10/stars.tsv`와 `stars-<새 날짜>.tsv`가 나란히 남아야 **변동**을 볼 수 있다.

## 갱신 점검표

재수집 뒤에 확인할 것들이다. 메타데이터만 보면 놓치는 것들을 모았다.

### A. 순위 변동

| 확인 | 왜 |
|---|---|
| 톱 30에 진입, 이탈한 저장소 | 리뷰 대상이 바뀐다 |
| 일평균 상위 저장소 | 지금 올라오는 것을 본다 |
| 경과일 90일 미만 저장소 | **일평균을 순위 근거로 쓰지 않는다**([9.1](01-star-traps.md)) |

### B. 상태 변화 — 메타데이터에 없는 것

| 확인 | 방법 | 발견 사례 |
|---|---|---|
| **폐기, 이전 표시** | 상위 저장소의 `README` **첫 단락**을 읽는다 | `openai/skills`가 폐기됐다 |
| 아카이브 여부 | API의 `archived` 필드 | — |
| 저장소 이전 | 리다이렉트 확인 | — |

**첫 줄이 가장 중요하다.** 폐기 사실은 설명, 토픽, 검색 결과에 없고 README에만 있다. 1분이면 확인되고, 안 하면 폐기된 저장소를 추천한다.

### C. 선별 규칙의 거짓 음성

| 확인 | 왜 |
|---|---|
| 스타 상위권에서 `SKILL.md`가 0개인 저장소 | **파일명 변형을 확인한다** |
| 설명에 "skill"이 있는데 판정에서 빠진 저장소 | 큐레이션, 규격, 파일명 변형 |

`Graphify-Labs/graphify`(123,488)가 이 점검으로 발견됐다. `SKILL.md`가 0개인데 `graphify/skill-<도구>.md`로 스킬 12개를 담고 있다([8.9](../part8/09-code-understanding.md)).

**전체 8위 저장소가 기계 판정에서 빠졌다.** 같은 유형이 더 있을 수 있다.

### D. 유형별 신선도

유형에 따라 같은 공백의 무게가 다르다.

| 유형 | 수명 | 3개월 공백 |
|---|---|---|
| 방법론형 | 길다 | 문제없다 |
| 실행형 | 중간 | 의존성 확인 |
| **지식형** | **짧다** | **사실이 틀렸을 수 있다** |
| **보안** | 짧다 | 새 위협이 반영되지 않았다 |

**지식형 + 규모가 큼 + 갱신 중단**이 가장 위험한 조합이다. `Orchestra-Research/AI-Research-SKILLs`가 지식형 98개를 담고 3.5개월 멈췄다([8.6](../part8/06-research.md)).

점검: **지식형, 보안 저장소의 마지막 푸시를 매 갱신마다 다시 본다.**

### E. 라이선스 변동

| 확인 | 왜 |
|---|---|
| `NOASSERTION` → 표준으로 바뀐 저장소 | 쓸 수 있게 됐다 |
| 라이선스가 사라진 저장소 | 쓸 수 없게 됐다 |
| AGPL, CC-BY-SA 신규 | 번들에 섞을 수 없다([9.4](04-licensing.md)) |

### F. 평가 인프라 신규

| 확인 | 왜 |
|---|---|
| `evals/`, `benchmarks/`, `tests/` 디렉터리가 생긴 저장소 | 드문 일이므로 기록할 가치가 있다 |

**"평가가 없다"고 쓰기 전에 파일 트리를 조회한다.** 설명이나 `README`에 적혀 있지 않아도 디렉터리가 있을 수 있다. `obra/superpowers`의 `tests/`와 `addyosmani/agent-skills`의 `evals/`가 그런 경우다 — 저장소 설명에 평가 언급이 없다.

**"없음"을 확인하는 일이 "있음"을 확인하는 일보다 소홀해진다.** 없는 것은 눈에 띄지 않기 때문이다. 파일 트리 조회는 API 호출 한 번이고 비용이 거의 없다.

## 리뷰 폐기 기준

리뷰를 지우거나 다시 쓰는 조건이다.

| 조건 | 조치 |
|---|---|
| 저장소가 폐기, 아카이브됐다 | 리뷰를 남기고 **폐기 표시를 머리에 붙인다** |
| 저장소가 사라졌다 | 리뷰를 남기고 "접근 불가"로 표시 |
| 구조가 크게 바뀌었다 | 다시 정밀 리뷰 |
| 1년 이상 푸시가 없다 | 지식형, 보안이면 경고를 붙인다 |
| 판단의 근거가 사실과 달랐다 | **고치고 무엇이 틀렸는지 적는다** |

**첫 줄이 중요하다.** 폐기된 저장소의 리뷰를 지우지 않는다. `openai/skills`가 폐기됐는데 스타 27,856으로 톱 30에 있다는 사실 자체가 생태계에 대한 정보다([9.1](01-star-traps.md)).

## 갱신 주기

주기는 관측된 변동 속도에서 정한다.

**분기(3개월)로 한다.** 근거는 수집 데이터다.

| 관측 | 함의 |
|---|---|
| 생태계 전체가 1년 안쪽 | 변동이 빠르다 |
| 가장 빠른 저장소가 일평균 1,364 | 순위가 몇 달에 뒤집힌다 |
| 신규 생성이 2026-04 정점 이후 감소 | 변동이 느려지고 있다 |
| 지식형 저장소의 3개월 공백이 위험 | 3개월이 의미 있는 단위 |
| 큐레이션 저장소가 5개월에 멈춘 사례 | 5개월은 너무 길다 |

**3개월이 지식형 신선도 기준과 맞고, 5개월 방치 사례보다 짧다.**

다만 분기 전체 갱신과 별도로 **가벼운 점검**을 둔다.

| 작업 | 주기 | 비용 |
|---|---|---|
| 데이터 재수집 (`collect.sh` + `classify.sh`) | 1개월 | 몇 분 |
| 순위 변동 기록 | 1개월 | 짧다 |
| 상위 30개 README 첫 단락 확인 | 1개월 | 30분 |
| 리뷰 본문 갱신 | **3개월** | 길다 |
| 선별 규칙 재검토 | 3개월 | 중간 |

**데이터는 자주, 리뷰는 분기로.** 데이터 수집은 스크립트이므로 싸고, 리뷰는 사람이 쓰므로 비싸다.

## 다음 갱신의 과제

현재 남아 있는 공백이다.

| 과제 | 왜 |
|---|---|
| **상위 저장소에 `SkillSpector`를 돌린다** | 이 책은 리뷰 대상을 스캔하지 않았다([9.3](03-supply-chain.md)) |
| `[확인 필요]` 항목을 줄인다 | 미완의 부채다 |
| 5.2의 정밀 리뷰를 30개에서 늘릴지 결정 | 분량과 깊이의 교환 |
| 150위 아래로 판정 범위를 넓힐지 결정 | 비용과 의미가 갈리는 선 |
| 라이선스 스캐너를 만들지 검토 | 비어 있는 자리이고 만들기 쉽다([9.5](05-saturation.md)) |

첫 줄이 가장 크다. **이 책의 "골라 쓰는 기준" 표들은 설계 품질에 대한 판단이고 안전성 보증이 아니다.** 스킬 26.1%에 취약점이 있다는 통계가 있는 생태계에서, 리뷰서가 스캔을 하지 않은 것은 공백이다.

## 기여

틀린 것을 발견하면 이슈로 알려 주면 된다.

| 종류 | 처리 |
|---|---|
| 사실 오류 (숫자, 날짜, 구조) | 고치고 수정 기록을 남긴다 |
| 놓친 저장소 | 선별 규칙에 맞는지 확인하고 추가 |
| 판단에 대한 이견 | **근거가 사실과 다르면 고치고, 근거는 맞는데 결론이 다르면 관점 차이다** |

마지막 줄을 적어 두는 이유가 있다. 이 책의 리뷰에는 근거를 같이 적어 두었다. **관점 차이를 지우려고 근거를 바꾸지 않는다.**
