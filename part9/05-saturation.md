# 9.5 중복과 포화

같은 문제를 푸는 저장소가 수십 개씩 있다. 이 장은 왜 그런지, 어떤 중복이 낭비이고 어떤 중복이 필요한지를 가른다.

## 중복이 생기는 이유 — 비용 구조

### 만드는 비용이 거의 0이다

| 생태계 | 새 프로젝트를 만드는 비용 |
|---|---|
| 라이브러리 | 설계 + 구현 + 테스트 + 패키징 |
| CLI 도구 | 설계 + 구현 + 배포 |
| **스킬** | **마크다운 파일 하나** |

공식 템플릿이 다섯 줄이다([6.1](../part6/01-anthropic-skills.md)).

```markdown
---
name: template-skill
description: Replace with description of the skill and when Claude should use it.
---

# Insert instructions below
```

**진입 비용이 0에 가까우면 공급이 수요를 넘어선다.**

### 찾는 비용이 만드는 비용보다 크다

이게 핵심이다.

표준 디스커버리가 없다([6.6](../part6/06-cloudflare.md)). "example.com은 어떤 스킬을 공개하는가"에 답하는 방법이 없다.

그래서 이런 선택이 생긴다.

| 선택 | 비용 |
|---|---|
| 남의 스킬을 찾는다 | 검색 → 여러 후보 → 읽고 평가 → 내 상황에 맞는지 판단 |
| 직접 만든다 | 마크다운 파일 하나 |

**찾아서 평가하는 비용이 만드는 비용보다 크면 다들 만든다.**

그리고 찾아낸 스킬이 70% 맞으면 고쳐 쓰고, 30% 맞으면 새로 쓰는 쪽이 빠르다([2.6](../part2/06-promotion.md)). 맞는 비율을 알려면 읽어야 하고, 읽는 것이 비용이다.

### 승자가 정해지는 메커니즘이 없다

다른 생태계에는 중복을 정리하는 장치가 있다.

| 생태계 | 정리 장치 |
|---|---|
| npm | 다운로드 수, 의존성 그래프 |
| 리눅스 배포판 | 패키지 저장소의 선택 |
| 언어 표준 라이브러리 | 표준에 편입 |
| **스킬** | **없음** |

스킬에는 다운로드 수가 없고, 품질 벤치마크가 없고([9.2](02-measuring-quality.md)), 공식 저장소에 편입되는 경로도 명확하지 않다.

**남는 지표는 스타수이고, 스타수는 "누가 더 잘 푸는가"가 아니라 "누가 먼저 눈에 띄었는가"를 반영한다**([9.1](01-star-traps.md)).

### 효과가 즉시 보이지 않으면 비교하지 않는다

도메인마다 중복의 심각도가 다르다.

| 도메인 | 효과 확인 시점 | 중복 |
|---|---|---|
| 출력 형식 변경 | 즉시 | 적다 |
| 다이어그램 | 즉시 | 중간 |
| 코드리뷰 | 즉시 | 중간 |
| **메모리** | **몇 주** | **심하다** |
| 개발 방법론 | 몇 주~몇 달 | 중간 |
| 제품 관리 | 몇 달 | 적다 (수요가 작다) |

**메모리가 가장 심한 이유가 여기 있다.** 일곱 개를 비교하려면 각각 설치해서 몇 주 써 봐야 한다. 그래서 비교하지 않고, 먼저 눈에 띈 것을 쓴다.

[7.3](../part7/03-single-purpose.md)에서 단일 목적 스킬이 터지는 조건으로 "효과가 즉시 보인다"를 꼽았다. 같은 조건이 **중복 정리**에도 작용한다. 즉시 보이면 비교되고, 비교되면 승자가 생긴다.

## 어떤 중복이 필요한가

모든 중복이 낭비는 아니다. 세 종류로 갈린다.

### 1. 낭비 — 같은 문제, 같은 조건

메모리 저장소 일곱 개가 여기 속한다. 조건이 같다. 같은 결핍, 같은 사용자, 같은 환경이다.

**합쳐지는 쪽이 모두에게 이득인데 합쳐지지 않는다.** 일곱 팀이 같은 문제를 각자 풀고, 사용자는 일곱 개 중 고르는 비용을 부담한다.

큐레이션 저장소의 이름 중복도 여기 속한다. `awesome-agent-skills`가 셋이면 사용자가 셋을 다 봐야 한다.

### 2. 필요 — 같은 문제, 다른 조건

AI 글 교정 스킬이 세 언어로 있다([8.5](../part8/05-writing.md)).

| 저장소 | 언어 | 스타 |
|---|---|---|
| `blader/humanizer` | 영어 | 53,730 |
| `epoko77-ai/im-not-ai` | 한국어 | 5,835 |
| `KKKKhazix/human-writing` | 중국어 | 3,937 |

**번역으로 해결되지 않는다.** AI 글의 흔적이 언어마다 다르다.

| 패턴 | 영어 | 한국어 |
|---|---|---|
| 번역투 | 없다 (생길 수 없다) | **주된 흔적** |
| 피동태 남용 | 없다 | 있다 |
| 엠 대시 남용 | 있다 | 없다 (관습이 약하다) |
| 억지 삼단 나열 | 있다 | 있다 |

공통 패턴 일부 + 언어별 고유 패턴이고, 고유 패턴 때문에 각 언어에서 다시 만들어야 한다.

**이건 중복이 아니라 재구현이다.** 같은 이름으로 불리지만 다른 문제를 푼다.

같은 구조가 플랫폼에도 적용된다. `cloudflare/skills`, `google/skills`, `microsoft/skills`가 다 "제품 사용법"인데 제품이 다르므로 중복이 아니다.

### 3. 탐색 — 같은 문제, 다른 설계

코드리뷰 도메인이 이 예다([8.2](../part8/02-code-review.md)).

| 저장소 | 분할 축 |
|---|---|
| `obra/superpowers` | 역할 (요청자 / 수신자) |
| `alibaba/open-code-review` | 실행 방식 (직접 / 위임) |
| `addyosmani/agent-skills` | 없음 (통합) |
| `backnotprop/plannotator` | 리뷰 대상 (코드 / **계획**) |
| `coldteadotai/pr-lens` | 출력 형식 (텍스트 / **다이어그램**) |

**다섯 가지 설계가 탐색되고 있다.** 정답이 없는 단계에서는 여러 설계가 공존하는 것이 유익하다.

보안 도메인에서도 같다. 같은 문제(코드베이스 감사)에 세 구조가 나왔다([8.1](../part8/01-security.md)).

| 저장소 | 구조 | 스타 |
|---|---|---|
| `cloudflare/security-audit-skill` | 스킬 1개 + 참조 14개 | 23,902 |
| `anthropics/defending-code-reference-harness` | 단계별 스킬 9개 | 7,542 |
| `trailofbits/skills` | 플러그인별 스킬 85개 | 7,351 |

**탐색이 끝나면 하나로 수렴할 것이고, 지금은 수렴하지 않는 것이 맞다.**

## 포화의 신호

신규 저장소 생성이 줄고 있다([5.4](../part5/04-patterns.md)).

| 연월 | 저장소 수 |
|---|---|
| 2026-03 | 59 |
| 2026-04 | 57 |
| 2026-05 | 28 |
| 2026-06 | 24 |
| 2026-07 | 19 |
| 2026-08 | 16 |
| 2026-09 | 13 |

(수집 날짜: 2026-10-04. 수집 목록 기준)

2026년 3~4월이 정점이고 이후 다섯 달 연속 감소한다.

**해석에 주의가 필요하다.** 이 데이터는 지금 스타수가 높은 저장소를 모은 것이다. 최근에 만들어진 저장소는 스타를 모을 시간이 적어서 목록에 덜 들어온다.

다만 두 가지는 말할 수 있다. **상위권 진입이 어려워졌고**, 선점된 영역이 많아졌다.

### 왜 상위권 진입이 어려워지는가

| 영역 | 선점 상태 |
|---|---|
| 개발 방법론 | `superpowers`(294,779), `addyosmani`(100,755) |
| 간결함 강제 | `ponytail`(152,808) |
| AI 글 교정 (영어) | `humanizer`(53,730) |
| 출력 구조 | `i-have-adhd`(53,105) |
| 디자인 취향 | `taste-skill`(92,269) |
| 다이어그램 | `archify`(76,618), `diagram-design`(43,213) |
| 메모리 | 일곱 개 경합 |
| 보안 감사 | `security-audit-skill`(23,902) |

**보편적 결핍 + 한 문장 설명 + 즉시 확인 가능**의 조합이 거의 다 선점됐다([7.3](../part7/03-single-purpose.md)).

남은 자리는 두 종류다. **좁은 도메인**(대상 인구가 작다)과 **언어, 지역**(재구현이 필요하다)이다. 둘 다 스타수 상한이 낮다.

## 빈 자리

포화된 영역과 비어 있는 영역이 나뉜다. 리뷰에서 반복적으로 "없다"고 적은 것들이다.

| 빈 자리 | 왜 비어 있나 |
|---|---|
| **범용 품질 벤치마크** | 측정이 보상받지 않는다([9.2](02-measuring-quality.md)) |
| **라이선스 스캐너** | 아무도 문제라고 인식하지 않는다([9.4](04-licensing.md)) |
| **표준 디스커버리** | RFC가 Draft이고 관례가 먼저 자리 잡았다([6.6](../part6/06-cloudflare.md)) |
| 메모리 오염 대응 | 메모리 도구들이 다루지 않는다([8.4](../part8/04-memory.md)) |
| 인용 검증 | 연구 스킬에 없다([8.6](../part8/06-research.md)) |
| 스킬 버전, 의존성 관리 | 레지스트리가 없다 |

**세 번째까지가 도구로 만들 수 있고 만들어지지 않은 것들이다.**

라이선스 스캐너가 가장 만들기 쉽다. `SKILL.md`의 프런트매터에서 `license`를 읽고, 디렉터리의 `LICENSE` 파일을 찾고, 번들 전체의 호환성을 확인하면 된다. npm 생태계의 `license-checker`에 해당한다. 기술적으로 어렵지 않다.

## 중복을 줄이는 방법

생태계 차원과 개인 차원으로 나뉜다.

### 생태계 차원

| 방법 | 효과 | 상태 |
|---|---|---|
| 표준 디스커버리 | 찾는 비용을 낮춘다 | RFC Draft |
| 품질 벤치마크 | 승자를 정한다 | 없다 |
| 레지스트리 | 다운로드 수가 생긴다 | 없다 |
| 이름 공간 | 이름 충돌을 막는다 | 없다 |

**첫 번째가 가장 효과가 크다.** 찾는 비용이 만드는 비용보다 작아지면 중복 생성 동기가 줄어든다.

### 개인 차원 — 만들기 전에

| 확인 | 방법 |
|---|---|
| 이미 있는가 | `awesome-*` 목록 두세 개를 본다 |
| 70% 이상 맞는가 | 맞으면 포크해서 고친다 |
| 조건이 다른가 | 언어, 플랫폼, 규모가 다르면 재구현이 맞다 |
| 설계가 다른가 | 다른 분할 축을 시도하는 것이면 가치가 있다 |
| 같은 조건, 같은 설계인가 | **만들지 않는다. 기존 저장소에 기여한다** |

마지막 줄이 실제로는 가장 어렵다. 남의 저장소에 기여하는 비용이 자기 저장소를 만드는 비용보다 크다 — 코드를 이해해야 하고, 리뷰를 받아야 하고, 머지를 기다려야 한다.

**MIT 라이선스가 포크를 쉽게 만드는 것도 중복을 늘린다.** `jnMetaCode/superpowers-zh`(8,256)가 원본의 중국어 확장판인데, 원본에 중국어 지원을 추가하는 대신 포크했다([7.5](../part7/05-regional.md)). 그게 나쁜 선택은 아니다 — 번역은 원본 저장소가 유지하기 어려운 종류의 기여다.

### 개인 차원 — 고를 때

| 상황 | 기준 |
|---|---|
| 일곱 개가 경합한다 | **가장 단순한 것부터 시도한다** |
| 효과가 즉시 안 보인다 | 평가를 포함한 저장소를 고른다 |
| 설계 축이 다르다 | 내 상황에 맞는 축을 고른다 |

첫 번째를 메모리 도메인에 적용하면 `planning-with-files`가 답이 된다. 계획을 파일에 쓰는 것으로 해결되는 문제에 메모리 계층을 설치하면 설치, 검증, 유지 비용이 추가되고 메모리 오염 위험이 생긴다([8.4](../part8/04-memory.md)).
