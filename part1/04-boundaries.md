# 1.4 스킬, 서브에이전트, MCP, 플러그인, 훅

에이전트를 확장하는 수단이 다섯 가지쯤 된다. 이름이 비슷하고 경계가 겹쳐서, 스킬로 만들 일을 MCP 서버로 만들거나 그 반대로 가는 일이 흔하다. 잘못 고르면 동작은 하는데 비용이 크거나, 필요한 순간에 작동하지 않는다.

이 장은 다섯 가지를 구분한다. 리뷰(6, 7, 8부)에서 "이건 스킬이 아니라 MCP로 갈 일이었다"는 평가가 나오므로, 그 말의 근거를 먼저 세운다.

## 한 장으로 보는 차이

| 수단 | 실체 | 언제 작동하나 | 무엇을 늘리나 |
|---|---|---|---|
| **스킬** | `SKILL.md` + 번들 파일 | 에이전트가 필요하다고 판단할 때 | **지식과 절차** |
| **서브에이전트** | 별도 컨텍스트에서 도는 에이전트 | 본 에이전트가 위임할 때 | **컨텍스트 분리** |
| **MCP 서버** | 도구를 제공하는 프로세스 | 그 도구를 호출할 때 | **할 수 있는 일** |
| **플러그인** | 위 요소들을 묶은 배포 단위 | 설치돼 있으면 상시 | **배포와 설치** |
| **훅** | 특정 시점에 실행되는 명령 | 정해진 시점마다 **항상** | **강제성** |

가장 중요한 축은 **스킬 대 MCP**다. 나머지는 상대적으로 구분이 쉽다.

## 스킬 대 MCP — 지식인가 능력인가

판단 질문은 하나다. **"에이전트가 방법을 몰라서 못 하는가, 수단이 없어서 못 하는가."**

| | 스킬 | MCP 서버 |
|---|---|---|
| 해결하는 결핍 | 방법을 모른다 | 수단이 없다 |
| 실체 | 텍스트 | 실행되는 프로세스 |
| 설치 | 파일 복사 | 프로세스 등록, 인증, 네트워크 |
| 비용 | 읽을 때만 | 상시 (도구 정의가 항상 로딩) |
| 외부 상태 | 접근 못 함 | 접근함 |

예를 들어 보자.

**"우리 회사 커밋 메시지 규칙에 맞게 커밋해 달라"** — 에이전트는 `git commit`을 할 수 있다. 수단은 있고 우리 규칙을 모를 뿐이다. → **스킬**

**"지라 티켓 상태를 In Review로 바꿔 달라"** — 에이전트는 지라에 접근할 방법이 없다. 절차를 아무리 잘 적어도 못 한다. → **MCP 서버**

**"PDF 양식을 채워 달라"** — 애매하다. 파이썬이 있으면 수단은 있다. 다만 어떤 라이브러리로 어떤 순서로 하는지가 까다롭다. → **스킬** (공식 `pdf` 스킬이 이 선택을 했고, 스크립트를 번들해서 "수단" 쪽도 보강했다)

세 번째가 실무에서 가장 많은 경우다. 수단이 아주 없는 건 아니고, 절차가 복잡해서 매번 다르게 실행되는 상황이다. 이때는 **스킬 + `scripts/`** 조합이 답이다. 지식을 주면서 실행 경로도 고정한다.

### MCP를 쓸 때도 스킬이 필요하다

둘은 대립하지 않는다. MCP 서버가 도구 20개를 제공하면 에이전트는 그 도구들을 **쓸 수** 있게 되지만, **잘 쓰는 법**은 모른다. 어떤 순서로 호출할지, 어떤 조합이 위험한지, 이 조직에서 금지된 사용법이 무엇인지는 도구 정의에 안 들어간다.

그래서 MCP 서버를 붙이고 그 서버를 잘 쓰는 법을 스킬로 적는 패턴이 생긴다. 수집 데이터에서 `timescale/pg-aiguide`(1,854)가 이 구조다. 설명이 "Postgres 스킬과 문서를 위한 MCP 서버 및 플러그인"이다. 서버와 스킬을 같이 배포한다.

공식 저장소의 `mcp-builder` 스킬도 같은 방향의 증거다. **MCP 서버를 만드는 법을 가르치는 스킬**이다. 236줄 본문에 번들 10개 파일, 121KB다. MCP와 스킬이 경쟁 관계면 이런 스킬이 존재할 이유가 없다.

## 스킬 대 서브에이전트 — 누가 읽는가

서브에이전트는 **별도 컨텍스트에서 도는 에이전트**다. 본 에이전트가 작업을 넘기고 결과만 받는다.

겹치는 지점이 있다. 둘 다 "특정 작업을 위한 지시문"을 담는다. 차이는 컨텍스트다.

| | 스킬 | 서브에이전트 |
|---|---|---|
| 읽는 주체 | 본 에이전트 | 별도 에이전트 |
| 중간 과정 | 본 컨텍스트에 쌓인다 | 본 컨텍스트에 안 쌓인다 |
| 결과 | 작업 결과 그대로 | 요약된 보고 |
| 적합한 작업 | 결과를 이어서 써야 하는 일 | 과정이 길고 결과만 필요한 일 |

판단 질문: **"중간 과정을 본 대화에 남겨야 하는가."**

파일 50개를 뒤져서 특정 패턴을 찾는 작업은 과정이 길고 결과는 한 줄이다. 중간에 읽은 50개 파일이 본 컨텍스트에 쌓이면 손해다. → 서브에이전트

글을 고치는 작업은 고친 결과를 사용자가 바로 봐야 하고, 이어지는 대화에서 그 글을 계속 다룬다. → 스킬

**둘을 같이 쓰는 경우도 있다.** 스킬이 "이 단계는 서브에이전트에 맡겨라"라고 지시할 수 있다. 공식 `skill-creator` 스킬이 이 구조다. 스킬 평가를 돌릴 때 테스트 케이스마다 서브에이전트를 띄우라고 지시한다. 테스트 실행 과정이 본 컨텍스트에 쌓이면 평가 자체가 불가능해지기 때문이다.

## 플러그인 — 배포 단위

플러그인은 새로운 종류가 아니다. **스킬, 서브에이전트, MCP 서버 설정, 훅, 슬래시 명령을 하나로 묶은 배포 단위**다.

스킬 하나를 쓰라고 할 때는 "이 디렉터리를 복사하세요"면 된다. 스킬 12개 + MCP 서버 2개 + 훅 3개를 쓰라고 하면 그렇게 안 된다. 플러그인이 그 문제를 푼다.

수집 데이터에서 `anthropics/claude-plugins-official`(37,338)이 공식 디렉터리다. `SKILL.md`를 33개 담고 있다. 플러그인 저장소인데 스킬을 담고 있다는 사실이 둘의 관계를 보여준다. 플러그인은 그릇이고 스킬이 내용이다.

리뷰할 때 주의할 점이 하나 있다. 플러그인 저장소의 스타수는 그 안의 어떤 스킬이 좋아서 붙은 것인지 알 수 없다. 12개 중 1개만 쓰는 사람도 스타를 누른다. [7.4 큐레이션 저장소의 경제학](../part7/04-awesome-lists.md)에서 같은 문제를 다룬다.

## 훅 — 유일하게 강제되는 것

훅은 정해진 시점에 **항상** 실행되는 명령이다. 에이전트가 판단하지 않는다.

이 차이가 결정적이다. 스킬은 에이전트가 "필요하다"고 판단해야 작동한다. 판단이 들어가면 틀릴 수 있다. 훅은 판단이 없다.

| | 스킬 | 훅 |
|---|---|---|
| 실행 결정 | 에이전트의 판단 | 조건 없이 시점마다 |
| 안 돌 수 있나 | 있다 (과소 트리거) | 없다 |
| 담는 것 | 지시문 | 실행 명령 |

판단 질문: **"이게 안 돌았을 때 사고가 나는가."**

"파일을 쓴 뒤에 항상 포맷터를 돌려라"는 스킬로 만들면 안 된다. 열 번 중 아홉 번 돌고 한 번 안 돌면 그 한 번이 문제다. 훅으로 만든다.

"글을 고칠 때는 이 기준으로 봐라"는 훅으로 만들 수 없다. 실행할 명령이 아니라 판단 기준이기 때문이다. 스킬이다.

그래서 "앞으로 X할 때마다 Y해"라는 요구는 거의 항상 훅이다. 기억이나 지침에 적어 두는 것으로는 보장되지 않는다.

## 고르는 순서

다섯 가지 중에서 고를 때 이 순서로 묻는다.

1. **안 돌면 사고가 나는가** → 훅
2. **외부 시스템에 접근해야 하는가** → MCP 서버
3. **과정이 길고 결과만 필요한가** → 서브에이전트
4. **방법을 몰라서 못 하는가** → 스킬
5. **위 여러 개를 함께 배포해야 하는가** → 플러그인으로 묶기

4번이 가장 넓은 범주다. 생태계에 스킬 저장소가 458개 생긴 이유이기도 하다. 대부분의 문제가 "할 수는 있는데 우리 방식대로 못 한다"이고, 그게 스킬의 자리다.

## 경계가 흐려지는 지점

마지막으로 분류가 깔끔하지 않은 사례를 적어 둔다.

**스킬이 스크립트로 외부에 접근하는 경우.** `scripts/`의 파이썬 코드가 API를 호출하면, 형식은 스킬인데 기능은 MCP와 겹친다. 규격이 막지 않는다. 차이는 인증과 권한 관리를 누가 하느냐로 남는다.

**디스커버리 문제.** 스킬은 로컬 파일이라서, 설치하지 않은 스킬은 존재 자체가 안 보인다. MCP 서버는 등록되면 도구 목록으로 노출된다. `cloudflare/agent-skills-discovery-rfc`(351)가 이 간극을 다룬다 — `.well-known`으로 스킬을 발견하자는 제안이다. 스타 351개로 작지만, 생태계가 어디서 막혀 있는지를 보여주는 저장소다.
