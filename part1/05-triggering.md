# 1.5 스킬은 어떻게 선택되는가

스킬을 아무리 잘 써도 불리지 않으면 없는 것과 같다. 이 생태계에서 가장 흔한 실패는 스킬이 나쁜 것이 아니라 **스킬이 안 불리는 것**이다.

이 장은 선택 메커니즘을 정리한다. [3.2 description 설계](../part3/02-description.md)의 전제가 되고, 리뷰에서 "이 스킬은 과소 트리거된다"고 쓸 때의 근거가 된다.

## 메커니즘

규격이 1단계로 정의한 그대로다. 설치된 모든 스킬의 `name`과 `description`이 시작할 때 로딩된다. 에이전트가 보는 것은 이런 목록이다.

```
사용 가능한 스킬:
- pdf: Use this skill whenever the user wants to do anything with PDF files...
- xlsx: ...
- mcp-builder: Guide for creating high-quality MCP servers...
- diff-review: 파이썬 변경분을 리뷰해 결함과 위험 패턴을 찾는다...
```

사용자가 요청을 보내면 에이전트가 이 목록을 보고 **읽을지 말지 판단한다.** 본문은 아직 안 읽은 상태다. 즉 판단 근거는 `description` 한 덩어리뿐이다.

여기서 중요한 사실이 따라온다. **`SKILL.md` 본문에 "이럴 때 쓰라"고 적어도 트리거에 영향을 주지 않는다.** 본문은 선택된 뒤에 읽히기 때문이다. 트리거 조건은 전부 `description`에 있어야 한다.

이걸 모르면 이렇게 쓴다.

```markdown
---
name: report-builder
description: 보고서를 만든다.
---

# 보고서 작성

## 이 스킬을 쓰는 경우
- 주간 보고서를 쓸 때
- 월간 실적을 정리할 때
- 임원 보고 자료를 만들 때
- 데이터를 표로 요약해야 할 때
```

"이 스킬을 쓰는 경우"가 본문에 있다. 선택된 뒤에 읽히므로 선택에 아무 기여를 하지 않는다. 저 네 줄은 `description`으로 올라가야 한다.

## 과소 트리거가 기본값이다

에이전트는 스킬을 적극적으로 찾지 않는다. **스스로 처리할 수 있다고 판단하면 스킬을 건너뛴다.**

이유를 이해할 필요가 있다. 스킬을 읽는 것은 비용이다. 간단한 요청마다 스킬 본문을 열면 느리고 비싸다. 그래서 에이전트는 "내가 그냥 하면 되는 일"과 "참고할 게 필요한 일"을 구분하려 한다. 이 구분이 보수적인 쪽으로 기울어 있다.

결과적으로 두 가지가 나타난다.

**단순한 요청은 스킬을 안 부른다.** "이 PDF 읽어 줘"는 스킬 설명이 완벽하게 들어맞아도 트리거되지 않을 수 있다. 에이전트가 기본 도구로 바로 할 수 있는 일이기 때문이다. 복잡하고 여러 단계인 요청일 때 스킬이 안정적으로 불린다.

**설명이 점잖으면 안 불린다.** `description`을 중립적으로 쓰면 "참고 자료가 있다"로 읽히고, 참고할 필요가 없다고 판단되면 건너뛴다.

그래서 `description`을 의도적으로 **밀어붙이게** 쓰는 관례가 생겼다. 공식 `pdf` 스킬의 설명이 이렇게 끝난다.

> If the user mentions a .pdf file or asks to produce one, use this skill.

"PDF 파일을 언급하면 이 스킬을 쓰라"고 지시한다. 설명이 아니라 명령이다. 같은 저장소의 다른 스킬도 "Use this skill whenever..."로 시작한다.

## 트리거 실패의 세 가지 유형

### 1. 키워드 누락

사용자가 실제로 쓰는 말이 `description`에 없는 경우다.

AI 흔적을 지우는 스킬을 만들면서 `description`에 "slop"만 적으면, 사용자가 "이거 AI가 쓴 것 같은데 좀 고쳐 줘"라고 할 때 안 걸린다. 사용자는 "slop"이라는 단어를 쓰지 않는다.

한국어 환경에서는 문제가 더 커진다. 같은 뜻을 가리키는 표현이 여러 개다. 퇴고, 다듬기, 윤문, 교정, 손보기, 고치기가 다 같은 요청일 수 있다. **한국어와 영어 키워드를 같이 넣는 것이 사실상 필수다.**

### 2. 요청이 너무 단순함

앞서 말한 구조적 특성이다. 해결 방법이 `description`에 있지 않다. 설명을 고쳐도 "이 파일 읽어 줘" 수준의 요청은 안 걸린다.

이건 결함이 아니라 설계다. 다만 스킬을 평가할 때 이 점을 알고 있어야 한다. 단순한 테스트 프롬프트로 트리거를 재면 어떤 `description`을 써도 점수가 나쁘게 나온다. [3.7 평가 만들기](../part3/07-evals.md)에서 이 함정을 다룬다.

### 3. 경쟁 스킬에 밀림

비슷한 스킬이 여러 개 설치돼 있으면 하나만 선택된다. `description`이 겹치면 어느 쪽이 불릴지 예측하기 어렵다.

그래서 `description`에 **쓰지 않을 조건**을 적는 것이 도움이 된다.

```yaml
description: ... 반대로 코드, 로그, 명세서, 번역처럼 문체가 아니라 정확성이
  목적인 글에는 쓰지 않는다.
```

제외 조건은 두 가지 일을 한다. 엉뚱한 트리거를 줄이고, 경쟁 스킬과의 경계를 그린다.

## 과잉 트리거도 문제다

반대 방향을 짧게 적어 둔다. `description`을 넓게 쓰면 관계없는 작업에도 불린다.

"글"이라는 단어로 넓게 잡은 교정 스킬은 커밋 메시지를 쓸 때도, 로그 메시지를 쓸 때도 불린다. 그때마다 본문이 읽히고, 문체 기준으로 기술 문서를 고치려 든다.

**과잉 트리거의 비용은 과소 트리거보다 눈에 잘 띄지 않는다.** 안 불리는 건 "왜 안 되지?"로 바로 드러나고, 잘못 불리는 건 "결과가 좀 이상한데"로 흐려진다. 그래서 과잉 쪽이 더 오래 방치된다.

균형점은 **넓은 키워드 + 명시적 제외 조건**이다. 키워드를 좁혀서 과잉을 막으면 과소가 생긴다. 넓게 잡고 제외로 깎는 쪽이 낫다.

## 트리거를 측정하는 방법

트리거는 추측하지 않고 재는 것이 맞다. 방법은 이렇다.

1. **걸려야 할 요청 8~10개**와 **걸리면 안 되는 요청 8~10개**를 만든다.
2. 각각을 실제로 실행해서 스킬이 불렸는지 기록한다.
3. 같은 요청을 여러 번 돌린다. 트리거는 결정적이지 않다.

핵심은 2번의 질문 품질이다. "PDF 읽어 줘" 같은 추상적인 요청은 테스트가 안 된다. 실제 사용자가 쓸 만한, 구체적이고 맥락이 붙은 요청이어야 한다. 파일 경로, 회사 이름, 열 이름, 사연이 섞인 문장이 좋은 테스트 케이스다.

걸리면 안 되는 요청은 **아슬아슬한 것**이 가치 있다. 전혀 무관한 요청을 넣으면 아무것도 측정되지 않는다. PDF 스킬의 반례로 "피보나치 함수 써 줘"를 넣으면 통과는 하지만 알아낸 게 없다. 키워드는 겹치는데 실제로는 다른 일이 필요한 요청이 좋은 반례다.

이 측정 절차와 자동화는 [3.2](../part3/02-description.md)에서 구체적으로 다룬다.

## 요약

| 사실 | 따라오는 결론 |
|---|---|
| 판단 근거는 `description`뿐이다 | 트리거 조건을 본문에 적지 않는다 |
| 에이전트는 보수적으로 건너뛴다 | 설명이 아니라 지시로 쓴다 |
| 단순한 요청은 안 걸린다 | 단순한 프롬프트로 트리거를 재지 않는다 |
| 사용자의 말과 내 말이 다르다 | 한국어, 영어 키워드를 같이 넣는다 |
| 넓히면 과잉, 좁히면 과소 | 넓게 잡고 제외 조건으로 깎는다 |
| 트리거는 결정적이지 않다 | 같은 요청을 여러 번 돌려 센다 |
