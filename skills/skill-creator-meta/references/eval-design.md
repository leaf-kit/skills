# 평가 설계

평가가 어려운 이유는 돌리기가 어려워서가 아니다. **통과하는 평가를 만들기가 너무 쉬워서**다. 이 문서는 그 함정을 피하는 방법을 적었다.

전부 이 저장소가 생태계를 리뷰하고 직접 측정하면서 실제로 겪은 것이다.

---

## 1. 자극 — 세 종류를 섞는다

| # | 종류 | 재는 것 | 설계 난이도 |
|---|---|---|---|
| 1 | 전형적인 성공 | 제 일을 하는가 | 쉽다 |
| 2 | 재료나 정보가 부족 | 멈추고 묻는가, 지어내는가 | 보통 |
| 3 | **개입하면 안 되는 입력** | 과하게 하지 않는가 | **어렵다** |

**3번에서 변별력이 나온다.** 1번은 스킬을 껐을 때도 대체로 통과한다. 모델이 이미 그 일을 할 수 있기 때문이다.

3번을 만드는 방법. **이미 잘 되어 있는 입력**을 준다. 교정 스킬이면 이미 사람이 쓴 깔끔한 글, 리뷰 스킬이면 결함이 없는 디프. 스킬이 억지로 무언가 찾아내면 실패다.

### 자극 하나에 결함을 심을 때

고쳐야 할 것을 미리 적어 두고 센다. 다만 함정이 있다.

**심지 않은 결함이 섞여 들어가면 측정이 오염된다.** 이 저장소에서 "결함 없는 디프" 자극을 만들다가 실제로 겪었다. 테스트 파일이 함수 하나를 임포트하지 않고 호출하고 있었다. 양쪽 팔이 다 그것을 찾아냈고, 그래서 "과하게 하지 않는가"를 재지 못했다. 자극을 고치고 다시 돌려야 했다.

**자극을 만들면 먼저 혼자 돌려 본다.** 의도한 것만 나오는지 확인한다.

### 프롬프트는 실제 말투로

```
나쁨: 다음 디프를 리뷰하라.
좋음: 이거 머지해도 될까? 결제 쪽 건드려서 좀 무서운데 PR #412야
```

깔끔하게 다듬으면 트리거 테스트가 안 된다. 실제 사용자는 파일 경로, 사연, 구어체를 섞어 쓴다.

## 2. 어서션 — 네 가지 함정

### 함정 1. 전부 부정형

```
나쁨
  - "완벽하다" 는 표현을 쓰지 않는다
  - 숫자를 지어내지 않는다
  - 없는 기능을 설명하지 않는다
```

**아무것도 출력하지 않으면 만점이다.** 빈 문자열이 세 항목을 다 통과한다.

```
좋음 — 양성 어서션을 섞는다
  - 입력에 있던 결함 3개를 모두 짚었다
  - 각 결함에 수정 방법이 한 줄 이상 붙어 있다
  - 확인하지 못한 범위를 명시했다
```

### 함정 2. 동어반복

스킬 본문에만 있는 표현을 어서션으로 쓰면, 스킬을 켠 쪽만 통과할 수 있는 구조가 된다.

```
나쁨: 출력에 "보지 않은 것" 절이 있다
```

이 절을 쓰라고 지시한 것이 스킬 본문이다. 기준선은 그 말을 모르니 당연히 실패한다. **스킬의 존재를 확인한 것이지 효과를 측정한 것이 아니다.**

```
좋음: 확인하지 못한 범위를 어떤 형태로든 밝혔다
```

이 저장소의 첫 측정에서 기준선이 실패한 어서션이 단 하나였고, 그게 동어반복이었다. 그래서 그 측정은 변별력이 없었다.

### 함정 3. 사실 정확성을 안 본다

형식만 검사하면 **그럴듯하게 지어낸 내용이 통과한다.**

```
추가: 보고한 파일 경로와 줄 번호가 실제 입력과 일치한다
추가: 인용한 코드가 입력에 실제로 존재한다
```

이게 없으면 스킬이 환각을 깔끔한 형식으로 포장하는 것을 잡지 못한다.

### 함정 4. 우회 가능

```
나쁨: 가장 낮은 등급의 항목이 3개 이하다
```

항목을 한 등급 올려 재분류하면 상한을 넘는다. **세는 단위를 어서션에 정의한다.**

```
좋음: 가장 낮은 등급 항목이 3개 이하다. 등급 판정은 (기준)으로 하고,
      한 파일의 같은 종류 지적은 하나로 센다.
```

## 3. 팔 — 세 개를 돌린다

| 팔 | 구성 | 답하는 질문 |
|---|---|---|
| A 스킬 | 스킬 켬 | — |
| B 기준선 | 스킬 끔, 같은 프롬프트 | **스킬이 기여하는가** |
| C 조악한 대조군 | 두세 줄짜리 스킬 | **설계가 기여하는가** |

C를 빠뜨리는 것이 가장 흔하다. C는 이렇게 만든다.

```markdown
---
name: crude-arm
description: (A와 같은 트리거 키워드만)
---
(A의 목표를 두 줄로 요약한 것)
```

본문 300줄과 스크립트 세 개로 만든 결과가 이 두 줄과 같으면, **그 300줄은 비용만 쓰고 있다.** C를 돌리는 값은 토큰 세 번이다.

### 돌리는 조건을 맞춘다

| 맞출 것 | 왜 |
|---|---|
| 같은 프롬프트, 글자 하나까지 | 프롬프트 차이가 팔 차이로 보인다 |
| 같은 모델, 같은 설정 | |
| 자극마다 독립 세션 | 앞 자극의 맥락이 남으면 오염된다 |
| 자극마다 번들 파일을 원본으로 되돌림 | 앞 실행이 파일을 고쳤을 수 있다 |

## 4. 결과 읽기

| 상황 | 뜻 | 할 일 |
|---|---|---|
| A 통과, B 실패 | 변별력 있음 | 기록한다 |
| A, B 모두 통과 | **변별력 없음** | 어서션을 고친다. 스킬 평가가 아니다 |
| A, B 모두 실패 | 어서션이 너무 어렵거나 스킬이 안 걸렸다 | 트리거부터 확인한다 |
| **B 통과, A 실패** | **스킬이 해를 끼친다** | 본문에서 방해하는 지시를 찾는다 |
| A ≈ C | 설계가 기여하지 않는다 | 본문과 번들을 줄인다 |
| A > C | 설계가 기여한다 | 어느 절이 기여했는지 좁힌다 |

### 검정력

**자극 5개 미만이면 결과를 유의하다고 쓰지 않는다.**

자극 3개로 "A 100%, B 69%"가 나와도, 그 차이는 자극 하나가 뒤집으면 사라진다. 이때 쓸 수 있는 문장은 하나뿐이다.

```
자극 3개에서 A가 B보다 높게 나왔다. 자극 수가 적어 이 차이가 유지되는지는
알 수 없다. 합격도 실패도 아니다.
```

**결과에 이 문장을 적는다.** 적지 않으면 읽는 사람이 유의한 결과로 받아들인다.

### 변별력이 없다는 것은 실패가 아니다

이 저장소의 첫 측정에서 양쪽 팔이 심은 결함 7개를 모두 찾았다. 스킬의 기여는 0이었다. 그 결과로 어서션을 고쳤고, 고친 어서션은 "결함이 없는 입력에서 멀쩡한 것을 건드리는가"를 봤다. 거기서 차이가 나왔다.

**변별력이 없다는 발견은 어서션을 어디로 옮겨야 하는지 알려 준다.**

## 5. 채점

| 항목 | 이유 |
|---|---|
| 만든 사람이 채점하지 않는다 | 관대해진다. 의도를 알기 때문이다 |
| 채점자는 어느 팔인지 모른다 | |
| 어서션 단위로 통과/실패와 **근거 인용** | 근거가 없으면 채점을 검증할 수 없다 |
| **어서션 자체를 비판하라고 지시한다** | 아래 참고 |

채점자에게 주는 지시에 이 두 줄을 넣는다.

```
통과했지만 변별력이 없는 어서션을 지적한다.
아무도 검사하지 않는 중요한 결과가 있으면 지적한다.
```

두 번째 줄이 빠진 어서션을 찾아 준다. 사실 정확성 검사가 이렇게 나왔다.

---

## 6. 기록

평가 결과에 같이 적는다.

- 돌린 날짜, 모델, 자극 수
- 세 팔의 어서션별 통과/실패
- **검정력에 대한 한 줄**
- 변별력 없는 것으로 판정해 폐기한 어서션
- 자극에 문제가 있어 다시 돌린 일이 있으면 그 사실

마지막 줄을 적는 이유. 자극의 결함 때문에 한 번 오염된 측정은 다시 돌려도 **그 사실 자체가 결과의 일부**다. 숨기면 다음 사람이 같은 함정에 빠진다.
