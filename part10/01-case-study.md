# 10.1 케이스: diff-review

코드 리뷰 스킬 하나를 처음부터 만든 기록이다. 3부의 작성법을 실제로 적용하면 무엇이 일어나는지 본다.

**예시가 아니라 실제 기록이다.** 결과가 좋았던 것만 적지 않는다. 설계 결함, 평가의 구멍, 측정이 설계를 뒤집은 지점을 같이 적는다.

## 왜 코드 리뷰인가

이 도메인을 고른 이유가 셋이다.

**측정이 가능하다.** 알려진 결함을 심어 두고 몇 개를 찾는지 세면 된다. 글쓰기나 디자인처럼 주관적이지 않다([3.7](../part3/07-evals.md)).

**스크립트가 필요하다.** 리뷰에는 판단이 필요 없는 부분이 있다 — 위험 패턴 탐지, 변경 규모 계산, 테스트 누락 확인. 그걸 코드로 내리면 매번 같게 실행된다([3.5](../part3/05-scripts.md)).

**과잉 적용이 실제 문제다.** 리뷰의 실패 방식은 결함을 놓치는 것과 **바뀌지 않은 코드를 지적하는 것** 둘이고, 두 번째가 더 나쁘다.

## 1단계 — 무엇을 스크립트로 내릴 것인가

[3.5](../part3/05-scripts.md)의 판단 기준을 적용했다.

| 작업 | 입출력이 정해지나 | 결정 |
|---|---|---|
| 위험 패턴 탐지 | ○ 코드 → 위치 목록 | **스크립트** |
| 변경 규모 계산 | ○ diff → 숫자 | **스크립트** |
| 테스트 누락 확인 | ○ 함수명 → 포함 여부 | **스크립트** |
| "이게 실제로 깨지는가" | ✕ 의미를 알아야 한다 | 지시문 |
| "이번 변경 때문인가" | ✕ 맥락을 봐야 한다 | 지시문 |

**분기 판단은 본문, 실행은 스크립트.** 공식 `pdf` 스킬의 구조를 따랐다([6.1](../part6/01-anthropic-skills.md)).

### AST를 쓴 이유

정규식으로 `except:`를 찾으면 주석과 문자열에 걸리고 들여쓰기 맥락을 모른다. AST는 구조를 보므로 오탐이 적다.

```python
def visit_FunctionDef(self, node):
    for d in node.args.defaults + [k for k in node.args.kw_defaults if k]:
        if isinstance(d, (ast.List, ast.Dict, ast.Set)):
            self.add("mutable_default", d, node.name)
```

8개 규칙을 S1/S2/S3로 등급을 붙여 탐지한다 — `bare_except`, `mutable_default`, `eq_none`, `shell_true`, `eval_exec`, `assert_for_check`, `except_pass`, `open_no_close`.

### 스크립트에 한계를 적었다

**스크립트가 자기 한계를 출력에 넣는다.**

```python
"note": "패턴에 걸렸다고 결함은 아니다. SKILL.md 의 세 질문으로 판정한다."
```

`check_test_delta.py`는 더 강하게 적었다.

```python
"note": "이름 기반 근사다. 간접 호출로 덮인 함수를 놓쳤다고 보고할 수 있다.
         '테스트 없음'이 아니라 '테스트에서 이름이 안 보임'으로 읽는다."
```

**근사를 근사라고 적지 않으면 에이전트가 그걸 사실로 보고한다.**

### 파싱 실패를 숨기지 않게 했다

```python
except SyntaxError as e:
    failed.append({"file": p, "reason": f"구문 오류 {e.lineno}행"})
```

실패를 `parse_failed`로 따로 내고, 본문에 **"보지 않은 것"** 절을 두어 보고하게 했다. 이게 나중에 3번 테스트 케이스가 된다.

## 2단계 — 본문 설계

### 과잉 적용 방지를 중심에 뒀다

```
리뷰의 실패 방식은 두 가지다. 결함을 놓치는 것, 그리고 바뀌지 않은
코드를 지적하는 것이다. 두 번째가 더 나쁘다. 리뷰가 길어지고 정작
이번 변경의 문제가 묻힌다.
```

세 질문으로 판정하게 했다.

1. 이게 실제로 깨지는가 — **재현 경로를 한 줄로 쓸 수 있어야 한다**
2. 이번 변경 때문인가 — 바뀌지 않은 줄의 문제는 보고하지 않는다
3. 고칠 방법을 적을 수 있는가 — "개선이 필요합니다"로 끝나면 보고하지 않는다

그리고 애매할 때의 처리를 명시했다.

```
판단이 애매하면 확인 질문으로 돌린다. 결함으로 단정하지 않는다.
애매한 것을 질문으로 남기는 비용이 멀쩡한 코드를 결함으로 보고하는
비용보다 작다.
```

**이 한 줄이 나중에 측정에서 결정적인 차이를 만든다.**

### S3를 세 개로 제한했다

| 등급 | 기준 | 보고 |
|---|---|---|
| S1 | 데이터 손실, 보안, 크래시 | 반드시 |
| S2 | 특정 입력에서 틀린 결과 | 반드시 |
| S3 | 유지보수 비용 | **세 개까지만** |

제한이 없으면 S3가 목록을 채우고 S1이 묻힌다.

### 참조 파일에 "언제 봐주는가"를 붙였다

패턴 목록만 주면 기계적으로 적용한다. 여덟 항목 전부에 예외 조건을 적었다.

```markdown
## 2. bare except (S2)
**언제 봐주는가** — 최상위 데몬 루프에서 의도적으로 모든 것을 잡고
**로그를 남기며** 재시작하는 경우. 로그가 없으면 봐주지 않는다.
```

그리고 **기계가 못 잡는 것**을 따로 적었다.

> 변경분 리뷰에서 가장 흔한 S1은 "있던 검사를 지운 것"이다. diff의 `-` 줄에 `if`, `assert`, `raise`, `return`이 있으면 왜 지웠는지 확인한다.

## 3단계 — 결함을 심은 픽스처

측정이 가능하려면 정답이 필요하다. 장바구니 저장소를 만들고 **결함 7개를 심었다.**

| 번호 | 등급 | 심은 결함 |
|---|---|---|
| D1 | S2 | `apply_discount`에서 빈 리스트 가드 삭제 |
| D2 | S2 | `apply_discount`에서 rate 범위 검증 삭제 |
| D3 | S2 | `bulk_add`에 가변 기본 인자 `bucket=[]` |
| D4 | **S1** | `verify`에서 `hmac.compare_digest` → `==` (타이밍 공격) |
| D5 | **S1** | `parse_rules`에서 `json.loads` → `eval` |
| D6 | **S1** | `export_report`에 `shell=True` (명령 주입) |
| D7 | S2 | `load_config`에 `bare except: pass` + 파일 미닫힘 |

**D1과 D2가 설계의 핵심이다.** "있던 검사를 지운 것"은 AST 패턴 매칭으로 못 잡는다. diff의 `-` 줄을 읽고 의미를 알아야 한다.

### 세 케이스

[3.7](../part3/07-evals.md)의 구성을 따랐다.

| # | 케이스 | 재는 것 |
|---|---|---|
| 0 | 결함 7개를 심은 변경 | 찾아내는가 |
| 1 | **결함 없는 변경** | 과하게 지적하지 않는가 |
| 2 | **구문 오류가 포함된 변경** | 파싱 실패를 숨기지 않는가 |

### 스크립트가 무엇을 잡고 무엇을 못 잡는지 먼저 확인했다

픽스처에 돌려 봤다.

```
탐지 6건 {S1: 2, S2: 3, S3: 1}
  [S1] src/coupon.py:12 eval_exec        ← D5
  [S1] src/coupon.py:16 shell_true       ← D6
  [S2] src/cart.py:16  mutable_default   ← D3
  [S2] src/coupon.py:23 bare_except      ← D7
  [S2] src/coupon.py:23 except_pass      ← D7
  [S3] src/coupon.py:21 open_no_close    ← D7
```

**D1, D2, D4를 못 잡는다.** 삭제된 가드 둘과 타이밍 공격이다. 설계대로다 — 기계는 어디를 볼지 알려주고 판정은 사람(에이전트)이 한다.

## 4단계 — 평가 중에 생긴 사고

**"결함 없는" 픽스처에 제가 실수로 넣은 진짜 결함이 있었다.**

테스트 파일에 `truncate` 함수 테스트를 추가하면서 임포트 줄을 고치지 않았다.

```python
from src.text import slugify    # truncate 가 빠졌다

def test_truncate():
    assert truncate("abcdef", 4) == "abc…"    # NameError
```

스킬을 붙인 쪽이 **pytest를 실제로 돌려서** 이걸 찾았다. 기준선도 찾았다.

### 어떻게 처리했나

케이스 1의 목적은 "결함이 없을 때 억지로 지적하지 않는가"를 재는 것이다. **픽스처에 진짜 결함이 있으면 그 측정이 성립하지 않는다.**

세 가지를 했다.

1. 픽스처를 고쳤다 (임포트 추가, 경계 테스트 보강)
2. 해당 케이스만 양쪽 다 **다시 돌렸다**
3. 이전 결과를 `eval-1-clean-diff-FLAWED-FIXTURE/`로 **보존했다**

**지우지 않고 남긴 이유가 있다.** `dotnet/skills`의 평가 품질 게이트가 막는 결함 목록 첫 줄이 이것이다([6.5](../part6/05-microsoft.md)).

> 참조된 픽스처가 디스크에 없다. 설정 단계에서 실패하는데 **스킬 실패로 읽힌다.**

**픽스처 결함이 스킬 평가를 오염시키는 전형이다.** 내 경우는 반대 방향이었다 — 픽스처 결함을 양쪽이 찾아내서 "과잉 지적"으로 읽힐 뻔했다.

`__pycache__`가 스테이징에 섞여 들어간 것도 같이 발견해서 `.gitignore`를 추가했다. **평가 환경의 위생이 평가 결과를 바꾼다.**

## 5단계 — 측정 결과

| 케이스 | 스킬 사용 | 기준선 |
|---|---|---|
| 0. 결함 7개 | **9/9** | 8/9 |
| 1. 결함 없음 | **4/4** | **1/4** |
| 2. 구문 오류 | **3/3** | 2/3 |
| **합계** | **16/16 (100%)** | **11/16 (69%)** |

(측정일: 2026-10-04. 구성당 1회. 자극 3개 — **검정력 부족**)

### 예상이 빗나간 지점

**케이스 0에서 기준선도 심은 결함 7개를 전부 찾았다.**

| | 스킬 사용 | 기준선 |
|---|---|---|
| 심은 결함 탐지 | **7/7** | **7/7** |
| 어서션 | 9/9 | 8/9 |

기준선이 놓친 어서션 하나는 "번들 스크립트를 실행했다"였다. **스킬이 없으면 스크립트도 없으므로 자동으로 실패한다.** 리뷰 품질에 대해 아무것도 재지 않는 항목이다.

**즉 케이스 0은 변별력이 없다.** 이 스킬을 만든 가장 큰 이유였던 "결함을 더 잘 찾는다"가 측정으로 뒷받침되지 않았다.

채점자가 더 날카롭게 지적했다.

> 기준선이 오히려 **더 넓었다.** D1을 결함으로 인라인 처리했고, `coupon.py` 변경 전체가 실수로 스테이징된 디버그 코드로 보인다고 추론해 `git restore --staged`를 제안했다.

### 그러면 스킬은 무엇을 했나

**케이스 1에서 4배 차이가 났다(4/4 대 1/4).**

| | 스킬 사용 | 기준선 |
|---|---|---|
| 요약 | `S1 0건, S2 0건, S3 1건. 머지해도 된다.` | 6개 절, 12개 이상 항목 |
| 애매한 것 | **확인 질문 3건으로** | **머지 차단 "버그"로** |
| 분량 | 3,695 B | 5,970 B |

같은 사실을 보고 **기준선은 가정적 경계 조건을 머지 차단 결함으로 올렸고, 스킬 쪽은 확인 질문으로 내렸다.** "이 저장소에 호출자가 없다"를 근거로 들었다.

본문에 적은 한 줄이 작동한 것이다.

```
판단이 애매하면 확인 질문으로 돌린다. 결함으로 단정하지 않는다.
```

**그리고 채점자가 기준선의 사실 오류를 찾았다.**

> 기준선의 재현 표가 **사실과 다르다** — `truncate("abcdef", 0)`은 `"ab…"`(3자)가 아니라 `"abcde…"`(6자)를 반환한다. 직접 실행해 확인했다.

재현 경로를 쓰라고 요구한 지시가 있었는데도 기준선은 **재현값을 지어냈다.** 스킬 쪽이 보고한 값은 전부 맞았다.

### 케이스 2에서 갈린 축

양쪽 다 구문 오류를 Blocker로 잡았다. 기준선의 분석이 오히려 더 깊었다 — 괄호만 닫아도 `return`이 문이라 안 된다는 점까지 봤다.

**기준선이 놓친 것은 범위 보고 하나다.** 파싱 실패를 "그래서 `b.py`의 다른 위험 패턴은 검사되지 않았다"로 바꾸지 않았다.

본문의 **"보지 않은 것"** 절이 이 차이를 만들었다.

## 6단계 — 측정이 뒤집은 설계 이해

**만들 때 생각한 기여와 측정된 기여가 다르다.**

| 설계 의도 | 측정된 기여 |
|---|---|
| 스크립트로 결함을 더 잘 찾는다 | **차이 없음** (7/7 대 7/7) |
| 심각도 체계를 준다 | 일관성은 있으나 어서션이 안 잼 |
| **애매하면 질문으로 돌린다** | **케이스 1에서 4배 차이** |
| **보지 않은 것을 적는다** | **케이스 2에서 유일한 차이** |

**측정하지 않았으면 몰랐다.** 그리고 이 발견이 다음 이터레이션의 방향을 바꾼다 — AST 규칙을 늘리는 것보다 과잉 지적 억제를 강화하는 쪽이 효과가 크다.

같은 구조의 발견이 [10.2](02-validation.md)에서 더 자세히 다뤄진다.

## 7단계 — 남은 결함

### 결함 1 — 케이스 0에 변별력이 없다

심은 결함이 **너무 전형적이었다.** `eval`, `shell=True`, 가변 기본 인자는 교과서 패턴이라 유능한 기준선이 다 찾는다.

고치는 방향은 **덜 전형적인 결함**을 심는 것이다. 경쟁 조건, 리소스 누수, 잘못된 비즈니스 로직처럼 맥락을 알아야 보이는 것들이다. 참조 파일의 "기계 검사가 못 잡는 것" 표에 이미 목록이 있다.

**해결하지 않았다.** 다음 이터레이션 과제로 남긴다.

### 결함 2 — 스크립트 실행을 자기 보고로만 채점했다

채점자가 지적했다.

> 런 디렉터리에 `outputs/response.md` 하나만 있고 트랜스크립트와 툴 호출 로그가 없다. 따라서 "번들 스크립트를 실제로 실행했다"는 응답 본문의 **자기 보고로만** 채점했다.

채점자가 보고된 값을 픽스처 코드와 대조해서 전부 맞다는 것을 확인했지만, **실행 여부 자체는 증명되지 않았다.**

고치려면 실행 로그를 산출물로 저장해야 한다.

### 결함 3 — 어서션이 사실 정확성을 재지 않는다

기준선이 재현값을 지어냈는데 **그걸 잡는 어서션이 없다.** 채점자가 수동 대조로 발견했다.

리뷰 스킬에서 이건 치명적이다. **지어낸 재현 경로는 없는 것보다 나쁘다** — 개발자가 그걸 믿고 시간을 쓴다.

추가할 어서션이다.

```
"보고한 재현값이 실제 코드 동작과 일치한다"
```

### 결함 4 — "3개 이하" 어서션이 우회된다

채점자가 짚었다.

> `항목 3개 이하`는 결함을 "확인 질문"으로 재분류하면 우회된다. "항목"이 정의되지 않았다 — 스킬 쪽은 결함 1건이지만 전체 항목은 4건이다.

**내가 설계한 억제 장치를 내가 만든 어서션이 제대로 못 잰다.**
