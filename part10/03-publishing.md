# 10.3 공개할 때

스킬을 만들고 공개하는 것은 다른 일이다. 이 장은 공개의 비용과 책임을 다룬다.

6, 7, 8부에서 리뷰한 저장소들이 잘한 것과 빠뜨린 것을 재료로 쓴다.

## 공개하기 전에 — 만들지 않을 이유

가장 먼저 확인할 것이다.

[10.1](01-case-study.md)의 케이스 스터디가 이 점에서 실패했다. 한국어 AI 글 교정 스킬을 만들었는데, 같은 문제를 푸는 저장소가 이미 있었다 — `epoko77-ai/im-not-ai`(5,835)다([8.5](../part8/05-writing.md)).

**찾아보지 않았다.** 마크다운 파일 하나를 쓰는 것이 기존 저장소 세 개를 읽고 비교하는 것보다 빨랐다.

| 확인 | 방법 |
|---|---|
| 이미 있는가 | `awesome-*` 목록 두세 개를 본다 |
| 70% 이상 맞는가 | 맞으면 포크해서 고친다 |
| 조건이 다른가 | 언어, 플랫폼, 규모가 다르면 재구현이 맞다 |
| 설계가 다른가 | 다른 분할 축이면 가치가 있다 |
| 같은 조건, 같은 설계인가 | **공개하지 않는다. 기존 저장소에 기여한다** |

마지막 줄이 가장 어렵다. 남의 저장소에 기여하는 비용이 자기 저장소를 만드는 비용보다 크다. **그게 생태계에 중복이 쌓이는 이유다**([9.5](../part9/05-saturation.md)).

## 저장소 구성 — 넣을 것

리뷰에서 확인한 좋은 사례들을 모았다.

### 필수

| 파일 | 내용 |
|---|---|
| `SKILL.md` | 스킬 본체 |
| `LICENSE` | **루트에** |
| `README.md` | 무엇을 하는가, 설치, 예시 입출력, **한계** |

**`LICENSE`를 루트에 두는 것이 중요하다.** 상위 60개 중 4개가 루트 라이선스가 없고, 그중 둘이 공식 저장소다([9.4](../part9/04-licensing.md)).

### 라이선스를 두 곳에 둔다

스킬은 **디렉터리 단위로 복사된다.** 루트 `LICENSE`만 두면 복사할 때 떨어진다.

| 위치 | 효과 |
|---|---|
| 루트 `LICENSE` | 깃허브가 식별하고 자동 검사가 통과한다 |
| 스킬별 `LICENSE.txt` | **복사 단위에 따라간다** |
| 프런트매터 `license` | 같이 따라간다 |

`anthropics/skills`가 후자 둘만 한다 — 루트에 없어서 깃허브가 식별하지 못한다. `obra/superpowers`는 루트에만 둔다.

**둘 다 두는 쪽이 맞다.**

### 평가를 같이 올린다

| 디렉터리 | 내용 |
|---|---|
| `evals/cases/` | 스킬당 테스트 케이스 |
| `evals/fixtures/` | 입력 자료 |
| `evals/README.md` | 무엇을 어떻게 재는지 |

**생태계 다수가 평가를 포함하지 않는다**([5.4](../part5/04-patterns.md)). 포함하면 두 가지를 얻는다.

쓰는 사람이 **이 스킬이 무엇을 보장하는지** 안다. 그리고 고칠 때 회귀를 확인할 수 있다.

`addyosmani/agent-skills`의 `evals/README.md`가 가장 좋은 참고 자료다([7.2](../part7/02-addyosmani.md)). 선행 연구를 인용하고, 3단 비용 계층을 적고, 자기 기여를 한 문장으로 특정했다.

### 제거 경로를 제공한다

| 파일 | 왜 |
|---|---|
| `uninstall.sh` | 스킬이 여러 디렉터리에 복사되면 수동 제거가 번거롭다 |

**남은 파일이 트리거 충돌을 일으킨다.** 설치 스크립트를 주는 저장소는 많고 제거 스크립트를 주는 경우는 드물다.

`epoko77-ai/im-not-ai`가 `install.sh`, `uninstall.sh`, `update.sh`를 다 둔다([8.5](../part8/05-writing.md)).

## README에 적을 것

### 한계를 적는다

가장 자주 빠뜨리는 항목이다. 무엇을 못 하는지, 어떤 경우에 쓰면 안 되는지를 적으면 **쓰는 사람이 잘못된 기대를 안 한다.**

케이스 스터디의 스킬은 본문 앞에 범위를 못 박았다.

```
바뀐 줄만 본다. 코드베이스 전체 감사가 아니다.
```

그리고 번들 스크립트가 **자기 한계를 출력에 넣는다.**

```
"note": "이름 기반 근사다. 간접 호출로 덮인 함수를 놓쳤다고 보고할 수 있다.
         '테스트 없음'이 아니라 '테스트에서 이름이 안 보임'으로 읽는다."
```

**근사를 근사라고 적지 않으면 에이전트가 그걸 사실로 보고한다.**

### 도구별 기능 차이를 적는다

다중 하네스를 지원하면 **도구마다 지원 범위가 다르다.** 그걸 안 적으면 사용자가 기능이 고장 났다고 판단한다.

`epoko77-ai/im-not-ai`가 이렇게 적는다.

> Copilot은 **단일 호출 경로만** 제공하며 Claude Code 전용 진단, finalize 다중 호출 경로는 실행하지 않습니다.

**"여러 도구에서 됩니다"로 끝내지 않는다.**

### 외부 의존성을 적는다

프런트매터 `compatibility`가 이 자리다([1.2](../part1/02-anatomy.md)).

```yaml
compatibility: Requires the `ocr` CLI installed (via npm install -g
  @alibaba-group/open-code-review or GitHub release binary). Requires a
  configured supported LLM provider before first run.
```

`alibaba/open-code-review`의 예다([8.2](../part8/02-code-review.md)). 수집 데이터에서 `compatibility`를 쓴 스킬을 거의 보지 못했다.

**외부 의존성이 있는데 안 적으면 사용자는 스킬이 고장 났다고 판단한다.**

### 마크다운 전용이면 적는다

스크립트가 없으면 공급망 위험이 낮다([9.3](../part9/03-supply-chain.md)). 그 사실을 적으면 검증 비용이 줄어든다.

`wanshuiyin/Auto-claude-code-research-in-sleep`(16,931)이 "경량 마크다운 전용"을 설명에 적는다.

### 출처를 밝힌다

판정 기준이 주관적인 영역에서 외부 근거를 대면 "저자의 취향"이 아니게 된다.

| 저장소 | 근거 |
|---|---|
| `blader/humanizer` | 위키백과 "Signs of AI writing" |
| `tanviet12/vbsec` | 언어별 기대 출력 픽스처로 회귀 테스트 |

## 버전과 배포

### 버전을 관리한다

`epoko77-ai/im-not-ai`가 v2.3.2다. 플러그인 마켓플레이스로 설치, 업데이트, 제거가 된다.

```bash
copilot plugin install humanize-korean@im-not-ai
copilot plugin update humanize-korean@im-not-ai
copilot plugin uninstall humanize-korean@im-not-ai
```

**스킬 생태계에 레지스트리가 없다**([9.5](../part9/05-saturation.md)). 버전 관리를 하면 사용자가 무엇이 설치됐는지 추적할 수 있다.

### 다중 하네스를 지원한다

상위권 저장소의 공통 전략이다([7.6](../part7/06-why-individuals-win.md)).

| 저장소 | 지원 |
|---|---|
| `DietrichGebert/ponytail` | 20개 |
| `obra/superpowers` | 16개 |
| `nexu-io/open-design` | 20개 이상 |
| `epoko77-ai/im-not-ai` | 4개 |

**규격이 공통이므로 비용이 크지 않다.** 디렉터리를 복사하거나 심링크를 걸면 된다. 그리고 지원 범위가 잠재 사용자 수를 결정한다.

### 규격을 지킨다

```bash
skills-ref validate ./my-skill
```

`name`이 디렉터리 이름과 다른 실수가 가장 흔하다([1.2](../part1/02-anatomy.md)).

**지키지 않아도 쓰이기는 한다.** `Graphify-Labs/graphify`(123,488)가 `skill-<도구>.md`를 쓰고 12만 스타를 받았다([8.9](../part8/09-code-understanding.md)).

다만 대가가 있다. 검증 도구를 통과하지 않고, 큐레이션 저장소의 자동 수집에 안 걸리고, 이 책의 선별에서도 빠졌다.

## 공개 후의 비용

### 유지 비용이 생긴다

| 유형 | 수명 | 갱신 부담 |
|---|---|---|
| 방법론형 | 길다 | 낮다 |
| 실행형 | 중간 | 의존성 갱신 |
| **지식형** | **짧다** | **계속** |

**지식형을 공개할 때 가장 신중해야 한다.** 낡은 지식형 스킬은 틀린 답을 자신 있게 낸다 — **없는 것보다 나쁘다**([4.2](../part4/02-three-types.md)).

수집 데이터에 그 상태의 저장소가 있다. `Orchestra-Research/AI-Research-SKILLs`(13,219)가 지식형 98개를 담고 3.5개월 멈췄다([8.6](../part8/06-research.md)).

### 유지할 생각이 없으면 적는다

정직한 처리다. 쓰는 사람은 유지 여부를 저장소 메타데이터로만 알 수 있고, 대개 확인하지 않는다 — **스타수는 맨 위에 크게 보이고 마지막 푸시는 커밋 목록을 봐야 안다**([9.1](../part9/01-star-traps.md)).

### 지식을 박아 두지 말고 조회한다

지식형의 수명 문제를 피하는 방법이 있다.

`NVIDIA/SkillSpector`가 OSV.dev에 실시간으로 CVE를 조회한다([6.8](../part6/08-others.md)). **취약점 목록을 저장소에 박아 두면 낡지만, 조회하면 안 낡는다.**

API 문서 URL을 두고 필요할 때 가져오는 방식도 같다. 유지 부담이 크게 줄어든다.

### 수익화를 생각한다면

`obra/superpowers`가 README에 `Commercial Services` 절을 둔다([7.1](../part7/01-superpowers.md)). MIT로 공개하고 그 위에 서비스를 판다.

**스타 29만 저장소를 무보수로 유지하는 것은 지속되지 않는다.** 오픈소스 스킬 저장소에서 수익화를 명시한 드문 사례다.

## 공개하는 쪽의 책임

[9.3](../part9/03-supply-chain.md)의 숫자를 다시 적는다.

> 분석한 31,132개 스킬 중 **26.1%가 취약점을 포함**하고 **5.2%가 악의적 의도로 보인다.**

공개하는 사람이 할 수 있는 것들이다.

| 항목 | 효과 |
|---|---|
| 스크립트의 네트워크 호출을 문서화한다 | 검증 비용을 줄인다 |
| 비밀값, 환경변수 접근을 밝힌다 | 가장 민감한 항목 |
| `hooks/`가 있으면 강조한다 | **판단 없이 항상 실행된다** |
| MCP 서버를 같이 배포하면 권한을 적는다 | 하나 설치하면 셋이 들어온다 |
| 번들 자산의 출처를 적는다 | `THIRD_PARTY_NOTICES.md` |

**세 번째가 가장 중요하다.** 스킬은 트리거돼야 작동하는데 훅은 항상 돈다. 플러그인에 훅이 들어 있으면 설치자가 그 사실을 알아야 한다.

## 공개 체크리스트

| | 항목 |
|---|---|
| □ | 같은 문제를 푸는 저장소를 찾아봤다 |
| □ | 루트에 `LICENSE`가 있다 |
| □ | 스킬 디렉터리에 `LICENSE.txt`가 있다 |
| □ | 프런트매터 `license` 필드가 있다 |
| □ | 외부 의존성이 `compatibility`에 있다 |
| □ | `skills-ref validate`를 통과한다 |
| □ | `README`에 **한계**가 적혀 있다 |
| □ | `README`에 도구별 기능 차이가 적혀 있다 |
| □ | `evals/`가 포함돼 있다 |
| □ | 테스트 케이스에 **개입하면 안 되는 경우**가 있다 |
| □ | 어서션에 양성 항목이 있다 |
| □ | 기준선 비교를 돌렸다 |
| □ | 자극 개수를 기록했다 (5개 미만이면 검정력 부족) |
| □ | 측정 날짜를 기록했다 |
| □ | 제거 경로가 있다 |
| □ | 스크립트의 네트워크, 비밀값 접근을 밝혔다 |
| □ | `hooks/`가 있으면 강조했다 |
| □ | 번들 자산의 출처를 적었다 |
| □ | 유지할 생각이 없으면 적었다 |

**케이스 스터디의 `diff-review`도 이 중 여럿을 못 지켰다.**

| 못 지킨 것 | 상태 |
|---|---|
| 트리거 평가 | 안 했다 — 불리는지 모른다 |
| 조악한 대조군 | 없다 — **설계가 기여했는지 모른다** |
| 보안 스캔 | 안 했다 |
| 어서션의 양성 항목 | 케이스 1이 전부 부정형이다 |
| 어서션의 사실 정확성 검사 | 없다 — 기준선이 재현값을 지어냈는데 못 잡았다 |

**그래서 공개하지 않았다.** 체크리스트를 통과하지 못한 스킬은 개인용으로 쓰는 것이 맞다.

그리고 측정이 알려 준 것이 하나 더 있다. **126줄 본문과 스크립트 3개가 기여했는지가 아직 미확인이다**([10.2](02-validation.md)). 케이스 1의 차이가 거의 전부 "애매하면 질문으로 돌려라"는 한 줄에서 왔으므로, **두 줄짜리 대조군으로 같은 결과가 나오면 나머지는 과잉이다.**

공개는 그 확인 뒤에 할 일이다.

## 생태계에 기여하는 다른 방법

스킬을 공개하는 것만이 기여가 아니다. 리뷰에서 확인한 **비어 있는 자리**들이다([9.5](../part9/05-saturation.md)).

| 빈 자리 | 난이도 |
|---|---|
| **라이선스 스캐너** | 낮다 — 프런트매터와 `LICENSE` 파일을 읽으면 된다 |
| 품질 벤치마크 | 높다 — 유형별로 다르고 비용이 크다 |
| 표준 디스커버리 | 높다 — 합의가 필요하다 |
| 메모리 오염 대응 | 중간 |
| 인용 검증 (연구 스킬) | 낮다 — DOI 조회 |

**첫 줄과 마지막 줄이 만들기 쉽고 아무도 만들지 않았다.**

라이선스 스캐너는 npm의 `license-checker`에 해당한다. 번들 전체의 호환성을 확인하는 도구이고, 이 생태계에 MIT, Apache, CC-BY-SA, AGPL, Proprietary, NOASSERTION, 없음이 섞여 있다([9.4](../part9/04-licensing.md)).

**중복된 스킬 하나를 더 만드는 것보다 기여가 크다.**
