# 10.2 평가로 검증하기

[10.1](01-case-study.md)의 측정을 재료로, 평가가 실제로 무엇을 알려 주는지 본다.

**평가의 가치는 점수가 아니라 점수에서 읽어내는 것이다.** 이 케이스에서는 점수가 설계 이해를 뒤집었다.

## 측정 데이터 전문

숨기지 않고 다 적는다.

| 케이스 | 구성 | 통과 | 심은 결함 탐지 | 분량 |
|---|---|---|---|---|
| 0. 결함 7개 | 스킬 | 9/9 | **7/7** | 6,004 B |
| 0. 결함 7개 | 기준선 | 8/9 | **7/7** | 8,256 B |
| 1. 결함 없음 | 스킬 | **4/4** | — | 3,695 B |
| 1. 결함 없음 | 기준선 | **1/4** | — | 5,970 B |
| 2. 구문 오류 | 스킬 | 3/3 | — | 2,497 B |
| 2. 구문 오류 | 기준선 | 2/3 | — | 5,747 B |

| 합계 | 스킬 | 기준선 |
|---|---|---|
| 통과율 | **16/16 (100%)** | **11/16 (69%)** |

(측정일: 2026-10-04. 구성당 1회. 자극 3개 — **검정력 부족**)

---

## 읽어내기 1 — 합계가 거짓말을 한다

100% 대 69%만 보면 스킬이 완승이다. **케이스별로 보면 전혀 다른 그림이다.**

| 케이스 | 차이 | 뜻 |
|---|---|---|
| 0 | +1 (9/9 대 8/9) | **변별력 없음** |
| 1 | **+3 (4/4 대 1/4)** | **변별력 큼** |
| 2 | +1 (3/3 대 2/3) | 변별력 작음 |

**스킬의 가치를 설명하는 것은 케이스 1 하나다.**

### 케이스 0의 +1이 가짜인 이유

기준선이 놓친 어서션은 "번들 스크립트를 최소 1개 이상 실제로 실행했다"였다.

**스킬이 없으면 스크립트도 없다.** 이 어서션은 구조적으로 기준선이 통과할 수 없고, 리뷰 품질에 대해 아무것도 재지 않는다.

채점자가 "동어반복적(tautological)"이라고 표현했다. [3.7](../part3/07-evals.md)의 변별력 표에 없던 네 번째 유형이다.

| 상황 | 뜻 |
|---|---|
| 양쪽 다 통과 | 변별력 없음 |
| 양쪽 다 실패 | 어서션이 틀렸다 |
| 스킬만 통과 | 변별력 있음 |
| 기준선만 통과 | 스킬이 해를 끼친다 |
| **스킬만 통과할 수 있는 구조** | **동어반복. 측정이 아니다** |

"스킬의 출력 형식을 따랐는가" 같은 어서션이 전부 여기 해당한다. **스킬이 작동했는지의 지표이지 기여의 측정이 아니다.**

---

## 읽어내기 2 — 설계 의도와 측정된 기여가 다르다

이 케이스의 핵심 발견이다.

| 설계할 때 생각한 기여 | 측정된 기여 |
|---|---|
| **스크립트로 결함을 더 잘 찾는다** | **차이 없음 (7/7 대 7/7)** |
| 심각도 체계 | 일관성은 있으나 어서션이 못 잼 |
| 애매하면 질문으로 돌린다 | **케이스 1에서 3점 차이** |
| 보지 않은 것을 적는다 | 케이스 2에서 유일한 차이 |

**이 스킬을 만든 가장 큰 이유가 측정으로 뒷받침되지 않았다.**

### 왜 스크립트가 차이를 못 만들었나

심은 결함이 **전형적이었기 때문이다.**

| 결함 | 성격 |
|---|---|
| D5 `eval` | 교과서 보안 항목 |
| D6 `shell=True` | 교과서 보안 항목 |
| D3 가변 기본 인자 | 파이썬 입문서 단골 |
| D4 `compare_digest` → `==` | 알려진 타이밍 공격 |
| D1, D2 삭제된 가드 | diff의 `-` 줄을 읽으면 보인다 |

**유능한 기준선은 이걸 다 찾는다.** 스크립트가 어디를 볼지 알려 주는 가치는, 볼 곳이 분명할 때 작아진다.

스크립트가 기여하는 영역은 따로 있다.

| 상황 | 스크립트의 기여 |
|---|---|
| 변경이 작고 결함이 전형적 | **작다** |
| 변경이 수천 줄 | 크다 — 우선순위를 정해 준다 |
| 매번 같은 검사를 반복 | 크다 — 재현된다 |
| 놓치면 안 되는 체크리스트 | 크다 — 빠지지 않는다 |

**세 번째가 측정되지 않았다.** 구성당 1회만 돌렸으므로 재현성을 재지 않았다. 기준선이 같은 7개를 **매번** 찾는지는 모른다.

## 읽어내기 3 — 억제가 탐지보다 큰 차이를 만든다

케이스 1에서 같은 코드를 보고 양쪽이 정반대로 판정했다.

| 사실 | 스킬 | 기준선 |
|---|---|---|
| `truncate(s, limit<=0)`의 동작 | 확인 질문 | **머지 차단 버그** |
| `slugify("_hello_")`의 앞뒤 하이픈 | 확인 질문 | **머지 차단 버그** |
| 새 동작의 테스트 누락 | S3 1건 | 버그 목록에 포함 |

**같은 사실을 보고 등급이 갈렸다.** 기준선은 6개 절, 12개 이상 항목을 냈다.

본문의 한 줄이 이 차이를 만들었다.

```
판단이 애매하면 확인 질문으로 돌린다. 결함으로 단정하지 않는다.
애매한 것을 질문으로 남기는 비용이 멀쩡한 코드를 결함으로 보고하는
비용보다 작다.
```

[3.3](../part3/03-body.md)에서 "두 방향 실패의 비용을 비교해 적는다"고 한 것의 실제 효과다. **비용 비교가 없으면 애매한 상황에서 매번 다르게 간다.**

### 그리고 기준선이 재현값을 지어냈다

채점자가 코드를 직접 실행해 확인했다.

> 기준선의 재현 표가 **사실과 다르다** — `truncate("abcdef", 0)`은 `"ab…"`(3자)가 아니라 `"abcde…"`(6자)를 반환한다.

**지시가 있었는데도 지어냈다.** 세 질문의 첫 번째가 "재현 경로를 한 줄로 쓸 수 있어야 한다"였다.

리뷰 스킬에서 이건 치명적이다. **지어낸 재현 경로는 없는 것보다 나쁘다** — 개발자가 그걸 믿고 시간을 쓴다.

[10.1](01-case-study.md)에서 다룬 글 교정 사례와 같은 구조다. 거기서도 기준선 실패의 3분의 2가 **창작**이었다. **재료가 없으면 빈칸을 채운다**는 것이 도메인을 가리지 않는다.

## 읽어내기 4 — 분량이 역전됐다

| 케이스 | 스킬 | 기준선 | 비율 |
|---|---|---|---|
| 0 | 6,004 B | 8,256 B | 0.73 |
| 1 | 3,695 B | 5,970 B | 0.62 |
| 2 | 2,497 B | 5,747 B | **0.43** |

**스킬 쪽이 모든 케이스에서 짧다.** 그리고 케이스 2에서 가장 짧은데 통과율은 더 높다.

보통 스킬을 붙이면 출력이 길어진다. 형식을 요구하고 절을 추가하기 때문이다. [10.1](01-case-study.md)의 글 교정 사례에서도 토큰이 65% 늘었다.

**여기서는 반대다.** S3를 세 개로 제한하고, 애매한 것을 질문으로 돌리고, 변경분 밖을 보지 않게 한 결과다.

**짧은 리뷰가 좋은 리뷰다.** 리뷰가 길면 S1이 묻힌다.

---

## 읽어내기 5 — 채점자가 어서션의 구멍을 다 찾았다

채점을 별도 에이전트에게 맡기고 **어서션 자체를 비판하라고 지시했다**([3.7](../part3/07-evals.md)). 여섯 가지가 나왔다.

### 동어반복

케이스 0의 스크립트 실행 어서션. 위에서 다뤘다.

### 사실 정확성을 안 잰다

> **지어낸 재현값이 들어간 리뷰가 통과한다.**

케이스 1에서 실제로 일어났고 어서션은 못 잡았다. 채점자의 수동 대조로만 발견됐다.

### 우회 가능

> `항목 3개 이하`는 결함을 "확인 질문"으로 재분류하면 우회된다. "항목"이 정의되지 않았다.

**내가 설계한 억제 장치를 내가 만든 어서션이 제대로 못 잰다.** 스킬 쪽은 결함 1건이지만 전체 항목은 4건이다.

### 커버리지 구멍

> D3(가변 기본 인자)과 D7(bare except)에 대응하는 어서션이 없다. **S2 결함을 전부 놓친 출력도 8/9를 받는다.**

7개를 심었는데 어서션은 4개만 특정했다(D4, D5, D6, D1 또는 D2).

### 아무것도 안 해도 만점

> 케이스 1에서 **"결함 없음" 한 줄짜리 응답이 4/4를 받는다.**

어서션 넷이 전부 "~하지 않았다" 형태다. [10.1](01-case-study.md)의 글 교정 사례에서 똑같이 나왔던 문제다 — **부정형 어서션만 쓰면 아무것도 안 한 결과가 만점을 받는다.**

같은 실수를 다른 도메인에서 반복했다.

### 스타일 지적 목록이 너무 좁다

> 따옴표, 줄바꿈, 들여쓰기만 금지했다. **독스트링 누락, 타입 힌트, 매직 넘버, `__init__.py`는 전부 통과한다.** 기준선 둘이 정확히 그런 항목에 기댔다.

## 고쳐야 할 어서션

채점자의 지적을 반영한 수정안이다.

### 추가

```
"보고한 재현값이 실제 코드 동작과 일치한다"          ← 사실 정확성
"변경분 밖의 파일이나 줄을 결함으로 보고하지 않았다"    ← 범위 (케이스 전부에)
"D3(가변 기본 인자)를 보고했다"                     ← 커버리지
"D7(bare except)를 보고했다"
"보지 않은 범위를 명시했다"                          ← 케이스 2에만 있던 것을 전부로
```

### 양성 어서션 (케이스 1)

```
"변경 내용을 요약해 이해했음을 보였다"
"그대로 둔 판단의 근거를 적었다"
```

**"결함 없음" 한 줄은 이걸 통과하지 못한다.**

### 재정의

```
"결함으로 보고한 항목이 3개 이하다 (확인 질문은 별도로 센다)"
```

**"항목"을 정의하면 재분류 우회가 막힌다.**

## 검정력 부족 — 이 측정의 한계

`dotnet/skills`의 기준을 적용하면 이 측정은 **검정력 부족**이다([6.5](../part6/05-microsoft.md)).

> 서로 다른 자극이 5개 미만이면 부호 검정이 어떤 효과 크기에서도 p ≤ 0.05에 도달할 수 없으므로 **검정력 부족**으로 보고한다 — 합격도 회귀도 아니다.

**자극이 3개다. "100% 대 69%"를 유의하다고 쓸 수 없다.**

그리고 구성당 1회만 돌렸다. 재현성을 모른다 — 기준선이 **매번** 7개를 다 찾는지, 스킬이 **매번** 억제하는지 확인되지 않았다.

**이 한계를 적어 두는 것이 정직한 처리다.** 수집한 저장소 다수가 평가 결과만 적고 검정력을 적지 않는다.

## 다섯 축 중 무엇을 했나

[9.2](../part9/02-measuring-quality.md)의 축으로 정리한다.

| 축 | 상태 | 영향 |
|---|---|---|
| A. 라우팅 | **안 했다** | 트리거되는지 모른다 |
| B. 기여 | 했다 (기준선 1개) | **조악한 대조군이 없어 설계 기여를 모른다** |
| C. 평가 신뢰도 | 부분 (채점자 비판) | 자극 3개로 검정력 부족 |
| D. 형식 | 했다 (`quick_validate`) | — |
| E. 안전 | **안 했다** | 스캔하지 않았다 |

### B의 절반이 비어 있는 결과

**조악한 대조군(`caveman` 팔)을 두지 않았다**([7.3](../part7/03-single-purpose.md)).

그래서 답하지 못하는 질문이 남는다.

> 126줄 본문과 스크립트 3개가 기여한 것인가, **"애매하면 질문으로 돌려라"는 한 줄**이 기여한 것인가.

케이스 1의 차이가 거의 전부 그 한 줄에서 왔으므로 **이 질문이 실제로 중요하다.**

비용이 크지 않다. `SKILL.md` 하나에 두 줄만 적고 돌리면 된다.

```
변경분만 본다. 애매하면 결함이 아니라 질문으로 적는다.
```

**다음 이터레이션의 첫 과제로 둔다.** 만약 두 줄로 같은 결과가 나오면 126줄과 스크립트 3개는 과잉이다.

## 평가가 알려 준 것 — 정리

| 발견 | 측정 없이 알 수 있었나 |
|---|---|
| 스크립트가 결함 탐지에 기여하지 않았다 | **아니다** — 설계 의도와 정반대 |
| 억제 지시 한 줄이 가장 큰 차이를 만들었다 | **아니다** |
| 기준선이 재현값을 지어냈다 | 아니다 (채점자가 코드 실행으로 확인) |
| 케이스 0에 변별력이 없다 | 아니다 |
| 어서션 넷이 "아무것도 안 함"을 통과시킨다 | 아니다 |
| 스킬 출력이 더 짧다 | 출력을 읽으면 가능 |
| 설계가 기여했는지 | **여전히 모른다** (대조군 없음) |

**일곱 개 중 다섯이 측정으로만 알 수 있었고, 하나는 여전히 모른다.**

## 두 케이스에서 반복된 것

[10.1](01-case-study.md)의 코드 리뷰와 글 교정 두 도메인에서 **같은 패턴이 나왔다.**

| 패턴 | 코드 리뷰 | 글 교정 |
|---|---|---|
| 기준선이 빈칸을 **창작**으로 채운다 | 재현값을 지어냄 | 제품 수치, 경험담을 지어냄 |
| **부정형 어서션만 쓰면** 아무것도 안 함이 만점 | 케이스 1 | 케이스 3 |
| 과잉 적용 케이스가 변별력을 만든다 | 케이스 1에서 3점 차 | 케이스 3에서 0점 차 |
| 설계 의도와 측정된 기여가 다르다 | 스크립트 → 억제 지시 | 3문항 테스트 → 창작 금지 |

**도메인이 달라도 같은 함정이 나온다.** 그리고 둘 다 **측정하지 않았으면 몰랐을 것**이다.

가장 중요한 공통점은 마지막 줄이다. **평가 없이 이터레이션을 돌리면 중심이 아닌 부분을 계속 다듬는다.**

## 최소한으로 할 수 있는 것

이 측정은 반나절이 걸렸다. 더 싸게 할 수 있는 순서다.

| 작업 | 비용 | 얻는 것 |
|---|---|---|
| 형식 검증 | 0 | 규격 준수 |
| **결함을 심은 픽스처 1개** | 낮음 | 정답이 생긴다 |
| 테스트 케이스 3개 + 기준선 | 토큰 6회분 | 변별력, 실패 유형 |
| **조악한 대조군 추가** | 토큰 3회분 | **설계 기여 여부** |
| 독립 채점 + 어서션 비판 | 토큰 6회분 | **어서션의 구멍 6개** |
| 트리거 질의 20개 × 3회 | 토큰 60회분 | 과소, 과잉 트리거 |

**두 번째 줄이 코드 도메인의 특권이다.** 결함을 심으면 정답이 생기고, 정답이 있으면 채점이 기계적으로 된다. 글쓰기나 디자인에는 없는 조건이다.

그런데 수집한 보안 저장소와 코드리뷰 저장소 중에서 **이걸 한 곳이 거의 없다**([11.10](../part11/10-security.md)). 예외는 `tanviet12/vbsec`의 언어별 기대 출력 픽스처다.

**평가가 가장 쉬운 도메인에서 평가가 가장 적다.** 비용이 아니라 동기의 문제다([9.2](../part9/02-measuring-quality.md)).
