# 2.3 길게 쓰면 해결된다는 오해

결과가 마음에 안 들면 프롬프트를 늘린다. 자연스러운 반응이고, 어느 지점까지는 효과가 있다. 그런데 어느 지점을 지나면 늘릴수록 결과가 밋밋해진다.

이 장은 그 전환점이 왜 생기는지, 늘리는 대신 무엇을 하는지를 다룬다.

## 조건이 쌓이면 평균으로 수렴한다

블로그 글을 요청하는 프롬프트가 이렇게 자라는 걸 생각해 보자.

```
1차: 사이드 프로젝트 관리법에 대한 글 써 줘

2차: + 전문적이면서 친근한 톤으로

3차: + 구체적인 예시를 들어

4차: + 너무 딱딱하지 않게

5차: + 실용적인 내용으로

6차: + 독자가 바로 적용할 수 있게
```

6차 프롬프트는 1차보다 길고 요구가 많다. 그런데 결과는 1차보다 더 평범해진다.

이유는 조건들이 **서로 다른 방향으로 당기기** 때문이다. "전문적"과 "친근한"은 반대 방향이다. "딱딱하지 않게"와 "실용적"도 긴장 관계다. 모든 조건을 동시에 만족하는 지점은 어느 조건도 강하게 반영되지 않은 지점이다. 그게 평균이다.

더 나쁜 건 이게 **수렴**이라는 점이다. 서로 다른 조건을 붙인 열 사람이 비슷한 결과를 받는다. 각자 자기 요구를 추가했는데 결과가 서로 닮는다. 조건을 많이 붙일수록 그 사람만의 결과에서 멀어진다.

## 조건은 깎는 도구다

조건의 역할을 잘못 이해한 데서 문제가 생긴다.

| 오해 | 실제 |
|---|---|
| 조건을 붙이면 내용이 채워진다 | 조건은 가능한 출력의 범위를 **좁힌다** |
| 조건이 많으면 정확해진다 | 조건이 많으면 **남는 범위가 평균 근처**가 된다 |

조각을 깎는 일에 비유할 수 있다. 깎으면 형태가 드러나지만, 재료가 없으면 아무리 깎아도 작아질 뿐이다. **글을 채우는 건 조건이 아니라 재료다.**

재료란 이런 것들이다.

- 실제로 있었던 장면 — "후배가 '형, 그거 누가 써요?'라고 물었다"
- 구체적인 숫자 — "할 일 목록이 40개였고 2주차에 7개를 끝냈다"
- 특정한 대상 — "사이드 프로젝트를 세 번 엎어 본 2년차 개발자 한 명"
- 실제 제약 — "슬랙에 붙여 넣는다"

조건 하나를 더 붙이는 것과 재료 하나를 넣는 것 중에 재료가 훨씬 크게 바꾼다. 재료는 출력 범위를 좁히는 게 아니라 **다른 곳으로 옮긴다.** 평균 근처에 없는 내용이 들어가기 때문이다.

## 그래서 묻는 방향을 바꾼다

프롬프트가 안 먹힐 때 묻는 순서를 뒤집는다.

```
# 흔한 방향
무슨 조건을 더 붙이면 될까

# 바꾼 방향
이 글에 들어갈 사실 중에 내가 알고 상대가 모르는 게 뭐지
```

두 번째 질문은 답하기 어렵다. 조건을 붙이는 건 쉽고 재료를 찾는 건 품이 든다. 그래서 사람들이 조건 쪽으로 간다. 쉬운 쪽이 효과가 없다는 것이 이 장의 요지다.

실제로 이 전환을 스킬에 심을 수 있다. 사용자가 "소개글 써 줘"라고만 했을 때, 조건을 추측해 채우는 대신 재료를 묻는 식이다.

> "정확하게 쓰라"는 조건을 더 붙이는 것보다, 그 자리에 들어갈 숫자나 장면을 하나 알려 주시는 게 훨씬 크게 바뀝니다. 그 제품을 처음 써 본 사람이 뭐라고 했는지 기억나시나요?

10부의 케이스 스터디에서 이 구조를 실제로 측정한다. 재료를 묻는 스킬과 안 묻는 기준선을 비교하면, 기준선이 재료의 빈자리를 **지어낸 내용으로 채운다**([10.2](../part10/02-validation.md)).

## 길어도 되는 프롬프트

모든 긴 프롬프트가 나쁜 건 아니다. 길이 자체가 문제가 아니라 **무엇으로 긴가**가 문제다.

| 길어도 되는 것 | 길면 나쁜 것 |
|---|---|
| 재료 (사실, 숫자, 장면, 원문) | 톤, 스타일 조건의 나열 |
| 판단 기준과 그 이유 | 같은 요구의 다른 표현 |
| 출력 형식 명세 | 금지 목록 |
| 예외 상황 처리 | 강조 반복 |

공식 `pdf` 스킬의 `description`은 매우 길다. 작업 열 가지를 나열한다. 그런데 이건 조건의 나열이 아니라 **적용 범위의 열거**다. 트리거를 넓히는 목적이고, 서로 당기지 않는다.

반대로 이런 건 길이가 손해다.

```
전문적이고, 신뢰감 있고, 권위 있으면서도, 접근하기 쉽고,
친근하고, 딱딱하지 않고, 읽기 편하고, 간결하면서도 충실하게
```

여덟 개 형용사가 서로를 지운다. 한 개로 줄이는 쪽이 낫다.

## 조건을 줄이는 세 가지 방법

### 1. 겹치는 조건을 합친다

"친근하게 / 딱딱하지 않게 / 읽기 편하게"는 같은 요구다. 하나만 남긴다. 셋을 적으면 세 배 강조되는 게 아니라, 세 개를 동시에 만족시키려다 중간값으로 간다.

### 2. 조건을 독자로 바꾼다

조건 여러 개가 독자 한 명으로 대체되는 경우가 많다.

```
# 조건 5개
전문적이면서 친근하게, 너무 어렵지 않게, 실무에 바로 쓸 수 있게,
예시를 들어서, 길지 않게

# 독자 1명
사이드 프로젝트를 세 번 엎어 본 2년차 개발자 한 명이 읽는다.
그 사람이 이번엔 안 엎으려면 첫 주에 무엇을 정해야 하는지 알려 준다.
```

아래쪽이 짧고 더 많은 것을 결정한다. "너무 어렵지 않게"는 독자가 정해지면 자동으로 따라온다.

### 3. 조건을 제약으로 바꾼다

취향처럼 적힌 조건이 실제로는 제약인 경우가 있다.

```
# 취향으로 적은 조건
짧게 써 줘

# 실제 제약
슬랙 메시지 한 개로 보낸다. 스크롤이 생기면 아무도 안 읽는다.
```

제약은 범위를 좁히면서도 판단 근거를 같이 준다. 조건과 달리 서로 당기지 않는다.

## 스킬에 적용할 때

스킬은 프롬프트가 파일로 굳은 것이라서 이 문제가 더 커진다. 프롬프트는 안 먹히면 다시 쓰는데, 스킬은 한 번 쌓인 조건이 계속 읽힌다.

실제로 스킬을 개선하는 과정에서 가장 흔한 실수가 **피드백마다 조건을 한 줄 붙이는 것**이다. 테스트에서 결과가 마음에 안 들면 "~하지 마"를 추가한다. 몇 번 반복하면 스킬이 조건 목록이 되고, 그 시점부터 어떤 입력에도 무난한 출력을 낸다.

대안은 조건을 붙이는 대신 **원인을 찾아 설명을 고치는 것**이다. 결과가 밋밋했다면 "밋밋하게 쓰지 마"를 붙이는 게 아니라, 왜 밋밋해졌는지를 보고 재료를 요구하는 단계를 넣는다. [3.8 반복 개선과 배포](../part3/08-iterate-and-ship.md)에서 이 구분을 다룬다.
