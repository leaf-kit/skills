# 2.5 예시의 비용과 효과

예시는 프롬프트에서 가장 효율이 높은 도구다. 말로 열 줄 설명할 것을 두 줄로 전달한다. 그래서 과하게 쓰기 쉽고, 과하게 쓰면 특유의 문제가 생긴다.

이 장은 예시를 넣을 자리와 빼야 할 자리를 가른다.

## 예시가 전달하는 것

예시 한 쌍을 보면 이런 정보가 동시에 전달된다.

```
입력: 사용자 인증에 JWT 토큰을 추가했다
출력: feat(auth): implement JWT-based authentication
```

- 형식 — `type(scope): description`
- 접두어 어휘 — `feat`
- 범위 표기 방식 — 괄호 안에 모듈명
- 언어 — 한국어 입력에 영어 출력
- 시제와 어투 — 명령형 현재
- 길이 감각 — 한 줄

말로 적으면 여섯 줄이고, 여섯 줄을 적어도 "시제와 어투"는 정확히 전달되지 않는다. 예시는 **명시하지 않은 것까지 전달한다.** 이게 장점이면서 동시에 위험이다.

## 비용 1 — 베낀다

예시를 하나만 주면 그걸 베낀다. 형식만 가져오는 게 아니라 내용까지 가져온다.

글쓰기 예시에서 특히 선명하다. "구체적으로 쓰라"는 이유를 설명하려고 예시를 하나 넣었다고 하자.

```
나쁜 예: 다양한 도구를 활용하면 효과적으로 생산성을 높일 수 있습니다.
고친 예: 슬랙 채널을 12개에서 3개로 줄였다. 묻고 답하는 데 걸리는
         시간이 반나절에서 10분이 됐다.
```

그 결과 슬랙 채널 이야기가 아닌 글에도 슬랙 채널이 나온다. 숫자를 쓰라는 메시지가 "12개에서 3개로"라는 구체적 내용으로 전달돼 버린다.

**해결책 세 가지**가 있다.

**예시를 둘 이상 준다.** 하나면 베끼고, 둘이면 둘 사이의 공통점을 찾는다. 두 예시의 소재가 서로 멀면 멀수록 좋다. 소재가 비슷하면 그 소재가 규칙의 일부로 읽힌다.

**예시가 예시임을 적는다.** "아래는 형식을 보여 주기 위한 것이고, 소재를 가져오지 않는다"를 붙인다. 효과가 완벽하지는 않지만 없는 것보다 낫다.

**예시의 소재를 일부러 엉뚱하게 고른다.** 실제 사용 맥락과 멀면 베껴도 티가 나서 베끼지 않는다.

## 비용 2 — 범위를 좁힌다

예시가 암묵적으로 적용 범위를 정한다.

코드 리뷰 스킬에 파이썬 예시만 세 개 넣으면, 자바 코드를 리뷰할 때 약해진다. 명시적으로 "모든 언어에 적용된다"고 적어도 예시가 더 강하게 작동한다.

이 문제는 도메인이 여러 개인 스킬에서 구조적으로 생긴다. 그래서 규격이 도메인별 참조 파일 분리를 권한다.

```
cloud-deploy/
├── SKILL.md          (공통 절차 + 선택 기준)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

본문에는 어느 도메인에도 치우치지 않는 내용만 두고, 도메인별 예시는 각 참조 파일로 내린다. 그러면 AWS 작업에 GCP 예시가 섞이지 않는다.

## 비용 3 — 컨텍스트를 먹는다

예시는 길다. 그리고 스킬 본문에 넣은 예시는 **그 스킬이 트리거될 때마다** 읽힌다([1.3](../part1/03-progressive-disclosure.md)).

판단 기준은 이렇다.

| 예시의 성격 | 어디에 두나 |
|---|---|
| 항상 필요한 형식 예시 | 본문 |
| 특정 상황에만 필요한 예시 | `references/` |
| 양이 많은 예시 모음 | `references/` + 본문에 읽기 조건 |

예시 모음을 참조 파일로 내린 사례를 보자. 한국어 슬롭 패턴 12종의 나쁜 예/고친 예 쌍은 분량이 크다. 본문에는 대표 세 개만 두고 나머지는 참조 파일에 두면서, 본문에 읽기 조건을 적는다.

```markdown
더 많은 패턴은 references/slop-patterns.md를 읽는다. 점검 모드에서
"뭔가 걸리는데 이름을 못 붙이겠는" 문장이 나오면 그 파일을 펼친다.
```

읽기 조건이 중요하다. 조건 없이 "자세한 건 참조 파일에"라고만 쓰면 항상 읽거나 한 번도 안 읽는다.

## 효과가 가장 큰 자리

예시를 꼭 넣어야 하는 경우가 있다.

### 형식이 복잡할 때

중첩 구조나 조건부 필드가 있는 출력은 말로 설명하면 반드시 틀린다. JSON 스키마, 표 구조, 템플릿은 예시가 가장 짧은 설명이다.

### 판정 기준이 주관적일 때

"좋은 글"이나 "읽기 쉬운 코드"는 정의가 안 된다. 나쁜 예와 좋은 예를 한 쌍으로 붙이면 기준선이 생긴다. 이때는 **쌍으로** 주는 것이 중요하다. 좋은 예만 주면 어디까지가 허용인지 모른다.

### 흔한 실수를 막을 때

"이렇게 하지 마"의 예시다. 금지를 추상적으로 적으면 안 걸리고, 실제 틀린 출력을 보여 주면 걸린다.

```yaml
# 좋은 예
name: pdf-processing

# 틀린 예
name: PDF-Processing   # 대문자 불가
name: -pdf             # 하이픈으로 시작 불가
name: pdf--processing  # 연속 하이픈 불가
```

공식 규격이 이 방식으로 `name` 규칙을 설명한다. 규칙을 글로 적고, 바로 아래에 틀린 예 세 개를 이유와 함께 붙였다.

## 예시 개수

경험적인 선이 있다.

| 개수 | 효과 |
|---|---|
| 0개 | 형식이 흔들린다 |
| 1개 | 그대로 베낀다 |
| 2개 | 규칙을 추출한다. **대부분 여기서 충분하다** |
| 3~4개 | 경계 사례를 포함할 때 유용 |
| 5개 이상 | 비용이 효과를 넘어선다 |

3개 이상 쓸 가치가 있는 경우는 **예시들이 서로 다른 것을 가르칠 때**다. 같은 패턴 다섯 개는 두 개와 효과가 같고 비용만 더 든다. 반면 정상 케이스 하나, 경계 케이스 하나, 예외 케이스 하나는 세 개가 다 필요하다.

## 반례의 가치

예시에서 가장 저평가된 것이 **반례**다. "이건 이 스킬이 다룰 일이 아니다"를 보여 주는 예시다.

트리거 평가를 설계할 때 이 원리가 그대로 적용된다. 걸리면 안 되는 요청 중에서 **아슬아슬한 것**이 가치가 있다. PDF 스킬의 반례로 "피보나치 함수 써 줘"를 넣으면 통과는 하지만 아무것도 측정하지 못한다. 키워드는 겹치는데 실제로는 다른 처리가 필요한 요청이 좋은 반례다([1.5](../part1/05-triggering.md)).

본문에서도 같다. 과잉 적용을 막으려면 "이건 해당 안 된다"는 예시가 필요하다.

```markdown
아래는 슬롭이 아니다.
- 사용자 특유의 말투, 반복되는 입버릇, 리듬을 위한 짧은 문장
- 구체적인 장면, 대화, 숫자가 들어간 문장 (설령 문장이 길거나 거칠어도)
- 격식체, 만연체 같은 문체 선택
```

이 목록이 없으면 스킬이 사용자의 목소리를 지운다. 멀쩡한 것을 고치는 실패는 놓치는 실패보다 눈에 덜 띄고 더 해롭다.
