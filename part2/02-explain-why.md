# 2.2 왜를 적는 프롬프트

프롬프트를 쓰다 보면 금지 목록이 길어진다. 결과가 마음에 안 들 때마다 한 줄씩 붙기 때문이다.

```
- 이모지 쓰지 마
- 불릿 세 개 넘게 쓰지 마
- "결론적으로"로 시작하지 마
- 마지막에 요약 문단 붙이지 마
- 표 쓰지 마
- 아니 표는 써도 되는데 3열 넘지 마
```

이 목록은 자란다. 그리고 자라는 만큼 효과가 떨어진다. 이 장은 왜 그런지, 대신 무엇을 쓰는지를 다룬다.

## 금지 목록이 무너지는 이유

금지는 **적용 범위를 스스로 정하지 못한다.**

"표 쓰지 마"라고 적었다고 하자. 데이터 10행을 비교해야 하는 상황이 오면 어떻게 되는가. 표가 가장 명확한 형식인데 금지돼 있다. 결과는 둘 중 하나다. 규칙을 지켜서 나쁜 출력을 내거나, 규칙을 무시해서 신뢰를 깎는다.

금지가 하나일 때는 이 문제가 안 보인다. 열 개가 되면 서로 충돌하기 시작한다. "불릿 세 개 넘게 쓰지 마"와 "항목을 빠뜨리지 마"가 동시에 걸리는 상황이 생긴다.

그리고 대문자로 강조해도 해결되지 않는다.

```
NEVER use tables. ALWAYS keep bullets under three.
```

강조는 우선순위를 올리지만 **판단 근거를 주지 않는다.** 충돌 상황에서 무엇을 포기할지 결정할 재료가 여전히 없다.

## 이유를 적으면 범위가 생긴다

같은 요구를 이유와 함께 적으면 다르게 작동한다.

```
# 금지형
표 쓰지 마.

# 이유형
이 글은 슬랙에 붙여 넣는다. 슬랙에서 마크다운 표는 깨져서
한 줄로 뭉친다. 그래서 비교할 항목이 있으면 표 대신 짧은
문단이나 들여쓰기로 보여 준다.
```

이유형은 **왜 안 되는지**를 적었기 때문에 적용 범위가 따라온다. 슬랙에 안 붙이는 경우에는 표를 써도 된다는 것이 지시 안에 들어 있다. 10행 비교가 필요하면 "표가 깨진다"는 제약 안에서 다른 방법을 찾는다.

차이를 한 줄로 쓰면 이렇다. **금지는 행동을 막고, 이유는 판단을 넘긴다.**

## 이유를 적으면 얻는 세 가지

### 1. 예외 처리가 저절로 된다

프롬프트를 쓸 때 모든 상황을 예상할 수 없다. 금지 목록은 예상한 상황만 다루고, 이유는 예상 못 한 상황까지 다룬다.

```
# 금지형이 못 다루는 상황
"3열 넘지 마" → 실제로 5개 항목을 비교해야 하는 입력이 왔다

# 이유형은 다룬다
"열이 많아지면 모바일에서 가로 스크롤이 생겨 읽기 어렵다"
→ 5개 항목이면 표를 둘로 쪼개거나 목록으로 바꾼다
```

### 2. 지시가 짧아진다

이유 하나가 금지 여러 개를 대체한다.

```
# 금지 4개
- 이모지 쓰지 마
- 느낌표 쓰지 마
- "대박", "꿀팁" 같은 말 쓰지 마
- 과장된 형용사 쓰지 마

# 이유 1개
이 글은 금융 규제 보고서에 들어간다. 감독 기관이 읽는다.
감정을 드러내는 표현은 보고서의 신뢰도를 깎는다.
```

아래쪽이 짧고, 적지 않은 경우까지 포괄한다. "ㅋㅋ"를 금지하지 않았는데도 안 쓴다.

### 3. 나중에 고칠 수 있다

금지 목록은 시간이 지나면 왜 넣었는지 잊는다. 이유가 적혀 있으면 그 이유가 더 이상 유효하지 않을 때 지울 수 있다.

실제로 스킬을 유지하는 비용의 대부분이 여기서 나온다. 500줄짜리 스킬에서 어느 지시를 빼도 되는지 판단해야 할 때, 이유가 없는 줄은 건드리지 못한다. 혹시 중요한 이유가 있을까 봐 그대로 둔다. 그렇게 쓰이지 않는 지시가 쌓인다.

## 이유를 적는 방법

### 결과를 적는다

"하지 마라"보다 "이렇게 되면 이런 일이 생긴다"가 낫다.

```
# 약함
구체적으로 써.

# 강함
구체적인 숫자나 장면이 없으면 독자가 글을 읽고도 아무것도
기억하지 못한다. "효율이 개선됐다"는 읽은 사람 머리에
남지 않고, "빌드가 8초에 끝난다"는 남는다.
```

### 독자나 용도를 적는다

출력물이 어디로 가는지를 적으면 많은 규칙이 불필요해진다.

```
이 커밋 메시지는 6개월 뒤에 버그를 추적하는 사람이 읽는다.
그 사람이 알아야 할 것은 무엇이 바뀌었는지가 아니라
왜 바뀌었는지다. diff를 보면 무엇이 바뀐지는 알 수 있다.
```

이 세 줄이 커밋 메시지 규칙 열 줄을 대체한다.

### 어긴 결과를 보여 준다

이유가 추상적일 때는 나쁜 예와 고친 예를 한 쌍으로 붙인다.

```
나쁜 예: 다양한 도구를 효과적으로 활용하면 생산성이 개선됩니다.
고친 예: 슬랙 채널을 12개에서 3개로 줄였다. 묻고 답하는 데
         걸리는 시간이 반나절에서 10분이 됐다.
```

예시는 이유를 설명하는 가장 짧은 방법이다. 다만 비용이 있다 — 예시를 그대로 베끼는 문제다. [2.5](05-examples.md)에서 다룬다.

## 이유를 적지 말아야 할 때

반대 경우도 있다.

**이유가 자명할 때.** "JSON으로 출력해"에 이유를 붙이면 분량만 늘어난다. 기계가 파싱한다는 건 설명할 필요가 없다.

**이유가 없을 때.** 그냥 취향인 규칙이 있다. "제목에 마침표 안 쓴다"는 이유가 없고, 억지로 만들면 거짓이 된다. 이럴 때는 취향이라고 적는 게 낫다. "우리 팀 관례다. 이유는 없다"가 가짜 이유보다 낫다 — 읽는 쪽이 그 규칙의 무게를 정확히 알 수 있다.

**안 돌면 사고가 나는 일.** 이유를 적어도 판단이 개입되면 열 번 중 한 번은 다르게 간다. 보안이나 데이터 손실이 걸린 일은 프롬프트에 적는 것 자체가 잘못된 선택이고, 훅처럼 판단이 없는 수단으로 가야 한다([1.4](../part1/04-boundaries.md)).

## 스킬에서 특히 중요한 이유

프롬프트는 쓴 사람이 바로 결과를 보고 고친다. 스킬은 다르다. **남이 쓰고, 나중에 쓰고, 내가 보지 않는 상황에서 쓴다.**

금지 목록으로 쓴 스킬은 작성자가 상상한 상황에서만 잘 돈다. 이유로 쓴 스킬은 작성자가 상상하지 못한 상황에서도 방향을 유지한다. 스킬을 리뷰할 때 금지 목록의 비율을 보는 이유다 — 금지가 많고 이유가 없는 스킬은 범용성이 낮다는 신호다.
