# 2.4 출력 형식 설계

[2.1](01-criteria.md)에서 범용성과 재현성이 서로 당긴다고 했다. 해결책은 층을 나누는 것이었다. **판단은 범용적으로, 출력 형식은 구체적으로.**

이 장은 그 아래쪽을 다룬다. 출력 형식을 고정하는 방법이다.

## 형식을 고정해야 하는 이유

형식이 매번 다르면 세 가지가 깨진다.

**비교할 수 없다.** 같은 작업을 두 번 돌렸는데 한 번은 표로, 한 번은 목록으로 나오면 결과를 나란히 놓고 볼 수 없다. 스킬을 개선할 때 전후 비교가 안 된다.

**이어서 쓸 수 없다.** 출력을 다음 단계의 입력으로 쓰는 경우 형식이 계약이다. 형식이 흔들리면 파이프라인이 끊어진다.

**찾을 수 없다.** 사람이 읽을 때도 그렇다. 매번 같은 자리에 같은 종류의 정보가 있으면 훑어서 찾는다. 자리가 바뀌면 다 읽어야 한다.

## 방법 1 — 템플릿을 그대로 준다

가장 확실한 방법이다. 원하는 구조를 마크다운으로 적어서 "이 틀을 그대로 써라"고 지시한다.

```markdown
## 보고서 구조

이 템플릿을 그대로 쓴다.

# [제목]
## 요약
## 발견한 것
## 권고
```

설명하지 않고 보여 주는 것이 핵심이다. "요약, 발견, 권고 세 부분으로 나눠 줘"라고 말로 적으면 제목 표기, 순서, 깊이가 매번 다르게 해석된다. 틀을 보여 주면 그 모양이 그대로 나온다.

### 자리표시자를 명시한다

템플릿 안의 어느 부분이 바뀌는지 표시해 둔다.

```markdown
원문: [문제가 된 문장을 그대로]
이유: [어느 패턴에 걸렸는지 + 어느 테스트에 막혔는지]
수정: [고친 문장, 삭제가 답이면 "(삭제)"]
```

`[ ]`로 감싼 부분이 채울 자리다. 이렇게 적으면 "삭제가 답인 경우"처럼 애매한 상황의 처리까지 형식 안에 들어간다.

## 방법 2 — 입력과 출력 쌍으로 보여 준다

형식이 입력에 따라 달라지는 경우에는 템플릿 하나로 부족하다. 예시 쌍을 쓴다.

```markdown
## 커밋 메시지 형식

**예시 1**
입력: 사용자 인증에 JWT 토큰을 추가했다
출력: feat(auth): implement JWT-based authentication

**예시 2**
입력: 오타 수정, README의 설치 명령어가 틀렸다
출력: docs(readme): fix install command typo
```

두 예시가 보여 주는 것은 형식만이 아니다. 접두어 선택(`feat` 대 `docs`), 범위 지정(`auth` 대 `readme`), 언어(한국어 입력에 영어 출력)까지 같이 전달된다. 이걸 말로 적으면 열 줄이 넘는다.

예시의 개수와 비용은 [2.5](05-examples.md)에서 다룬다. 여기서는 하나만 적어 둔다. **예시 두 개가 한 개보다 훨씬 낫다.** 하나면 그걸 베끼고, 둘이면 둘 사이의 규칙을 찾는다.

## 방법 3 — 순서를 고정한다

내용이 아니라 순서만 고정하는 경우도 있다. 출력이 길고 사용자가 특정 부분만 볼 때 유용하다.

```markdown
점검 모드의 출력 순서

① 슬롭으로 판정한 문장 목록
② 전체 수정본
③ 한 줄 체크리스트
```

②를 먼저 보고 싶은 사람은 두 번째 블록으로 바로 간다. 순서가 매번 바뀌면 매번 찾아야 한다.

순서를 정할 때 기준이 하나 있다. **복사해서 쓸 것을 중간에 두지 않는다.** 전체 수정본처럼 그대로 복사하는 블록은 앞뒤에 설명이 끼지 않아야 한다. 설명이 섞이면 복사할 때 걸러내야 한다.

## 방법 4 — 구조화 출력

기계가 읽을 출력은 JSON이나 TSV로 받는다. 이때는 형식을 말로 적는 대신 **스키마를 준다.**

```json
{
  "expectations": [
    {"text": "어서션 문장", "passed": true, "evidence": "근거"}
  ],
  "summary": {"passed": 2, "failed": 1, "total": 3, "pass_rate": 0.67}
}
```

필드 이름이 정확해야 하는 경우에는 그렇다고 적는다. 공식 `skill-creator` 스킬이 이 경고를 직접 적어 두었다.

> `grading.json`의 expectations 배열은 반드시 `text`, `passed`, `evidence` 필드를 써야 한다(`name`/`met`/`details` 같은 변형이 아니라). 뷰어가 이 필드 이름에 의존한다.

이유를 같이 적은 점이 중요하다. "뷰어가 이 이름에 의존한다"가 있으면, 왜 변형이 안 되는지 알고 지킨다. 이유 없이 "정확히 이 이름을 써라"만 있으면 비슷한 이름으로 바꿔도 될 것 같아 보인다.

## 형식을 고정하면서 생기는 문제

### 빈 칸을 채우려 든다

템플릿에 섹션이 다섯 개 있으면 다섯 개를 다 채운다. 채울 내용이 없는 섹션에도 뭔가 쓴다. 이게 슬롭이 생기는 전형적인 경로다.

해결 방법은 **비워도 되는 칸을 명시하는 것**이다.

```markdown
## 권고
(권고할 것이 없으면 이 절을 삭제한다. "특별한 권고 없음"이라고
적지 않는다. 그 문장은 아무 정보가 없다.)
```

"없으면 빼라"를 적지 않으면 "없음"이라고 적힌 섹션이 남는다.

### 형식이 내용을 왜곡한다

표를 쓰라고 했는데 표에 안 맞는 내용이 올 때, 내용을 깎아서 표에 맞춘다. 비교할 항목이 두 개뿐인데 3열 표를 만들면 세 번째 열이 억지로 생긴다.

그래서 형식 지시에 **탈출구**를 둔다.

```markdown
항목이 세 개를 넘으면 표로 만든다. 두 개 이하면 문장으로 쓴다.
표의 열을 채우려고 항목을 만들어 넣지 않는다.
```

### 분량 지시가 형식과 충돌한다

"세 문단으로"와 "모든 발견을 빠뜨리지 말고"를 같이 적으면 충돌한다. 발견이 열 개면 세 문단에 안 들어간다. 이때 어느 쪽을 포기할지 적어 둔다.

```markdown
세 문단을 목표로 하되, 빠뜨리는 것보다 길어지는 쪽을 택한다.
```

## 형식 설계 점검표

쓴 형식 지시를 놓고 확인한다.

| 질문 | 통과 못 하면 |
|---|---|
| 틀을 말로 설명했나, 보여 줬나 | 보여 주는 쪽으로 바꾼다 |
| 채울 자리가 표시돼 있나 | `[ ]`로 명시한다 |
| 비워도 되는 칸이 적혀 있나 | "없으면 삭제한다"를 넣는다 |
| 내용이 형식에 안 맞을 때의 탈출구가 있나 | 조건을 붙인다 |
| 복사할 블록이 끊기지 않게 배치됐나 | 순서를 고친다 |
| 필드 이름이 정확해야 하는 이유가 적혀 있나 | 이유를 적는다 |

## 스킬에서의 출력 형식

스킬에서 출력 형식은 특히 무게가 크다. 스킬은 여러 번 쓰이고, 사용자가 그 형식에 익숙해진다. 형식이 일정하면 사용자가 결과를 훑는 법을 익히고, 흔들리면 매번 처음부터 읽는다.

그리고 형식은 **스킬이 작동했는지 확인하는 신호**이기도 하다. 스킬에 정해진 출력 형식이 있으면, 그 형식으로 나왔는지만 봐도 스킬이 트리거됐는지 알 수 있다. 평가에서 이 성질을 쓴다 — "체크리스트가 끝에 붙어 있는가"는 검증 가능한 어서션이면서 트리거 여부의 지표다([3.7](../part3/07-evals.md)).
