# 8.4 메모리, 컨텍스트

생태계에서 **중복이 가장 심한 도메인**이다. 같은 결핍을 푸는 저장소가 일곱 개 넘게 있고 합쳐서 21만 스타가 넘는다.

## 이름까지 닮았다

```
claude-mem    memU    MemOS    EverOS    cognee    context-mode
```

`memU`, `MemOS`, `EverOS`는 세 글자 안에서 같은 어휘를 쓴다. 저장소를 모르는 사람이 셋을 구별할 수 없다.

## 하나의 결핍, 세 가지 다른 문제

이름이 닮았지만 푸는 문제가 정확히 같지는 않다. 셋으로 갈린다.

### 문제 A — 세션을 넘어 기억하지 못한다

| 저장소 | 접근 |
|---|---|
| `thedotmack/claude-mem` | 모든 것을 포착해 세션 간 영속 컨텍스트 |
| `NevaMind-AI/memU` | 에이전트 간 개인 메모리 |
| `EverMind-AI/EverOS` | 모든 AI 에이전트용 이식 가능 메모리 계층 |
| `MemTensor/MemOS` | 자기진화 메모리 OS |

네 저장소가 같은 결핍을 푼다. 차이는 범위다 — 한 도구 안인가(`claude-mem`), 여러 에이전트에 걸치는가(`memU`, `EverOS`).

### 문제 B — 컨텍스트 창이 모자란다

| 저장소 | 접근 |
|---|---|
| `mksglu/context-mode` | 도구 출력을 샌드박싱해 컨텍스트 창 최적화 |

이쪽은 기억이 아니라 **비용** 문제다. 도구 출력이 컨텍스트를 먹는 것을 막는다.

[1.3](../part1/03-progressive-disclosure.md)에서 다룬 점진적 공개와 같은 방향이다. 스킬 설계에서는 참조 파일을 조건부로 읽어 비용을 낮추고, 이쪽은 도구 출력을 걸러서 낮춘다.

### 문제 C — 긴 작업의 상태를 잃는다

| 저장소 | 접근 |
|---|---|
| `OthmanAdi/planning-with-files` | 파일 기반 영속 계획 |

설명이 "AI 코딩 에이전트와 긴 작업을 위한 파일 기반 영속 계획. 크래시..."다.

**해법이 가장 단순하다.** 메모리 계층을 만드는 대신 계획을 파일에 쓴다. 에이전트가 중단되거나 컨텍스트를 잃어도 파일이 남는다.

`obra/superpowers`의 `writing-plans`, `executing-plans`와 같은 아이디어다([7.1](../part7/01-superpowers.md)). 계획을 산출물로 만들면 상태가 외부에 남는다.

## cognee만 생성일이 다르다

| 저장소 | 생성 |
|---|---|
| `topoteretes/cognee` | **2023-08-16** |
| `MemTensor/MemOS` | 2025-07-06 |
| `NevaMind-AI/memU` | 2025-07-29 |
| `thedotmack/claude-mem` | 2025-08-31 |
| `EverMind-AI/EverOS` | 2025-10-28 |
| `OthmanAdi/planning-with-files` | 2026-01-03 |
| `mksglu/context-mode` | 2026-02-23 |

`cognee`가 2023년 8월이다. 스킬 규격 공개(2025-09-22)보다 2년 빠르다.

**원래 AI 메모리 플랫폼이었고 나중에 스킬을 붙였다.** `SKILL.md` 18개가 있다. [5.2](../part5/02-top50.md)에서 트랙 A에서 제외한 저장소다 — 스킬을 빼도 플랫폼이 남는다.

`MemOS`와 `memU`도 2025년 7월 생성으로 규격보다 두 달 빠르다. **메모리 문제는 스킬 생태계가 만든 문제가 아니다.** 에이전트가 생기면서 생긴 문제이고, 스킬은 그 해법을 배포하는 형식으로 나중에 붙었다.

이것이 이 도메인의 중복을 설명하는 한 축이다. 스킬 생태계 밖에서 이미 경쟁하던 프로젝트들이 스킬 형식을 추가하면서 한 목록에 모였다.

이유는 이 저장소들이 제품이기 때문으로 보인다. 큐레이션 목록은 작성자가 흥미를 잃으면 멈추고, 제품은 사용자가 있으면 이어진다.

## 라이선스 — NOASSERTION이 둘

| 저장소 | 라이선스 |
|---|---|
| `claude-mem` | Apache-2.0 |
| `cognee` | Apache-2.0 |
| `EverOS` | Apache-2.0 |
| `MemOS` | Apache-2.0 |
| `planning-with-files` | MIT |
| `context-mode` | **NOASSERTION** |
| `memU` | **NOASSERTION** |

`NOASSERTION`은 깃허브가 라이선스를 식별하지 못했다는 뜻이다. 파일이 있어도 표준 형식이 아니거나 커스텀 조항이 섞인 경우다.

**메모리 도구에서 이 문제가 특히 중요하다.** 메모리 도구는 대화 내용과 코드를 저장한다. 데이터가 어디에 어떻게 저장되고 누가 접근하는지가 라이선스와 약관에 달려 있다. `[확인 필요: context-mode, memU의 라이선스 원문 조항]`

## 이 도메인의 고유 위험 — 메모리 오염

`NVIDIA/SkillSpector`의 탐지 범주 17개 중 하나가 **메모리 오염**(memory poisoning)이다([6.8](../part6/08-others.md)).

메모리 도구가 없으면 잘못된 정보가 세션과 함께 사라진다. 메모리가 있으면 **한 번 심은 거짓이 계속 남는다.**

공격 경로를 생각해 보면 이렇다.

| 단계 | 일어나는 일 |
|---|---|
| 1 | 공격자가 저장소나 문서에 조작된 내용을 심는다 |
| 2 | 에이전트가 읽고 메모리에 저장한다 |
| 3 | 이후 모든 세션에서 그 내용을 사실로 취급한다 |
| 4 | 원본을 지워도 메모리에는 남는다 |

4번이 핵심이다. **메모리는 출처에서 분리된다.** 저장된 뒤에는 어디서 왔는지 추적하기 어렵다.

수집한 일곱 저장소 중 이 위험을 다루는지 확인된 것이 없다. `[확인 필요: 메모리 저장소들의 출처 추적, 검증 기능]`

`cloudflare/agent-skills-discovery-rfc`가 스킬 배포에 무결성 검증을 제안했는데([6.6](../part6/06-cloudflare.md)), 메모리 내용에 대한 같은 제안은 수집 데이터에서 보이지 않는다.

## 중복이 왜 유지되는가

일곱 저장소가 합쳐서 21만 스타다. 승자가 정해지지 않았다.

### 비교 비용이 선택 비용보다 크다

일곱 개를 비교하려면 각각 설치해서 몇 주 써 봐야 한다. 메모리 도구의 효과는 즉시 안 보인다 — 세션을 여러 번 넘겨야 차이가 난다.

[7.3](../part7/03-single-purpose.md)에서 단일 목적 스킬이 터지는 조건으로 "효과가 즉시 보인다"를 꼽았다. 메모리 도구는 그 조건을 못 만족한다. 그래서 **먼저 눈에 띈 것을 쓰고, 비교하지 않는다.**

결과적으로 스타수가 "누가 더 잘 푸는가"가 아니라 "**누가 먼저 눈에 띄었는가**"를 반영한다.

### 측정이 없다

이 도메인은 객관적 평가가 가능하다. 세션을 넘긴 뒤 특정 사실을 기억하는지 세면 된다. 회상 정확도, 저장 비용, 조회 지연을 다 측정할 수 있다.

**일곱 저장소 중 벤치마크를 확인한 것이 없다.** 공통 벤치마크가 있으면 중복이 정리된다. 없으면 일곱 개가 계속 공존한다.

[9.5 중복과 포화](../part9/05-saturation.md)에서 이 메커니즘을 다룬다.

### 범위가 미묘하게 다르다

완전히 같지는 않다. 한 도구 전용(`claude-mem`)과 여러 에이전트에 걸치는 것(`memU`, `EverOS`), 기억(`MemOS`)과 비용 절감(`context-mode`)과 계획 영속화(`planning-with-files`)가 섞여 있다.

**사용자가 그 차이를 알기 어렵다.** 설명이 "메모리"라는 같은 단어를 쓰기 때문이다. `google/skills`가 `description`에 "이건 쓰지 말고 저 스킬을 쓰라"를 적어 경계를 그린 것처럼([6.4](../part6/04-google.md)), 저장소 설명도 그렇게 쓸 수 있다. 아무도 하지 않는다 — 경쟁자를 가리키는 일이기 때문이다.

## 스킬 설계 관점에서 배울 것

### planning-with-files가 가장 스킬다운 해법이다

메모리 문제를 **파일로** 푼다. 새 인프라를 만들지 않는다.

이것이 스킬 생태계의 성격과 맞는다. 스킬은 마크다운 파일이고, 계획도 파일이다. 에이전트가 이미 파일을 읽고 쓸 수 있으므로([1.4](../part1/04-boundaries.md)의 "방법을 몰라서 못 하는가"), 수단이 아니라 **방법**이 결핍이다.

반면 `MemOS`나 `EverOS`는 메모리 계층을 만든다. 수단을 추가하는 접근이고, MCP 서버에 가깝다. 스킬 형식을 붙였지만 본체는 인프라다.

| 접근 | 결핍 | 적합한 수단 |
|---|---|---|
| 계획을 파일로 | 방법을 모른다 | **스킬** |
| 메모리 계층 | 수단이 없다 | MCP 서버 / 인프라 |

`planning-with-files`가 MIT이고 `SKILL.md` 18개라는 점도 일치한다. 인프라 없이 방법만 배포한다.

### context-mode는 점진적 공개의 다른 적용

도구 출력을 샌드박싱한다. 스킬 설계에서 참조 파일을 조건부로 읽는 것과 같은 원리를 런타임에 적용한 것이다([1.3](../part1/03-progressive-disclosure.md)).

스킬을 만들 때도 같은 판단이 필요하다. 스크립트 출력이 길면 전부 컨텍스트에 들어온다. [3.5](../part3/05-scripts.md)에서 "출력을 기계가 읽을 수 있게 낸다"고 한 것이 비용 측면에서도 유리하다 — JSON으로 필요한 값만 꺼내 쓰면 산문 전체를 읽지 않는다.

## 도메인 요약

### 강점

**유지가 잘 된다.** 일곱 저장소 전부 최근 푸시다. 경쟁이 유지를 강제한다.

**접근이 다양하다.** 인프라형(메모리 계층), 파일형(계획 영속화), 비용형(컨텍스트 최적화)이 다 탐색됐다.

**규격보다 먼저 있던 프로젝트들이 참여했다.** `cognee`(2023-08), `MemOS`, `memU`(2025-07)가 스킬 형식을 추가했다. 규격의 채택 범위를 보여 준다.

### 한계

**중복이 가장 심하다.** 일곱 저장소가 같은 결핍을 푼다. 승자가 정해지지 않았고, 정해질 메커니즘이 없다.

**벤치마크가 없다.** 객관적 측정이 가능한 도메인인데 아무도 측정하지 않는다. 회상 정확도와 비용을 재면 중복이 정리될 것이다.

**메모리 오염 위험이 다뤄지지 않는다.** 저장된 내용이 출처에서 분리되고, 한 번 심은 거짓이 계속 남는다. `NVIDIA/SkillSpector`가 탐지 범주로 꼽은 위험인데, 메모리 저장소들이 이를 다루는지 확인되지 않았다.

**라이선스 불명이 둘 있다.** 대화와 코드를 저장하는 도구에서 `NOASSERTION`은 실무적 장애다.

**이름으로 구별되지 않는다.** `memU`, `MemOS`, `EverOS`, `claude-mem`을 처음 보는 사람이 가를 수 없다.

### 골라 쓰는 기준

| 상황 | 추천 |
|---|---|
| 긴 작업의 상태를 잃지 않고 싶다 | `OthmanAdi/planning-with-files` (파일 기반, 가장 단순) |
| 한 도구에서 세션을 넘겨 기억 | `thedotmack/claude-mem` |
| 여러 에이전트에 걸친 메모리 | `memU` 또는 `EverOS` — **라이선스 확인** |
| 컨텍스트 비용을 줄인다 | `mksglu/context-mode` — 라이선스 확인 |
| 지식 그래프 기반 | `topoteretes/cognee` |
| 설치 전 | `NVIDIA/SkillSpector`로 스캔 |

**가장 단순한 것부터 시도하는 쪽을 권한다.** 계획을 파일에 쓰는 것으로 해결되는 문제에 메모리 계층을 설치하면, 설치, 검증, 유지 비용이 추가되고 메모리 오염 위험이 생긴다.
