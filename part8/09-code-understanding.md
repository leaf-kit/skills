## graphify — 선별 규칙의 거짓 음성

[5.1](../part5/01-collection.md)에서 기계 판정 규칙을 세웠다. `SKILL.md` 파일 개수를 센다.

`Graphify-Labs/graphify`는 `SKILL.md`가 **0개**다. 그래서 선별에서 제외했다. 스타 123,488개로 전체 8위인 저장소다.

그런데 설명이 이렇다.

> 어떤 코드베이스든, 그 문서, SQL 스키마, 설정, PDF까지 질의 가능한 지식 그래프로 바꾼다. **`/graphify` 스킬**...

파일 트리를 다시 조회했다.

```
graphify/skill-agents.md
graphify/skill-aider.md
graphify/skill-amp.md
graphify/skill-claw.md
graphify/skill-codex.md
graphify/skill-copilot.md
graphify/skill-devin.md
graphify/skill-droid.md
graphify/skill-kilo.md
graphify/skill-kiro.md
graphify/skill-opencode.md
graphify/skill-pi.md
```

**스킬이 12개 있다. 파일명이 `SKILL.md`가 아니다.**

### 왜 이렇게 됐나

하네스별로 스킬 파일을 따로 두면서 파일명에 도구 이름을 넣었다. `skill-codex.md`, `skill-copilot.md`처럼 된다.

규격은 두 가지를 요구한다([1.2](../part1/02-anatomy.md)).

- 스킬은 **디렉터리**이고 그 안에 `SKILL.md`가 있다
- `name` 필드가 **부모 디렉터리 이름과 같아야** 한다

이 저장소는 둘 다 따르지 않는다. 디렉터리가 아니라 파일 하나씩이고, 파일명이 `SKILL.md`가 아니다.

다른 저장소들은 같은 문제를 디렉터리로 푼다.

| 저장소 | 방식 |
|---|---|
| `obra/superpowers` | `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/` 등 하네스별 **디렉터리** |
| `DietrichGebert/ponytail` | `.openclaw/skills/`, `skills/` 등 하네스별 디렉터리 |
| `epoko77-ai/im-not-ai` | `skills/`, `codex/skills/`, `copilot/skills/` |
| **`Graphify-Labs/graphify`** | `graphify/skill-<도구>.md` **파일** |

### 이 사실이 뜻하는 것

**세 가지를 적어 둔다.**

**1. 이 책의 선별 규칙에 거짓 음성이 있다.** [5.1](../part5/01-collection.md)에서 거짓 음성의 예로 큐레이션 목록과 규격 저장소를 들었다. 여기에 "**스킬을 담았지만 규격 파일명을 쓰지 않은 저장소**"가 추가된다. 트랙 A 선별에서 전체 8위 저장소가 빠졌다.

**2. 규격 준수가 보편적이지 않다.** 12만 스타 저장소가 규격 파일명을 안 쓴다. `agentskills/agentskills`의 `skills-ref validate`를 돌리면 통과하지 않을 것이다([8.3](03-builders.md)).

**3. 기계 판정을 하나만 쓰면 안 된다.** `SKILL.md` 개수 하나로는 부족하고, 설명에 "skill"이 있는지도 같이 봐야 한다. 그러면 오탐이 늘어난다 — 선별이 다시 사람 판정으로 돌아온다.

**선별 규칙을 고치는 쪽을 택하지 않았다.** 이유는 재현성이다. 규칙을 복잡하게 만들면 재현이 어려워지고, 사람 판정 비중이 커진다. 대신 **규칙이 놓친 것을 기록으로 남긴다.** 이 저장소는 그 첫 기록이다.

갱신할 때 이 항목을 점검표에 넣는다 — 스타 상위권에서 `SKILL.md`가 0개인 저장소는 파일명 변형을 확인한다([9.6](../part9/06-update-policy.md)).

181일에 12만 스타, 일평균 682개로 생태계 3위다([0.2](../part0/02-why-stars.md)).

### 입력 범위가 넓다

> 어떤 코드베이스든, **그 문서, SQL 스키마, 설정, PDF까지** 질의 가능한 지식 그래프로 바꾼다.

코드만이 아니라 문서, 스키마, 설정, PDF를 함께 읽는다. **프로젝트의 지식이 코드에만 있지 않다는 인식**이 설계에 있다.

### 왜 이게 스킬인가

이 저장소가 푸는 결핍을 [1.4](../part1/04-boundaries.md)의 기준으로 보면 애매하다.

| 결핍 | 수단 |
|---|---|
| 코드베이스를 읽을 수단이 없다 | ✕ 에이전트는 파일을 읽을 수 있다 |
| 큰 코드베이스를 전부 읽을 컨텍스트가 없다 | ○ **이게 결핍이다** |

**컨텍스트 한계가 결핍이다.** 10만 줄 코드베이스를 전부 읽을 수 없으므로, 질의 가능한 구조로 바꿔 필요한 부분만 가져온다.

이것이 [1.3](../part1/03-progressive-disclosure.md)의 점진적 공개와 같은 문제다. 스킬 설계에서는 참조 파일을 조건부로 읽고, 이쪽은 코드베이스를 인덱싱해 조건부로 조회한다.

그래서 본체는 스킬이 아니라 인덱싱 도구다. 스킬은 그 도구를 에이전트가 쓰게 하는 층이다 — `alibaba/open-code-review`와 같은 구조다([8.2](02-code-review.md)).

### 12개 하네스 지원

파일명은 규격을 안 따르지만 하네스 지원 범위는 넓다. `agents`, `aider`, `amp`, `claw`, `codex`, `copilot`, `devin`, `droid`, `kilo`, `kiro`, `opencode`, `pi`다.

상위권 저장소의 공통 전략을 다시 확인한다([7.6](../part7/06-why-individuals-win.md)).

## Understand-Anything — 목적을 설명에 박았다

| 항목 | 값 |
|---|---|
| 스타 | 85,163 |
| `SKILL.md` | 9 |
| 라이선스 | MIT |
| 푸시 | 2026-10-02 |

설명 첫 문장이 이렇다.

> **가르치는 그래프 > 인상적인 그래프.** 어떤 코드든 탐색하고 검색할 수 있는 인터랙티브 지식 그래프로 바꾼다.

**첫 문장이 비교다.** 무엇을 하는지보다 무엇을 우선하는지를 먼저 적었다.

이것이 [2.2](../part2/02-explain-why.md)에서 다룬 "이유를 적는다"의 설명 버전이다. 지식 그래프 도구는 보기 좋은 그림을 만들기 쉽고, 그 그림이 이해를 돕지 않을 수 있다. 어느 쪽을 택할지를 설명에 박아 두면 사용자가 기대를 맞춘다.

`cathrynlavery/diagram-design`의 "그림자 없음, Mermaid 슬롭 없음"과 같은 종류의 문구다([8.7](07-design.md)). **이 생태계에서 설명에 안티패턴이나 우선순위를 적는 관례가 생기고 있다.**

### 스킬 9개의 구성

```
understand                  기본
understand-chat             대화로 탐색
understand-dashboard        대시보드
understand-diff             변경 분석
understand-domain           도메인 모델
understand-explain          설명
understand-figma            Figma 연동
understand-knowledge        지식
understand-onboard          온보딩
```

**`understand-onboard`가 있다.** 새로 합류한 사람이 코드베이스를 파악하는 용도다. 코드 이해 도구의 가장 분명한 용례이고, 그걸 별도 스킬로 뺐다.

`understand-diff`도 실용적이다. 전체 구조가 아니라 **변경분**을 이해하는 경로다. 코드 리뷰와 맞물린다([8.2](02-code-review.md)).

`understand-figma`는 코드가 아니라 디자인을 읽는다. 범위가 코드 밖으로 나간 스킬이다.

### 접두어로 묶었다

아홉 개가 모두 `understand-`로 시작한다. 번들 안에서 **접두어가 네임스페이스 역할**을 한다.

`epoko77-ai/im-not-ai`의 `humanize-*`([8.5](05-writing.md))와 `anthropics/defending-code-reference-harness`의 `dnr-*`([6.2](../part6/02-anthropic-others.md))가 같은 방식이다.

실용적 이점이 있다. 사용자가 `understand-`까지 입력하면 관련 스킬이 모인다. 그리고 다른 저장소의 스킬과 이름이 충돌하지 않는다 — 스킬 여러 번들을 같이 설치하는 환경에서 중요하다([7.2](../part7/02-addyosmani.md)).

## book-to-skill — 결과물이 지식형이 된다

| 항목 | 값 |
|---|---|
| 스타 | 33,440 |
| `SKILL.md` | **1** |
| 라이선스 | MIT |
| 푸시 | 2026-09-29 |

> 어떤 기술서 PDF든 Claude Code 스킬로 바꾼다 — 일하면서 공부하고 참조하고 쓸 수 있게 준비된 상태로.

[8.3](03-builders.md)에서 변환형 메타스킬로 다뤘다. 이 장에서는 **결과물의 성격**을 본다.

### 세 가지 문제

**1. 선별을 건너뛴다.** 책 300쪽을 스킬로 바꾸면 300쪽이 참조 파일이 된다. 좋은 스킬은 "항상 필요한 것"과 "조건부인 것"을 가르는 작업의 결과인데([1.3](../part1/03-progressive-disclosure.md)), 자동 변환은 그 작업을 하지 않는다.

**2. 지식형이 되고 수명이 짧아진다.** 책에 유효기간이 있으면 스킬도 같이 낡는다. 그리고 책은 갱신되지 않는다 — 개정판이 나올 때까지 몇 년이 걸린다.

**3. 저작권이 걸린다.** 기술서를 스킬로 바꾸면 그 책의 내용이 스킬에 들어간다. 개인이 쓰는 것과 공개 배포하는 것은 다르다.

세 번째가 실제로 나타난 사례가 `wondelai/skills`(2,322)다 — "베스트셀러 책에서 가져온 프레임워크. 50개 스킬"을 MIT로 배포한다([8.8](08-product.md)).

**도구는 MIT이고 결과물의 권리는 도구가 보장하지 않는다.** `book-to-skill`로 만든 스킬을 공개하면 책의 권리 문제가 사용자에게 온다. `[확인 필요: book-to-skill이 저작권 경고를 포함하는지]`

### 그런데 왜 3만 스타인가

**빈 파일에서 시작하는 것이 어렵고 변환은 쉽다**([8.3](03-builders.md)). 스킬을 만들고 싶은데 무엇을 쓸지 모르는 사람에게, 가진 책을 넣으면 분량이 나온다는 제안은 매력적이다.

문제는 그렇게 만든 스킬이 좋은 스킬이 아닐 수 있다는 점이다. **분량이 나오는 것과 쓸모가 있는 것은 다르다.**

## 도메인 요약

### 강점

**결핍을 정확히 짚었다.** 컨텍스트 한계가 실제 문제이고, 질의 가능한 구조로 바꾸는 것이 직접적인 해법이다.

**설명에 우선순위를 적은 사례가 있다.** `Understand-Anything`의 "가르치는 그래프 > 인상적인 그래프"는 기대를 맞추는 설계다.

**접두어 네임스페이스가 쓰인다.** `understand-*` 아홉 개가 충돌을 피하고 묶인다.

**입력 범위가 넓다.** `graphify`가 코드, 문서, 스키마, 설정, PDF를 함께 읽는다.

**유지된다.** 세 저장소 전부 최근 푸시다.

### 한계

**규격 준수가 안 된 사례가 있다.** `graphify`가 `skill-<도구>.md`를 쓴다. 검증 도구를 통과하지 않을 것이고, 이 책의 선별에서도 빠졌다.

**평가가 없다.** 코드 이해는 측정 가능한 축이 있다 — 인덱싱한 구조가 실제 코드와 맞는지, 질의 결과가 정확한지다. `Agents365-ai/drawio-skill`이 드리프트 디프와 CI 테스트를 구현한 것처럼([8.7](07-design.md)) 가능한 영역인데 확인된 것이 없다.

**변환 결과물의 품질이 보장되지 않는다.** `book-to-skill`은 선별을 건너뛰고 지식형을 만들며 저작권이 걸린다.

**본체가 스킬이 아닌 경우가 많다.** 인덱싱 도구가 본체이고 스킬은 그것을 부르는 층이다. 설치, 유지 비용이 스킬 하나보다 크다.
