# 8.5 문서, 글쓰기

AI가 쓴 글을 사람 글처럼 고치는 스킬이 **세 언어로 각각 존재한다.** 이 도메인의 중심 사실이다.

| 스타 | 저장소 | 언어 | SKILL.md | 라이선스 | 생성 |
|---|---|---|---|---|---|
| 53,730 | `blader/humanizer` | 영어 | 1 | MIT | 2026-01-18 |
| 5,835 | `epoko77-ai/im-not-ai` | 한국어 | 7 (실질 4) | MIT | 2026-04-24 |
| 3,937 | `KKKKhazix/human-writing` | 중국어 | — | — | 2026-08-05 |
| 13,220 | `latent-spaces/brag` | 영어 | 2 | — | — |
| 7,233 | `zenstory-ai/oh-story-claudecode` | 중국어 | — | — | — |
| 2,469 | `zenstory-ai/drama-skills` | 중국어 | — | — | — |
| 7,986 | `ChenLiu-1996/figures4papers` | — | 1 | — | — |

여기에 공식 번들의 글쓰기 스킬이 있다. `anthropics/skills`의 `doc-coauthoring`(15,815바이트, 번들 없음), `internal-comms`(32줄), `brand-guidelines`(73줄)다.

(수집 날짜: 2026-10-04. 확인 수준: `epoko77-ai/im-not-ai` 정밀 리뷰, `blader/humanizer`는 [7.3](../part7/03-single-purpose.md)에서 정밀 리뷰, 나머지 요약 리뷰)

## 같은 제약이 세 언어에서 반복된다

세 저장소가 같은 금지선을 둔다.

| 저장소 | 제약 |
|---|---|
| `blader/humanizer` | `without changing what it says` (말하는 내용을 바꾸지 않고) |
| `epoko77-ai/im-not-ai` | **내용은 한 글자도 건드리지 않고** |
| `KKKKhazix/human-writing` | AI가 쓴 중국어를 구체적인 사람이 말하는 것처럼 |

**문체 교정의 가장 큰 위험이 내용 변경이라는 인식이 독립적으로 세 번 나타났다.**

이것이 좋은 금지선 설계의 사례다. 교정 스킬은 "고쳐라"는 지시로 가득하므로 무언가 고치려 든다. 어디까지가 허용인지 적지 않으면 내용까지 바꾼다([3.3](../part3/03-body.md)의 과잉 적용 방지).

그리고 이 제약은 **검증 가능한 어서션이 된다.**

```
"원문의 사실 내용이 바뀌지 않았다"
"원문에 없던 주장을 추가하지 않았다"
```

주관적 영역에서 금지선을 재는 전형이다([3.7](../part3/07-evals.md)).

## im-not-ai — 패턴을 체계화한 사례

| 항목 | 값 |
|---|---|
| 버전 | v2.3.2 |
| 패턴 | **10대 카테고리 × 85 서브 패턴** (+검증 대기 1건) |
| 심각도 | S1 / S2 / S3 |
| 탐지 단위 | 스팬 |
| 지원 도구 | Claude Code, GitHub Copilot CLI, OpenAI Codex CLI, Gemini CLI |

### 패턴 목록이 언어 고유다

README가 꼽는 한국어 AI 흔적이다.

```
번역투
과도한 영어 인용
기계적 병렬 ("첫째 · 둘째 · 셋째")
AI 특유 관용구 ("결론적으로", "시사하는 바가 크다")
피동태 남용
문두 접속사 남발
이모지, 불릿 남용
```

`blader/humanizer`의 영어 목록과 비교하면 겹침과 차이가 보인다.

| 패턴 | 영어 | 한국어 |
|---|---|---|
| 억지 삼단 나열 | `forced triads` | 기계적 병렬 |
| 상투적 마무리 | `one-line closers` | "결론적으로", "시사하는 바가 크다" |
| 대구 구조 | `not-X-but-Y contrasts` | — |
| **번역투** | **없음** | **있음** |
| **피동태 남용** | **없음** | **있음** |
| 엠 대시 남용 | `dashes everywhere` | 없음 |
| 과장된 주장 | `inflated claims` | — |

**번역투는 영어 목록에 있을 수 없다.** 영어 원문에 번역투가 생기지 않는다. 한국어 AI 글에서는 "~에 대한 이해를 높이다", "~라고 할 수 있다" 같은 번역체 명사구가 주된 흔적이다.

반대로 엠 대시 남용은 한국어에서 문제가 안 된다. 한국어 글에 엠 대시를 쓰는 관습이 약하다.

**그래서 번역으로 해결되지 않는다.** 공통 패턴 일부 + 언어별 고유 패턴이고, 고유 패턴 때문에 각 언어에서 다시 만들어야 한다([7.5](../part7/05-regional.md)).

### 심각도 등급이 과잉 교정을 막는다

S1 / S2 / S3로 분류한다.

이것이 교정 스킬에서 중요한 장치다. 패턴에 걸린다고 다 고치면 멀쩡한 글이 망가진다. 등급이 있으면 **어디까지 고칠지 사용자가 정할 수 있다.**

`DietrichGebert/ponytail`이 `lite / full / ultra` 강도를 둔 것과 같은 설계다([7.3](../part7/03-single-purpose.md)). 둘 다 **스킬의 세기를 조절 가능하게 만들었다.**

이 책 [3.3](../part3/03-body.md)에서 "두 방향 실패의 비용을 비교해 적는다"고 한 것의 다른 해법이다. 비용 비교를 글로 적는 대신 등급을 노출해서 사용자가 고르게 한다.

### 검증 대기 패턴을 따로 센다

README가 "(+검증 대기 hold 1건 포함)"이라고 적는다.

**패턴 하나를 검증되지 않은 상태로 분리해 센다.** 85개 중 1개가 아직 확인 안 됐다는 사실을 공개한다.

이 책이 `[확인 필요: ...]`로 남기는 규율과 같은 것이다([0.1](../part0/01-this-repository.md)). 확인 못 한 것을 확인한 것처럼 섞지 않는다. 수집 데이터에서 이런 구분을 명시한 저장소를 다른 데서 보지 못했다.

### 스킬을 역할로 쪼갰다

```
skills/humanize/            범용
skills/humanize-korean/     한국어 특화
skills/humanize-scan/       탐지만
skills/humanize-redo/       다시 하기
extras/skills/commit-ko/    한국어 커밋 메시지
```

`humanize-scan`이 별도인 것이 핵심이다. **탐지와 교정을 분리했다.** 사용자가 "어디가 문제인지만 알려 줘"라고 할 때와 "고쳐 줘"라고 할 때는 다른 요청이다.

`blader/humanizer`는 파일 하나다. 탐지만 원하는 사용자가 고쳐진 글을 받는다.

### 도구별 경로가 다르다는 것을 밝혔다

README가 이렇게 적는다.

> Copilot은 **단일 호출 경로만** 제공하며 Claude Code 전용 진단, finalize 다중 호출 경로는 실행하지 않습니다.

**도구마다 기능이 다르다는 사실을 문서화했다.** 다중 하네스를 지원하는 저장소 다수가 "여러 도구에서 됩니다"라고만 적는다. 실제로는 도구마다 지원 범위가 다르고, 그걸 안 적으면 사용자가 기능이 고장 났다고 판단한다.

규격의 `compatibility` 필드가 이 정보를 담는 자리인데([1.2](../part1/02-anatomy.md)), 여기서는 README에 적었다. 도구별 차이는 한 필드에 담기 어렵다.

### 버전을 관리한다

v2.3.2다. 플러그인 마켓플레이스로 설치, 업데이트, 제거가 된다.

```bash
copilot plugin install humanize-korean@im-not-ai
copilot plugin update humanize-korean@im-not-ai
copilot plugin uninstall humanize-korean@im-not-ai
```

**제거 경로가 명시돼 있다.** `uninstall.sh`도 저장소에 있다([7.5](../part7/05-regional.md)). 스킬이 여러 디렉터리에 복사되는 구조에서 남은 파일은 트리거 충돌을 일으킨다.

### 설계가 더 정교한데 스타는 11%다

`blader/humanizer`(53,730)의 11%다.

| | `blader/humanizer` | `epoko77-ai/im-not-ai` |
|---|---|---|
| 스킬 분리 | 없음 (1개 파일) | 역할별 4개 |
| 점진적 공개 | 없음 (397줄 32KB 단일) | 범용/언어 특화 분리 |
| 강도 조절 | 없음 | S1/S2/S3 |
| 미검증 항목 표시 | 없음 | 있음 |
| 버전 관리 | — | v2.3.2 |
| 제거 경로 | — | 있음 |
| 지원 도구 | — | 4개 |
| 스타 | **53,730** | 5,835 |

**스타수는 품질이 아니라 대상 인구를 따라간다.** 깃허브에서 한국어로 글 쓰는 사용자가 영어로 쓰는 사용자보다 적다([0.2](../part0/02-why-stars.md)).

## 공식 번들의 글쓰기 스킬 — 대조군

`anthropics/skills`의 세 스킬이 다른 접근을 보여 준다([6.1](../part6/01-anthropic-skills.md)).

| 스킬 | SKILL.md | 번들 배수 | 성격 |
|---|---|---|---|
| `doc-coauthoring` | 15,815 B | **1.0×** | 문서 공동 작성 |
| `internal-comms` | 1,511 B (32줄) | 14.8× | 내부 커뮤니케이션 |
| `brand-guidelines` | 2,235 B (73줄) | 6.1× | 브랜드 규정 |

`doc-coauthoring`이 유일하게 번들이 없다. 15,815바이트를 한 파일에 둔다. **교정, 작성 스킬은 나눌 것이 적다**는 신호로 읽힌다 — 문장을 훑으면서 여러 기준을 동시에 보는 작업이라 조건부 분리가 맞지 않을 수 있다.

`blader/humanizer`가 397줄 32KB를 한 파일에 둔 것도 같은 이유일 수 있다. 반면 `im-not-ai`는 범용/언어 특화로 나눴다. **어느 쪽이 맞는지는 측정해야 알 수 있고, 세 저장소 다 측정이 없다.**

`internal-comms`가 32줄로 공식 스킬 중 가장 짧다. `brand-guidelines`는 73줄이다. 둘 다 지식형이다 — 조직의 커뮤니케이션 관례와 브랜드 규정은 에이전트가 알 방법이 없다. **짧아도 되는 이유가 분명하다.** 조직 고유 사실만 담으면 되고, 글쓰기 일반론은 담을 필요가 없다.

## 도메인 요약

### 강점

**금지선 설계가 모범적이다.** 세 언어 저장소가 독립적으로 "내용을 바꾸지 않는다"를 제약으로 둔다. 주관적 영역에서 검증 가능한 어서션이 되는 형태다.

**강도 조절이라는 해법이 나왔다.** `im-not-ai`의 S1/S2/S3, `ponytail`의 lite/full/ultra가 과잉 교정 문제를 사용자 선택으로 돌렸다.

**미검증 항목을 분리해 센 사례가 있다.** `im-not-ai`가 85개 중 1개를 검증 대기로 공개한다. 생태계에서 드문 규율이다.

**범위를 좁혀 측정 가능하게 만든 사례가 있다.** `brag`가 출력물의 용도를 고정했다.

### 한계

**평가가 없다.** 세 교정 저장소 다 기준선 비교가 없다. 금지선 어서션은 만들기 쉬운데도 없다 — "원문의 사실이 바뀌지 않았다"는 기계로도 상당 부분 확인된다.

**점진적 공개를 쓸지가 미해결이다.** `humanizer`와 `doc-coauthoring`은 단일 파일, `im-not-ai`는 분리다. 어느 쪽이 맞는지 측정한 저장소가 없다.

**언어별 재구현이 계속 필요하다.** 번역으로 해결되지 않으므로 언어마다 누가 만들어야 한다. 수집 데이터에 영어, 한국어, 중국어만 있다.

**대상 인구가 스타수를 정한다.** 설계 수준과 주목이 반비례하는 구간이 이 도메인에 선명하다.

### 골라 쓰는 기준

| 상황 | 추천 |
|---|---|
| 영어 글의 AI 티 제거 | `blader/humanizer` |
| 한국어 글의 AI 티 제거 | `epoko77-ai/im-not-ai` (탐지만 원하면 `humanize-scan`) |
| 중국어 글 | `KKKKhazix/human-writing` |

| 조직 브랜드 규정 적용 | `brand-guidelines`를 참고해 **직접 만든다** (조직 고유 사실이 본체) |

`brand-guidelines`를 직접 만들라고 적은 이유가 있다. 지식형 스킬이고 내용이 **조직 고유 사실**이다. 남의 브랜드 규정을 가져다 쓸 수 없다. 공식 스킬은 73줄짜리 틀을 보여 주는 참고 자료로 쓰는 것이 맞다.
