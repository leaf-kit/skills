# 부록 C. 용어집

본문에서 쓴 용어를 정리한다. 검색이 안 되는 번역은 하지 않고 원문을 함께 적는다.

## 규격 용어

### 스킬 (Agent Skill)

`SKILL.md` 파일 하나를 포함하는 디렉터리. 에이전트가 필요하다고 판단할 때 읽는 지시문이다. 규격은 [agentskills.io/specification](https://agentskills.io/specification)에 있다. → [1.2](../part1/02-anatomy.md)

### SKILL.md

스킬의 필수 파일. YAML 프런트매터 + 마크다운 본문으로 된다. 본문에는 형식 제약이 없다. → [1.2](../part1/02-anatomy.md)

### 프런트매터 필드

| 필드 | 필수 | 제약 |
|---|---|---|
| `name` | ○ | 1–64자, 소문자, 숫자, 하이픈, **부모 디렉터리 이름과 일치** |
| `description` | ○ | 1–1024자 |
| `license` | | 라이선스 이름 또는 번들 파일 참조 |
| `compatibility` | | 1–500자, 환경 요구사항 |
| `metadata` | | 문자열 키-값 맵 |
| `allowed-tools` | | 사전 승인 도구. **실험적** |

### 점진적 공개 (progressive disclosure)

전부 미리 읽지 않고 필요해진 만큼만 읽는 3단 구조.

| 단계 | 읽히는 것 | 권장 크기 | 시점 |
|---|---|---|---|
| 1 | `name`, `description` | 약 100 토큰 | 시작할 때, **모든 스킬** |
| 2 | `SKILL.md` 본문 | 5,000 토큰 이하 | 그 스킬이 활성화됐을 때 |
| 3 | `scripts/`, `references/`, `assets/` | 제한 없음 | 본문이 읽으라고 했을 때 |

→ [1.3](../part1/03-progressive-disclosure.md)

### 번들 (bundle)

스킬 디렉터리의 선택 파일들. `scripts/`(실행 코드), `references/`(조건부로 읽는 문서), `assets/`(출력물 재료)로 나뉜다.

구분 기준: **읽어서 이해하면 `references/`, 출력물에 넣으면 `assets/`, 실행만 하면 `scripts/`.** → [3.6](../part3/06-assets.md)

## 이 책이 쓰는 분류

### 세 유형

| 유형 | 주는 것 | 본체 위치 | 평가 | 수명 |
|---|---|---|---|---|
| **실행형** | 수단과 고정된 실행 경로 | `scripts/` | 객관적 | 중간 |
| **지식형** | 모르는 사실 | `references/` | 사실 정확성 | **짧다** |
| **방법론형** | 일하는 순서와 판단 기준 | 본문 | 주관적 | 길다 |

→ [4.2](../part4/02-three-types.md)

### 세 규모

| 규모 | `SKILL.md` | 스타수의 의미 |
|---|---|---|
| 단일 스킬 | 1개 | **그 스킬에 대한 평가** |
| 번들 | 2~100개 | 번들 안 어딘가에 대한 평가 |
| 마켓플레이스 | 100개 초과 | **수집 행위에 대한 평가** |

→ [4.3](../part4/03-scale.md)

### 메타스킬

스킬을 대상으로 하는 스킬. 네 갈래로 나뉜다 — 만들기, 최적화, 변환, 측정. → [4.4](../part4/04-meta-skills.md)

### 트랙 A / 트랙 B

이 책의 선별 범주.

| 트랙 | 조건 |
|---|---|
| A | `SKILL.md` ≥ 1 **그리고** 스킬이 주된 산출물 |
| B | 스킬을 담지 않지만 스킬 생태계를 대상으로 함 (큐레이션, 규격, 도구) |
| 제외 | 사람의 역량을 뜻하는 "skill", 스킬을 부속품으로 곁들인 제품 |

판정 질문: **"이 저장소에서 스킬을 다 빼면 남는 게 있는가."** → [5.1](../part5/01-collection.md)

### 정밀 리뷰 / 요약 리뷰

| 표시 | 뜻 |
|---|---|
| 정밀 리뷰 | `README`와 실제 `SKILL.md`를 열어 보고 썼다 |
| 요약 리뷰 | 저장소 설명과 메타데이터만 보고 썼다 |

메타데이터에 폐기 사실이 없으므로 이 구분이 필요하다. → [0.3](../part0/03-how-to-read.md)

## 확장 수단

### 스킬 / 서브에이전트 / MCP / 플러그인 / 훅

| 수단 | 실체 | 작동 시점 | 늘리는 것 |
|---|---|---|---|
| 스킬 | `SKILL.md` + 번들 | 에이전트가 필요하다고 판단할 때 | 지식과 절차 |
| 서브에이전트 | 별도 컨텍스트의 에이전트 | 위임할 때 | 컨텍스트 분리 |
| MCP 서버 | 도구를 제공하는 프로세스 | 그 도구를 호출할 때 | **할 수 있는 일** |
| 플러그인 | 위 요소들의 배포 단위 | 설치돼 있으면 상시 | 배포와 설치 |
| **훅** | 특정 시점의 실행 명령 | **항상** | **강제성** |

고르는 순서: 안 돌면 사고가 나면 **훅** → 외부 접근이 필요하면 **MCP** → 과정이 길고 결과만 필요하면 **서브에이전트** → 방법을 몰라서 못 하면 **스킬** → 여러 개를 함께 배포하면 **플러그인**. → [1.4](../part1/04-boundaries.md)

### MCP (Model Context Protocol)

에이전트에게 도구를 제공하는 프로토콜. 스킬과 대립하지 않는다 — 공식 저장소에 `mcp-builder` 스킬이 있다. → [1.4](../part1/04-boundaries.md)

## 트리거

### 트리거 (trigger)

에이전트가 스킬을 읽기로 결정하는 일. **판단 근거는 `description`뿐이다.** 본문은 선택된 뒤에 읽히므로 본문에 적은 트리거 조건은 효과가 없다. → [1.5](../part1/05-triggering.md)

### 과소 트리거 (undertriggering)

불려야 할 때 안 불리는 것. 에이전트는 스스로 처리할 수 있다고 판단하면 스킬을 건너뛴다. **이것이 기본값이다.**

### 과잉 트리거 (overtriggering)

불리면 안 될 때 불리는 것. 과소보다 눈에 덜 띄어서 더 오래 방치된다 — 안 불리는 건 "왜 안 되지?"로 드러나고, 잘못 불리는 건 "결과가 좀 이상한데"로 흐려진다.

균형점: **넓은 키워드 + 명시적 제외 조건.**

### 트리거 악용 (trigger abuse)

`description`을 조작해 의도하지 않은 상황에 스킬이 불리게 만드는 공격. `NVIDIA/SkillSpector`의 탐지 범주 중 하나다. **정당한 설계와 같은 기법을 쓴다.** → [9.3](../part9/03-supply-chain.md)

## 평가

### 어서션 (assertion)

결과가 만족해야 할 검증 가능한 조건. 제3자가 결과를 보고 합격, 불합격을 판정할 수 있어야 한다. → [3.7](../part3/07-evals.md)

### 기준선 (baseline)

스킬 없이 같은 요청을 돌린 결과. **기준선 없는 평가는 평가가 아니다.**

기존 스킬을 개선하는 경우에는 고치기 전 버전이 기준선이고, 고치기 전에 스냅샷을 떠야 한다.

### 조악한 대조군

일부러 조악하게 만든 스킬을 세 번째 팔로 두는 것. `DietrichGebert/ponytail`의 `caveman.js`가 사례다.

기준선 하나만 두면 "스킬이 좋아서 나아진 것인가, 아무 스킬이나 붙여도 달라지는 것인가"를 구분할 수 없다. → [7.3](../part7/03-single-purpose.md)

### 변별력

어서션이 스킬의 가치를 구분하는 능력. 양쪽(스킬, 기준선)이 다 통과하면 변별력이 없다.

| 상황 | 뜻 |
|---|---|
| 스킬만 통과 | 변별력 있음 |
| 양쪽 다 통과 | **변별력 없음** |
| 양쪽 다 실패 | 어서션이 틀렸거나 너무 어렵다 |
| **기준선만 통과** | **스킬이 해를 끼친다** |

→ [3.7](../part3/07-evals.md)

### 부정형 어서션의 함정

"~하지 않았다" 형태의 어서션만 쓰면 **아무것도 하지 않은 답변이 만점을 받는다.** 양성 어서션을 섞어야 한다. → [10.2](../part10/02-validation.md)

### 검정력 부족 (underpowered)

서로 다른 자극이 5개 미만이면 부호 검정이 어떤 효과 크기에서도 p ≤ 0.05에 도달할 수 없다. 그 경우 결과를 합격도 실패도 아닌 **제3의 상태**로 분류한다.

**반복 실행은 신뢰도를 재고 독립 표본을 늘리지 않는다.** `dotnet/skills`가 이 기준을 CI로 강제한다. → [6.5](../part6/05-microsoft.md)

### 라우팅 평가

스킬 여러 개의 `description`이 서로 충돌하는지 재는 것. 어간 추출 TF-IDF로 근사하면 **결정적이고 공짜다.**

음성 케이스에 `owner` 필드로 어느 형제 스킬이 처리해야 하는지 명시한다. `addyosmani/agent-skills`가 CI에서 돌린다. → [7.2](../part7/02-addyosmani.md)

### 다섯 축

이 책이 정리한 평가 축.

| 축 | 재는 것 | 비용 |
|---|---|---|
| A. 라우팅 | 불려야 할 때 불리는가 | 0 |
| B. 기여 | 없을 때보다 나은가 | **높음** |
| C. 평가 신뢰도 | 이 측정을 믿을 수 있는가 | 0 |
| D. 형식 | 규격을 지켰는가 | 0 |
| E. 안전 | 악성, 취약 패턴이 있는가 | 낮음 |

**다섯 축을 다 갖춘 저장소가 수집 데이터에 없다.** → [9.2](../part9/02-measuring-quality.md)

## 생태계

### 슬롭 (slop)

틀리지 않았는데 밋밋한 산출물. 아무도 원하지 않았는데 그럴듯한 모양으로 쏟아진 것.

글쓰기 도메인에서 나온 말인데 디자인 도메인에서도 쓰인다 — `cathrynlavery/diagram-design`이 "Mermaid 슬롭 없음"을, `Leonxlnx/taste-skill`이 "지루하고 일반적인 슬롭을 멈춘다"를 설명에 적는다. → [8.5](../part8/05-writing.md), [8.7](../part8/07-design.md)

### 디스커버리 (discovery)

"example.com은 어떤 스킬을 공개하는가"에 답하는 문제. **표준이 없고 네 가지 접근이 각자 돌아간다.**

| 접근 | 주체 | 무결성 |
|---|---|---|
| 설치 스킬 (`skill-installer`) | OpenAI | 없음 |
| 인덱스 파일 (`index.json`) | Google | 없음 |
| `.well-known` + 검증 절 | Cloudflare | 규격에 있음 (**Draft**) |
| 스캔 + 서명 + 카탈로그 | NVIDIA | **구현** |

→ [6.6](../part6/06-cloudflare.md)

### 메모리 오염 (memory poisoning)

조작된 내용이 에이전트 메모리에 저장되어 이후 모든 세션에서 사실로 취급되는 것. **원본을 지워도 메모리에는 남는다** — 메모리는 출처에서 분리된다. → [8.4](../part8/04-memory.md)

### 포화

보편적 결핍 + 한 문장 설명 + 즉시 확인 가능의 조합이 선점된 상태. 남은 자리는 좁은 도메인과 언어, 지역이고 둘 다 스타수 상한이 낮다. → [9.5](../part9/05-saturation.md)

### 낭비성 중복 / 필요한 재구현

| 종류 | 조건 | 사례 |
|---|---|---|
| 낭비 | 같은 문제, 같은 조건 | 메모리 저장소 7개 |
| **재구현** | 같은 문제, **다른 조건** | AI 글 교정 3개 언어 |
| 탐색 | 같은 문제, 다른 설계 | 코드리뷰 분할 축 5가지 |

→ [9.5](../part9/05-saturation.md)
