# 3.5 scripts 설계

`scripts/`는 스킬에서 가장 저평가된 디렉터리다. 지시문만으로 스킬을 만들 수 있으니 스크립트를 안 쓰고 넘어가기 쉽다. 그런데 스크립트가 해결하는 문제는 다른 방법으로 해결되지 않는다.

## 스크립트가 해결하는 것

### 1. 실행이 매번 달라지는 문제

같은 절차를 말로 설명하면 매번 다르게 실행된다. 재현성이 깎인다([2.1](../part2/01-criteria.md)).

PDF 양식의 필드 좌표를 확인하는 작업을 생각해 보자. 말로 설명하면 이렇게 된다.

```markdown
PDF를 이미지로 변환해서 각 필드의 위치를 확인한다. pdf2image나
pypdf를 쓸 수 있다. 좌표계가 좌하단 기준인 점에 주의한다.
해상도는 필드가 구분될 만큼 올린다...
```

읽은 쪽이 매번 코드를 새로 쓴다. 쓸 때마다 라이브러리 선택이 다르고, 해상도가 다르고, 좌표 변환 실수가 섞인다.

스크립트로 내리면 호출 한 줄이다.

```
scripts/check_bounding_boxes.py
```

실행 경로가 고정된다. **같은 입력에 같은 출력이 나온다.**

### 2. 비용 문제

스크립트는 읽히지 않고 **실행**될 수 있다. 내용이 컨텍스트에 전혀 안 들어올 수도 있다. 같은 절차를 참조 문서로 두면 읽을 때마다 토큰을 쓴다.

### 3. 검증 가능성

스크립트는 종료 코드와 출력을 낸다. 성공, 실패가 명확하다. 지시문으로 같은 일을 하면 "제대로 했는지"를 판정할 근거가 출력물뿐이다.

## 언제 내리나 — 중복 발견 신호

스크립트를 만들 시점을 판단하는 가장 좋은 방법은 **테스트 실행 기록을 읽는 것**이다.

스킬을 평가하면서 여러 테스트 케이스를 돌리면, 실행 과정이 남는다. 그 기록에서 이걸 찾는다.

> 테스트 케이스들이 **각자 독립적으로 비슷한 헬퍼 코드를 썼는가.**

세 케이스 모두 `create_docx.py` 같은 파일을 만들었다면, 그건 스킬이 그 스크립트를 번들해야 한다는 강한 신호다. 한 번 써서 `scripts/`에 넣고 쓰라고 지시하면, 앞으로 모든 실행이 바퀴를 다시 발명하지 않는다.

이 신호는 설계 단계에서는 안 보인다. 실행해 봐야 보인다. 그래서 스크립트 설계는 보통 **두 번째 이터레이션**의 일이다([3.8](08-iterate-and-ship.md)).

## 판단 기준 네 가지

| 질문 | 예 → 스크립트 | 아니오 → 지시문 |
|---|---|---|
| 입력과 출력이 정해져 있나 | 파일 변환, 좌표 추출 | 글의 톤 판단 |
| 매번 같은 결과가 나와야 하나 | 검증, 집계 | 창작, 구성 |
| 절차가 10줄 넘게 설명되나 | 다단계 파이프라인 | 한 줄 규칙 |
| 사람이 결과를 눈으로 확인하나 | 아니오면 스크립트에 적합 | 예면 지시문 가능 |

핵심은 첫 번째다. **입력과 출력이 정해지면 코드로 쓸 수 있다.** 정해지지 않으면 코드가 아니라 판단이다.

## 공식 pdf 스킬의 스크립트 구성

실제 사례를 보는 것이 가장 빠르다.

```
skills/pdf/scripts/
├── check_bounding_boxes.py
├── check_fillable_fields.py
├── convert_pdf_to_images.py
├── create_validation_image.py
├── extract_form_field_info.py
├── extract_form_structure.py
├── fill_fillable_fields.py
└── fill_pdf_form_with_annotations.py
```

여덟 개를 보면 설계 원칙이 읽힌다.

**이름이 동작을 말한다.** `check_`, `convert_`, `extract_`, `fill_`, `create_`로 시작한다. 본문에서 호출할 때 무엇을 하는 스크립트인지 이름만으로 안다. 스크립트를 읽지 않아도 쓸 수 있다는 뜻이고, 그게 비용 절감의 핵심이다.

**검사와 실행이 분리돼 있다.** `check_fillable_fields.py`로 먼저 확인하고, 결과에 따라 `fill_fillable_fields.py`(채울 수 있는 양식)나 `fill_pdf_form_with_annotations.py`(채울 수 없는 양식)로 간다. 분기 판단은 지시문이 하고, 각 경로의 실행은 스크립트가 한다.

**검증 스크립트가 따로 있다.** `create_validation_image.py`는 결과를 사람이 확인할 수 있게 만든다. 스크립트가 실행만 하고 끝나지 않고, 제대로 됐는지 보여 주는 단계까지 번들에 있다.

## 스크립트 작성 요건

규격이 세 가지를 요구한다.

> 스크립트는 자체 완결적이거나 의존성을 명확히 문서화해야 한다. 쓸모 있는 오류 메시지를 포함해야 한다. 예외 상황을 무너지지 않고 처리해야 한다.

### 의존성을 명시한다

스크립트가 외부 패키지를 쓰면 어디서든 알 수 있게 적는다. 두 곳에 적는다.

```yaml
# SKILL.md 프런트매터
compatibility: Requires Python 3.14+ and uv
```

```python
# scripts/extract.py 머리
"""PDF 양식 필드 정보를 추출한다.

의존성: pypdf >= 4.0
사용법: python extract_form_field_info.py <pdf 경로>
출력: JSON (stdout)
"""
```

설치한 사람이 왜 안 되는지 알 수 있어야 한다. 의존성이 없을 때 조용히 실패하는 스크립트가 최악이다.

### 오류 메시지가 다음 행동을 알려 준다

에이전트가 읽을 오류 메시지는 사람이 읽을 것과 요건이 다르다. **무엇이 틀렸는지가 아니라 무엇을 하면 되는지를 적는다.**

```python
# 나쁨
raise ValueError("Invalid PDF")

# 좋음
raise ValueError(
    f"{path}에 채울 수 있는 양식 필드가 없습니다. "
    f"스캔된 PDF일 수 있습니다. "
    f"fill_pdf_form_with_annotations.py를 쓰세요."
)
```

아래쪽은 오류 메시지가 다음 스크립트를 가리킨다. 에이전트가 읽고 바로 다음 단계로 간다. 위쪽은 에이전트가 직접 추론해야 하고, 추론이 틀릴 수 있다.

### 출력을 기계가 읽을 수 있게 낸다

스크립트 출력은 에이전트가 읽는다. 사람이 읽기 좋은 포맷보다 **파싱 가능한 포맷**이 낫다.

```
# 사람용
총 12개 필드를 찾았습니다. 그중 3개는 비어 있습니다.

# 에이전트용
{"total": 12, "empty": 3, "fields": [{"name": "...", "filled": false}]}
```

JSON이면 에이전트가 특정 값만 꺼내 쓸 수 있다. 산문이면 전체를 읽고 해석해야 한다.

### 부분 실패를 구분한다

파일 열 개를 처리하는 스크립트에서 세 개가 실패했을 때, 전체 실패로 끝내면 성공한 일곱 개가 버려진다.

```python
{
  "succeeded": ["a.pdf", "b.pdf"],
  "failed": [{"file": "c.pdf", "reason": "암호로 보호됨"}]
}
```

에이전트가 실패한 것만 다르게 처리할 수 있다.

## 본문에서 스크립트를 가리키는 법

스크립트를 만들어도 본문이 안 가리키면 안 쓰인다. 세 가지를 적는다.

```markdown
## 양식 채우기

1. `scripts/check_fillable_fields.py <pdf>`로 채울 수 있는 필드가
   있는지 확인한다.
2. 필드가 있으면 `scripts/fill_fillable_fields.py`를 쓴다.
3. 필드가 없으면 (스캔 PDF 등) `scripts/fill_pdf_form_with_annotations.py`
   를 쓴다. 이 경로는 좌표가 필요하므로 먼저
   `scripts/check_bounding_boxes.py`로 좌표를 확인한다.
4. 채운 뒤 `scripts/create_validation_image.py`로 결과를 이미지로
   만들어 확인한다.
```

- **언제 쓰나** — 단계와 조건
- **어떻게 부르나** — 인자 형태
- **다음에 무엇을 하나** — 결과에 따른 분기

이게 없으면 에이전트가 스크립트를 열어 읽고 스스로 판단한다. 읽으면 비용이 발생하고, 판단하면 매번 달라진다. 스크립트를 만든 효과가 사라진다.

## 스크립트를 쓰지 말아야 할 때

**한 번만 쓰는 변환.** 스크립트 작성, 유지 비용이 그 한 번보다 크다.

**판단이 들어가는 일.** "이 문장이 슬롭인가"를 코드로 쓰려 하면 키워드 매칭이 되고, 키워드 매칭은 문체 판단을 못 한다. 판단은 지시문에 남긴다.

**외부 상태에 의존하는 일.** API 호출이나 인증이 필요하면 MCP 서버 쪽을 본다. 스크립트로도 되지만 인증과 권한 관리를 스킬이 떠안게 된다([1.4](../part1/04-boundaries.md)). 그리고 남이 설치할 때 공급망 위험이 커진다 — 마크다운만 든 스킬과 네트워크를 쓰는 스크립트가 든 스킬은 검증 비용이 다르다([9.3](../part9/03-supply-chain.md)).

**환경에 따라 다르게 동작하는 일.** 스크립트가 특정 OS나 특정 버전에서만 되면, 다른 환경의 사용자에게는 스킬 전체가 망가진 것으로 보인다. 이럴 때는 `compatibility`에 명시하고, 가능하면 실패 시 지시문 경로로 되돌아갈 길을 본문에 적어 둔다.
