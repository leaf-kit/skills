# 3.1 의도 포착

스킬을 만들기 시작할 때 가장 흔한 실패는 코드를 잘못 쓰는 것이 아니다. **무엇을 만들어야 하는지 모르는 채로 쓰기 시작하는 것**이다.

"코드 리뷰 스킬을 만들자"는 아직 설계가 아니다. 리뷰에서 무엇을 보는지, 언제 불려야 하는지, 출력이 어떤 모양인지가 비어 있다. 이 상태로 쓰면 500줄짜리 일반론이 나온다.

이 장은 쓰기 전에 답해야 할 질문을 정리한다.

## 질문 4개

### 1. 이 스킬이 가능하게 하는 일이 무엇인가

"무엇을 하는 스킬인가"보다 "**이게 없으면 무엇이 안 되는가**"로 묻는 쪽이 낫다. 결핍에서 출발하면 범위가 좁혀진다.

```
약한 답: 코드를 리뷰한다
나은 답: 우리 팀 컨벤션을 모르는 사람이 올린 PR에서
        컨벤션 위반을 찾아낸다
```

아래쪽에는 대상(PR), 기준(우리 팀 컨벤션), 산출물(위반 목록)이 들어 있다. 위쪽에는 아무것도 없다.

이 답이 안 나오면 [1.4](../part1/04-boundaries.md)로 돌아가 스킬이 맞는지부터 확인한다. 결핍이 "방법을 모른다"가 아니라 "수단이 없다"면 스킬이 아니다.

### 2. 언제 트리거돼야 하는가

사용자가 **실제로 쓸 말**을 모은다. 내가 쓰는 말이 아니다.

여기서 나오는 목록이 `description`의 재료가 된다. 세 종류를 모은다.

| 종류 | 예 |
|---|---|
| 직접적인 표현 | "코드 리뷰해 줘", "PR 봐 줘" |
| 간접적인 표현 | "이거 머지해도 되나", "뭐 빠진 거 없나" |
| 걸리면 안 되는 표현 | "이 함수 뭐 하는 거야" (설명 요청) |

세 번째가 중요하다. 제외 조건을 지금 모아 두지 않으면 나중에 과잉 트리거를 발견하고 역추적해야 한다.

### 3. 출력이 어떤 모양인가

이 질문에 답하면 스킬의 절반이 나온다. 출력 형식을 정하면 본문이 그 형식을 만드는 절차로 자동으로 정리된다.

구체적으로 적는다.

```
① 위반 목록 — 파일:줄 / 어긴 규칙 / 고친 코드
② 전체 수정 패치
③ 확인이 필요한 항목 (판단이 애매해서 사람이 봐야 할 것)
```

"리뷰 결과를 보여 준다"로 끝내면 매번 다른 모양이 나온다([2.4](../part2/04-output-format.md)).

### 4. 테스트 케이스를 만들 것인가

만들 수 있는 스킬과 만들기 어려운 스킬이 갈린다.

| 테스트가 쉬운 스킬 | 테스트가 어려운 스킬 |
|---|---|
| 파일 변환, 데이터 추출 | 글쓰기 문체 |
| 코드 생성, 형식 검증 | 디자인 품질 |
| 정해진 절차의 수행 | 아이디어 발상 |

왼쪽은 결과가 객관적으로 검증된다. 오른쪽은 사람 판단이 필요하다.

오른쪽이라고 테스트를 포기하지는 않는다. **다만 어서션을 억지로 붙이지 않는다.** 주관적인 출력에 객관적 어서션을 붙이면 "글자 수가 500자 이상인가" 같은 무의미한 항목이 생기고, 그게 통과해도 아무것도 알 수 없다.

주관적 스킬에서는 어서션을 다르게 설계한다. 품질을 재는 대신 **지켜야 할 금지선**을 잰다.

```
# 무의미한 어서션 (주관적 품질을 객관적으로 재려는 시도)
"글이 자연스럽다"
"문장이 매끄럽다"

# 쓸모 있는 어서션 (금지선 위반을 잰다)
"원문에 없던 숫자, 통계, 인용을 새로 만들어 넣지 않았다"
"사용자의 구어체 말투를 격식체로 통일하지 않았다"
"수정 제안이 5건 이하다"
```

아래쪽은 객관적으로 판정되고, 통과 여부가 실제 품질과 연결된다. 자세한 설계는 [3.7](07-evals.md)에서 다룬다.

## 이미 있는 대화에서 뽑아내기

가장 좋은 재료는 **이미 한 작업의 기록**이다. "이걸 스킬로 만들자"는 생각은 대개 어떤 작업을 하고 난 뒤에 든다. 그 작업의 대화에 답이 다 있다.

뽑아낼 것은 네 가지다.

1. **쓴 도구와 순서** — 무엇을 먼저 읽고 무엇을 나중에 했나
2. **사용자가 고친 것** — 내가 틀린 방향으로 갔고 사용자가 돌려세운 지점. 여기가 스킬에 반드시 들어갈 지시다
3. **입출력 형식** — 실제로 주고받은 모양
4. **막힌 지점** — 중간에 헤맨 부분. 참조 자료나 스크립트가 필요한 자리

2번이 가장 값이 나간다. 사용자가 고쳐 준 지점은 "기본 동작이 틀린 지점"이고, 스킬의 존재 이유가 보통 거기에 있다. 반대로 사용자가 아무 말 없이 지나간 부분은 기본 동작으로 충분한 부분이고, 스킬에 적을 필요가 없다.

## 범위를 좁히는 압박

의도를 정리하다 보면 범위가 자란다. "리뷰 스킬이면 보안도 보고 성능도 보고 테스트 커버리지도 보면 좋겠다."

자라는 것을 막는 방법이 있다. **한 문장으로 쓴 다음 접속사를 세는 것**이다.

```
# 접속사 3개 — 스킬 3개다
컨벤션 위반을 찾고, 보안 취약점을 점검하고, 테스트가
빠진 곳을 알려 준다

# 접속사 0개 — 스킬 1개다
우리 팀 컨벤션을 모르는 사람이 올린 PR에서 컨벤션 위반을 찾아낸다
```

"그리고"와 "또는"이 들어가면 쪼갤 신호다. 쪼개는 비용도 있지만([2.6](../part2/06-promotion.md)), 처음부터 셋을 합치는 비용이 더 크다. 셋을 합친 스킬은 세 영역 모두에서 얕아지고, `description`이 범위를 못 잡아 트리거가 흔들린다.

## 모르는 것은 묻는다

의도 포착을 혼자 끝낼 수 없는 경우가 있다. 특히 네 가지는 추측하면 거의 틀린다.

- **기준** — 우리 팀 컨벤션이 무엇인가. 문서가 있나
- **예외** — 적용하지 않을 상황이 있나
- **판단이 갈리는 지점** — 애매할 때 어느 쪽으로 기울어야 하나
- **성공 기준** — 어떤 결과를 받으면 만족인가

추측해서 채우면 그럴듯한 일반론이 나온다. 그 일반론은 어느 팀에서도 쓸 수 있고 어느 팀에서도 쓸모가 없다.

묻는 방식에 요령이 있다. **열어 두고 묻지 않는다.**

```
# 답하기 어려운 질문
팀 컨벤션이 어떻게 되나요?

# 답하기 쉬운 질문
최근에 PR에서 지적한 것 중에 반복되는 게 있나요? 세 개면 충분합니다.
```

아래쪽은 기억에서 바로 꺼낼 수 있다. 그리고 "반복되는 지적 세 개"는 컨벤션 문서보다 실제 문제를 더 잘 가리킨다.

## 정리 양식

의도 포착의 결과를 이 형태로 적어 두면 바로 `SKILL.md` 초안이 된다.

```markdown
## 결핍
(이게 없으면 무엇이 안 되는가 — 한 문장, 접속사 없이)

## 트리거
걸려야 할 표현:
걸리면 안 될 표현:

## 출력
① ...
② ...
③ ...

## 판단이 갈리는 지점
- 상황: → 기울 방향:

## 테스트 가능성
객관적 / 주관적 — 주관적이면 금지선 어서션 목록:

## 확인 필요
- [확인 필요: ...]
```

마지막 항목이 비어 있지 않은 상태에서 본문을 쓰기 시작하면, 빈칸이 추측으로 채워진다. 쓰기 전에 비우는 쪽이 낫다.
