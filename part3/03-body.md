# 3.3 본문 쓰기

프런트매터 아래 본문에는 규격상 형식 제약이 없다. 권고만 있다. 500줄 이하, 5,000 토큰 이하.

제약이 없다는 게 자유롭다는 뜻은 아니다. 본문은 **그 스킬이 트리거될 때마다 전부 읽힌다.** 조건부가 아니다. 그래서 본문에 들어간 모든 줄은 비용이고, 그 비용을 정당화해야 한다.

## 본문에 들어갈 것과 안 들어갈 것

| 본문에 둔다 | 다른 데로 보낸다 |
|---|---|
| 항상 필요한 절차 | 조건부 상세 → `references/` |
| 판단 기준과 그 이유 | 반복 실행 코드 → `scripts/` |
| 출력 형식 | 출력물 재료 → `assets/` |
| 흔한 예외 처리 | 트리거 조건 → `description` |
| 참조 파일 읽기 조건 | 드문 예외 → `references/` |

마지막 행이 중요하다. 참조 파일을 만들었으면 **본문에 언제 읽는지 적어야 한다.** 그 한 줄이 없으면 참조 파일은 있으나 마나다([1.3](../part1/03-progressive-disclosure.md)).

## 명령형으로 쓴다

본문은 에이전트에게 주는 지시다. 설명문이 아니다.

```markdown
# 약함 (설명)
이 스킬은 먼저 독자를 파악하고, 그다음에 초안을 작성하며,
마지막으로 점검 과정을 거치도록 설계되어 있습니다.

# 강함 (지시)
읽을 사람 한 명과 목적을 한 줄로 적는다.
초안을 쓴다.
"지울 것 3가지"를 적용한다.
```

차이는 두 가지다. 지시형이 짧고, 수행할 동작이 분명하다. "설계되어 있습니다"는 누가 무엇을 해야 하는지 말하지 않는다.

한국어로 쓸 때는 평서체(`~한다`)가 명령형 역할을 한다. `~하세요`나 `~해야 합니다`보다 짧고, 지시의 무게가 균일하다.

## 대문자 강조에 의존하지 않는다

본문을 쓰다 보면 중요한 지시에 강조를 붙이고 싶어진다.

```markdown
NEVER fabricate statistics. ALWAYS ask the user first.
You MUST follow this exact format.
```

강조가 작동하기는 한다. 문제는 **강조가 많아지면 서로를 지운다**는 점이다. ALWAYS가 열 개면 우선순위가 다시 평평해진다. 그리고 강조는 충돌 상황에서 무엇을 포기할지 알려 주지 않는다([2.2](../part2/02-explain-why.md)).

대안은 이유를 적는 것이다.

```markdown
# 강조형
NEVER fabricate statistics.

# 이유형
없는 통계를 만들어 넣지 않는다. 구체적인 거짓은 밋밋한 사실보다
나쁘다. 사용자가 자기 이름으로 발행하면 거짓말이 된다.
```

이유형은 길지만 적용 범위가 따라온다. 통계뿐 아니라 인용, 사례, 경험에도 같은 판단이 적용된다. 강조형은 통계만 막는다.

**대문자 강조를 쓰는 자신을 발견하면 노란불로 본다.** 그 자리에 설명이 빠져 있다는 신호다. 다만 금지선이 명확하고 설명할 이유가 자명한 경우(보안, 데이터 손실)에는 강조를 써도 된다.

## 구조

본문의 순서에 정해진 규칙은 없지만, 실무에서 잘 작동하는 배치가 있다.

```markdown
# 스킬 이름

## (문제 정의 — 이 스킬이 다루는 것이 무엇인가)
한두 단락. 범위와 한계를 먼저 못 박는다.

## (모드 분기 — 작업 종류가 여러 개면)
먼저 어느 경우인지 판별하고 해당 절로 보낸다.

## (각 모드의 절차)
단계별 지시.

## (판단 기준)
애매할 때 어느 쪽으로 기울지.

## (출력 형식)
템플릿.

## (참조 파일 안내)
어느 파일을 언제 읽나.
```

### 문제 정의를 앞에 둔다

맨 앞에 범위와 한계를 적는 것이 중요하다. 에이전트가 본문을 읽기 시작할 때 "이 스킬이 무엇을 하지 않는지"를 먼저 알아야 과잉 적용을 막는다.

한계를 적은 예시다.

```markdown
슬롭을 완벽하게 없애는 방법은 없다. 이 스킬도 약속하지 않는다.
줄이는 방법만 다룬다.
```

이 두 줄이 없으면 스킬이 "완벽히 제거"를 목표로 삼고 과하게 고친다.

### 모드 분기를 일찍 한다

작업 종류가 둘 이상이면 앞에서 갈라서 해당 절로 보낸다.

```markdown
## 두 가지 모드

- **점검 모드** — 이미 쓴 글을 고쳐 달라고 한다. → "점검 모드" 절로.
- **작성 모드** — 글을 새로 써 달라고 한다. → "작성 모드" 절로.
```

분기를 늦게 하면 양쪽 절차가 섞인 지시를 다 읽게 된다.

## 과잉 적용을 막는 절

실무에서 가장 자주 빠지는 절이 있다. **하지 말아야 할 것을 적는 절**이다.

스킬은 "하라"는 지시로만 채우면 과하게 작동한다. 교정 스킬은 멀쩡한 글을 고치고, 리뷰 스킬은 문제없는 코드에서 문제를 찾아낸다. 지시를 받았으니 무언가 해야 한다고 판단하기 때문이다.

그래서 **반대 방향의 지시**를 명시한다.

```markdown
### 과하게 고치지 않는다

이 스킬의 실패 방식은 두 가지다. 슬롭을 놓치는 것, 그리고 멀쩡한
글을 고치는 것이다. 두 번째가 더 나쁘다. 사용자의 목소리를
지우기 때문이다.

고칠 게 적으면 적다고 말한다. 분량을 채우려고 억지로 찾아내지 않는다.
특히 아래는 슬롭이 아니다.

- 사용자 특유의 말투, 반복되는 입버릇
- 구체적인 장면, 대화, 숫자가 들어간 문장 (문장이 거칠어도)
- 격식체, 만연체 같은 문체 선택

판단이 애매하면 그대로 둔다. 애매한 문장 하나를 살려두는 비용이
사용자의 문장 하나를 죽이는 비용보다 작다.
```

마지막 줄이 핵심이다. **두 방향 실패의 비용 비교**를 적어 두면, 애매한 상황에서 어디로 기울지가 결정된다. 이 비교가 없으면 애매할 때마다 다르게 간다.

## 분량 관리

### 측정부터 한다

본문 길이는 감으로 판단하지 않는다. 공식 스킬들의 실제 줄 수가 참고가 된다.

| 스킬 | 줄 수 |
|---|---|
| `internal-comms` | 32 |
| `docx` | 91 |
| `mcp-builder` | 236 |
| `pdf` | 314 |
| `skill-creator` | 485 |
| `claude-api` | 603 |

(측정: `anthropics/skills` 기본 브랜치, 2026-10-04)

대부분이 100줄 아래다. **500줄은 상한이고 목표가 아니다.** `docx`는 91줄로 1.1MB 번들을 운전한다.

### 줄 수와 토큰은 다르다

`claude-api`는 603줄에 101,724바이트다. 한 줄 평균 169바이트다. `skill-creator`는 485줄에 33,168바이트로 한 줄 평균 68바이트다. **줄 수가 비슷해도 실제 크기는 3배 차이 난다.**

긴 산문을 줄바꿈 없이 쓰면 줄 수는 적고 토큰은 많다. 500줄 아래인데 비용이 크다고 느껴지면 줄 길이를 본다.

### 줄이는 순서

본문이 길어졌을 때 이 순서로 줄인다.

1. **조건부 상세를 참조 파일로 내린다** — 가장 효과가 크다
2. **반복되는 절차를 스크립트로 내린다**
3. **같은 요구의 다른 표현을 합친다** — 세 번 다르게 적은 지시를 한 번으로
4. **강조와 반복을 지운다**
5. **예시를 줄인다** — 2개 넘는 동종 예시는 비용이 효과를 넘는다

5번까지 해도 500줄을 넘으면 스킬 두 개가 섞여 있을 가능성을 본다([2.6](../part2/06-promotion.md)).

## 쓰고 나서 확인할 것

| 질문 | 통과 못 하면 |
|---|---|
| 트리거 조건이 본문에 적혀 있나 | `description`으로 옮긴다 |
| 모든 줄이 매번 필요한가 | 조건부인 것을 `references/`로 |
| 참조 파일마다 읽기 조건이 있나 | 조건을 적는다 |
| 대문자 강조가 몇 개인가 | 이유로 바꾼다 |
| 하지 말아야 할 것이 적혀 있나 | 과잉 적용 방지 절을 추가한다 |
| 애매할 때 어디로 기울지 적혀 있나 | 두 방향 실패의 비용을 비교해 적는다 |
| 출력 형식이 보여지는 형태로 있나 | 템플릿을 적는다 |
