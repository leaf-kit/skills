# 3.8 반복 개선과 배포

스킬은 한 번에 완성되지 않는다. 만들고 평가하고 고치는 순환이 본체다. 이 장은 그 순환을 어떻게 돌리는지, 그리고 언제 멈추는지를 다룬다.

## 순환의 모양

```
의도 포착 → 초안 → 테스트 케이스 → 실행(스킬 + 기준선)
   → 채점 → 사람의 평가 → 개선 → (다시 실행)
```

한 바퀴를 이터레이션이라고 부른다. 이터레이션마다 결과를 따로 저장해서 전후를 비교한다.

```
<skill-name>-workspace/
├── iteration-1/
│   ├── eval-0-<이름>/
│   │   ├── eval_metadata.json
│   │   ├── with_skill/run-1/{outputs/, grading.json, timing.json}
│   │   └── without_skill/run-1/{outputs/, grading.json, timing.json}
│   ├── benchmark.json
│   └── feedback.json
└── iteration-2/
```

디렉터리를 미리 다 만들지 않는다. 진행하면서 필요한 것만 만든다.

## 개선의 원칙 네 가지

### 1. 피드백을 일반화한다

이것이 가장 중요하고 가장 자주 어긴다.

테스트 케이스는 세 개뿐이다. 스킬은 수천 번 쓰인다. **세 케이스에만 맞는 수정은 손해다.**

```
# 피드백
"2번 케이스에서 제품 이름을 'A사 신제품'으로 적은 게 어색하다"

# 과적합 수정 (나쁨)
제품 이름을 모를 때 "A사 신제품"이라고 쓰지 않는다.

# 일반화 수정 (좋음)
사용자가 알려주지 않은 고유명사를 추측해 채우지 않는다.
자리표시자로 남기고 무엇이 필요한지 알린다.
```

아래쪽은 제품 이름뿐 아니라 인물, 회사, 지명, 버전에도 적용된다.

판단 기준: **수정 내용에 테스트 케이스의 세부사항이 들어 있으면 과적합이다.** 파일 이름, 특정 단어, 그 케이스의 숫자가 지시에 박히면 다시 쓴다.

### 2. 조건을 붙이지 말고 원인을 고친다

피드백마다 "~하지 마"를 한 줄 추가하는 것이 가장 쉬운 수정이고 가장 나쁜 수정이다. 몇 번 반복하면 스킬이 금지 목록이 되고, 그 시점부터 어떤 입력에도 무난한 출력을 낸다([2.3](../part2/03-length-myth.md)).

```
# 조건 추가 (나쁨)
밋밋하게 쓰지 않는다.
일반론을 쓰지 않는다.
뻔한 표현을 쓰지 않는다.

# 원인 수정 (좋음)
글이 밋밋해지는 원인은 재료가 없는 것이다. 재료가 없으면
한 번 묻고, 없다고 하면 쓸 수 있는 선까지만 쓰고 자리표시자를
남긴다. 분량을 채우려고 일반론으로 늘리지 않는다.
```

### 3. 쓰이지 않는 부분을 지운다

실행 기록을 읽으면 스킬의 어느 부분이 실제로 쓰였는지 보인다. 세 케이스 모두 읽지 않은 참조 파일, 한 번도 적용되지 않은 절, 에이전트가 무시한 지시가 있다.

지우는 것을 아깝게 생각하지 않는다. **본문은 매번 읽히고, 안 쓰이는 줄은 쓰이는 줄의 비중을 낮춘다.**

실행 기록에서 찾을 것 세 가지다.

| 발견 | 조치 |
|---|---|
| 읽히지 않은 참조 파일 | 읽기 조건을 고치거나 파일을 지운다 |
| 비생산적인 작업을 유발한 지시 | 그 지시를 지운다 |
| 케이스마다 비슷한 코드를 새로 씀 | `scripts/`로 번들한다 |

세 번째는 [3.5](05-scripts.md)에서 다룬 중복 발견 신호다. 실행 기록을 읽지 않으면 영원히 안 보인다.

### 4. 막히면 접근을 바꾼다

같은 문제가 두세 번 수정에도 안 고쳐지면, 지시를 더 강하게 쓰는 대신 **다른 방식을 시도한다.**

- 금지를 이유로 바꿔 본다
- 비유나 다른 틀로 설명해 본다
- 절차의 순서를 바꿔 본다
- 그 판단을 스크립트로 내려 본다
- 그 기능을 포기하고 범위를 좁혀 본다

마지막 것이 종종 답이다. 스킬이 못 하는 일을 억지로 시키는 대신, 못 한다고 적고 사용자에게 넘기는 쪽이 낫다.

## 사람의 평가를 먼저 받는다

채점 결과가 나오면 스스로 분석하고 싶어진다. 순서를 지키는 쪽이 낫다. **출력물을 사람에게 먼저 보인다.**

이유는 두 가지다. 어서션은 설계자가 생각한 것만 검사한다. 생각하지 못한 문제는 어서션에 없고, 사람이 출력을 보면 바로 보인다. 그리고 내가 먼저 분석하면 그 분석이 사람의 판단을 끌어간다.

사람에게 보일 때 같이 보일 것들이다.

| 항목 | 왜 |
|---|---|
| 테스트 프롬프트 | 무엇을 요청했는지 |
| 스킬 사용 출력 | 결과 |
| 기준선 출력 | 비교 대상 |
| 이전 이터레이션 출력 | 나아졌는지 |
| 어서션 채점 | 기계 판정 |

비교가 가능한 형태로 보이는 것이 핵심이다. 스킬 출력만 보면 "괜찮네"로 끝나고, 기준선과 나란히 놓으면 차이가 어디서 오는지 보인다.

## 멈추는 시점

이터레이션을 무한히 돌리지 않는다. 멈추는 조건 세 개다.

1. **사용자가 만족한다고 한다**
2. **피드백이 전부 비어 있다** — 지적할 것이 없다
3. **의미 있는 진전이 없다** — 두 이터레이션 연속으로 통과율과 피드백이 제자리

3번에서 멈추는 것이 중요하다. 더 돌릴수록 좋아진다는 보장이 없다. 과적합이 시작되는 지점이기도 하다.

멈출 때 남은 문제를 기록한다. 해결하지 못한 것을 "해결했다"로 덮지 않는다. 실제 사례로, 글 교정 스킬에서 멈출 때 이런 항목이 남았다.

> 3번 케이스의 어서션이 전부 부정형이라 변별력이 없다. 양성 어서션으로 바꿔야 한다. 다음 이터레이션 과제.

> 수정본에 미작성 플레이스홀더가 남는지 검사하는 어서션이 없다.

## description 최적화는 마지막에

트리거 최적화는 본문이 안정된 뒤에 한다. 본문이 바뀌면 스킬의 범위가 바뀌고, 범위가 바뀌면 `description`을 다시 써야 한다. 순서를 거꾸로 하면 두 번 일한다.

최적화 방법은 [3.2](02-description.md)에 있다. 핵심은 **검증 집합으로 고르는 것**이다. 훈련 질의에 맞춘 설명은 실제 사용자 요청에서 더 나쁘다.

## 배포

### 패키징

스킬 디렉터리를 그대로 배포할 수 있다. 다만 설치 단위로 묶으면 편하다. 공식 도구가 패키징 스크립트를 제공한다.

```bash
python -m scripts.package_skill <path/to/skill-folder>
```

### 저장소에 올릴 때 넣을 것

| 파일 | 내용 |
|---|---|
| `SKILL.md` | 스킬 본체 |
| `README.md` | 무엇을 하는 스킬인지, 설치 방법, 예시 입출력 |
| `LICENSE` | 스킬의 라이선스 |
| `evals/` | 테스트 케이스와 어서션 |

`evals/`를 같이 올리는 것을 권한다. 쓰는 사람이 이 스킬이 무엇을 보장하는지 알 수 있고, 고칠 때 회귀를 확인할 수 있다. 수집한 저장소 대부분이 평가를 포함하지 않는다 — 그래서 그 스킬들이 실제로 작동하는지 확인할 방법이 없다([9.2](../part9/02-measuring-quality.md)).

`README.md`에는 **한계를 적는다.** 무엇을 못 하는지, 어떤 경우에 쓰면 안 되는지를 적으면 쓰는 사람이 잘못된 기대를 안 한다.

### 검증

올리기 전에 규격 준수를 확인한다.

```bash
skills-ref validate ./my-skill
```

`name`이 디렉터리 이름과 다른 실수가 가장 흔하고, 이 검사가 잡아 준다.

### 공개 후

스킬을 공개하면 유지 비용이 생긴다. 이슈가 오고, 규격이 바뀌고, 호환되는 도구가 늘어난다.

유지할 생각이 없으면 `README.md`에 적는 쪽이 정직하다. 수집한 저장소 중에 스타가 수만 개인데 마지막 푸시가 오래된 것들이 있다. 쓰는 사람은 그 사실을 저장소 메타데이터로만 알 수 있고, 대개 확인하지 않는다.
