# 3.4 references 설계

`references/`는 조건부로 읽히는 문서가 들어가는 자리다. 점진적 공개의 3단계이고, 비용이 거의 없는 층이다([1.3](../part1/03-progressive-disclosure.md)).

비용이 없으니 많이 넣으면 좋을 것 같지만, 참조 파일은 **읽히지 않으면 없는 것과 같다.** 이 장은 무엇을 내리고 어떻게 읽히게 만드는지를 다룬다.

## 무엇을 내리나

판단 질문은 하나다. **"이 스킬이 트리거될 때 항상 필요한가."**

| 항상 필요 | 조건부 |
|---|---|
| 공통 절차 | 특정 형식 처리 |
| 판단 기준 | 패턴 사전, 예시 모음 |
| 출력 형식 | 도메인별 세부 규칙 |
| 모드 분기 | 드문 예외 처리 |

공식 `pdf` 스킬이 이 판단을 보여 준다.

```
skills/pdf/
├── SKILL.md       (314줄 — 공통 절차)
├── forms.md       (양식 채우기)
├── reference.md   (상세 기술 참조)
└── scripts/       (8개 스크립트)
```

PDF 작업의 다수는 양식과 무관하다. 양식 절차를 본문에 두면 대부분의 실행에서 낭비된다. 본문에는 이렇게만 적혀 있다.

> 고급 기능, JavaScript 라이브러리, 상세 예시는 REFERENCE.md를 보라. PDF 양식을 채워야 하면 FORMS.md를 읽고 그 지시를 따르라.

두 문장이 두 파일의 읽기 조건을 정했다.

## 읽기 조건을 적는 법

참조 파일 설계에서 가장 중요한 일이다. 조건이 없으면 두 가지 중 하나가 일어난다. **항상 읽거나, 한 번도 안 읽는다.** 둘 다 분리한 효과가 사라진다.

### 나쁜 조건

```markdown
자세한 내용은 references/patterns.md를 참고한다.
```

"자세한 내용"이 언제 필요한지가 없다. 조건이 아니라 존재 안내다.

### 좋은 조건

```markdown
점검 모드에서 "뭔가 걸리는데 이름을 못 붙이겠는" 문장이 나오면
references/slop-patterns.md를 펼친다.
```

"이름을 못 붙이겠는 문장이 나오면"이 조건이다. 그 상황이 아니면 안 읽는다.

조건을 쓸 때 쓰는 패턴 세 가지다.

| 패턴 | 예 |
|---|---|
| 상황 조건 | "양식을 채워야 하면" |
| 막힘 조건 | "판정이 애매하면", "오류가 나면" |
| 분기 조건 | "AWS면 aws.md, GCP면 gcp.md" |

## 파일 쪼개는 기준

### 도메인별로 쪼갠다

스킬이 여러 플랫폼이나 언어를 다루면 도메인별로 나눈다. 규격이 이 구조를 권한다.

```
cloud-deploy/
├── SKILL.md       (공통 절차 + 선택 기준)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

효과가 두 가지다. 비용이 줄고, **예시가 범위를 좁히는 문제**가 해결된다. 본문에 AWS 예시만 넣으면 GCP 작업이 약해진다([2.5](../part2/05-examples.md)). 도메인별로 내리면 섞이지 않는다.

### 크기로 쪼갠다

규격이 작은 파일을 권한다. 이유는 **필요한 부분이 조금인데 전부 들어오는 문제**다. 500줄 참조 파일에서 20줄만 필요해도 500줄이 읽힌다.

목표 선은 **파일 하나에 하나의 주제**다. 주제가 둘이면 파일이 둘이다.

### 300줄을 넘으면 목차를 붙인다

긴 참조 파일에는 목차를 넣는다. 에이전트가 필요한 절만 찾아 읽을 수 있다.

```markdown
## 목차

1. [인사말형 서두](#1-인사말형-서두)
2. [배경 설명형 서두](#2-배경-설명형-서두)
3. [대구형 문장](#3-대구형-문장)
...
```

목차가 있으면 파일 전체를 읽지 않고도 구조를 안다.

## 참조 사슬을 만들지 않는다

규격이 명시적으로 금지한다.

> 파일 참조는 `SKILL.md`로부터 한 단계 깊이로 유지하라. 깊게 중첩된 참조 사슬을 피하라.

사슬이란 이런 구조다.

```
SKILL.md → references/a.md → references/b.md → references/c.md
```

문제가 두 방향이다. 중간에서 멈추면 지시의 일부만 적용된다. 끝까지 따라가면 전부 읽게 되어 분리한 의미가 없다. 어느 쪽이든 손해다.

파일이 많아지면 사슬 대신 **본문에 표를 둔다.**

```markdown
## 참조 파일

| 파일 | 언제 읽나 |
|---|---|
| `references/slop-patterns.md` | 판정이 애매한 문장이 나올 때 |
| `references/aws.md` | 대상 플랫폼이 AWS일 때 |
| `references/forms.md` | 양식 필드를 채워야 할 때 |
```

본문이 모든 참조 파일을 직접 가리키고, 참조 파일끼리는 가리키지 않는다. 깊이 1을 유지하는 방법이다.

## 디렉터리 관례가 지켜지지 않는 현실

규격은 참조 문서를 `references/`에 두라고 권한다. 그런데 공식 `pdf` 스킬은 `forms.md`와 `reference.md`를 스킬 루트에 둔다.

규격이 관례를 "권장"이라고만 적었고 강제하지 않기 때문이다. 실제로 수집한 저장소들을 보면 배치가 제각각이다.

**남의 스킬을 읽을 때 알아 둘 것:** `references/` 디렉터리가 없다고 참조 파일이 없다고 판단하면 안 된다. 루트의 `.md` 파일, `docs/`, `guides/` 같은 이름으로 흩어져 있을 수 있다.

**내가 만들 때:** `references/`를 쓰는 쪽이 낫다. 규격이 권하는 이름이고, 남이 읽을 때 찾는 자리다. 다만 파일이 하나뿐이고 본문과 같은 층위라면 루트에 둬도 문제는 없다.

## 참조 파일 자체를 쓰는 법

참조 파일은 본문과 다른 성격의 글이다.

### 본문보다 사전처럼 쓴다

본문은 절차를 순서대로 안내한다. 참조 파일은 **필요한 항목만 찾아 읽는** 문서다. 그래서 항목 단위로 독립적이어야 한다.

```markdown
## 3. 대구형 문장

구조가 뜻보다 앞서는 문장.

**신호** — A가 아니라 B입니다 / 중요한 것은 ~가 아니라 ~입니다

> 나쁜 예: 좋은 코드는 동작하는 코드가 아니라 읽을 수 있는 코드입니다.
> 고친 예: 6개월 전 내가 쓴 함수를 읽는 데 40분이 걸렸다. 동작은 했다.

**언제 봐주는가** — 대비가 글의 실제 논점일 때는 대구가 가장 정확한
도구다. 그 경우 한쪽을 지우면 뜻이 무너진다. 그게 판별법이다.
```

이 항목만 읽어도 완결된다. 앞 항목을 읽어야 이해되는 구조로 쓰면 결국 전체가 읽힌다.

### 예외를 같이 적는다

위 예시의 "언제 봐주는가" 항목이 그것이다. 패턴 목록을 주면 기계적으로 적용한다. 적용하지 않을 조건을 같이 적어야 과잉 적용이 줄어든다.

패턴 사전형 참조 파일에서는 이게 특히 중요하다. 패턴에 걸린다고 자동으로 문제인 건 아니기 때문이다. 그래서 파일 끝에 쓰는 법을 적어 둔다.

```markdown
## 이 목록을 쓰는 방법

패턴에 걸린다고 자동으로 문제는 아니다. 패턴은 **어디를 볼지**
알려주고, 판정은 본문의 테스트가 한다.

1. 패턴으로 의심 지점을 찾는다.
2. 본문의 판정 기준을 적용한다.
3. 막히면 고친다. 통과하면 둔다.
```

### 주관적 판단임을 인정한다

판정 기준이 주관적인 영역에서는 그렇다고 적는다.

```markdown
어디까지가 문제이고 어디부터가 스타일인지는 사람마다 다르다.
이 기준은 하나의 기준일 뿐 정답이 아니다. 사용자가 "이건 내
방식이다"라고 하면 그 판정은 취소된다. 사용자의 판단이 이
목록의 판단을 이긴다.
```

이 문장이 있으면 에이전트가 자기 판정을 절대적으로 적용하지 않는다. 과잉 적용을 막는 장치이면서, 사용자에게 기준을 덧붙일 여지를 안내하는 장치다.
