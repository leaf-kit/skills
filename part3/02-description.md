# 3.2 description 설계

`description`은 스킬에서 가장 중요한 한 필드다. 본문이 아무리 좋아도 이 필드가 약하면 스킬이 불리지 않고, 불리지 않으면 없는 것과 같다.

제약은 **1~1,024자**다. 짧게 쓰라는 제약이 아니다. 길게 쓸 수 있다는 뜻이고, 실제로 길게 쓰는 편이 유리하다.

## 넣어야 할 것 다섯 가지

### 1. 무엇을 하는가

한 문장. 결과물 중심으로 쓴다.

```
AI가 쓴 티가 나는 밋밋한 글(AI슬롭)을 줄인다.
```

### 2. 언제 쓰는가

트리거의 본체다. [3.1](01-capture-intent.md)에서 모은 사용자 표현을 여기 쏟는다.

```
글을 새로 쓸 때는 독자와 재료를 먼저 확보하고, 이미 쓴 글은
슬롭 문장을 찾아 근거와 함께 고친다.
```

두 가지 모드가 있으면 둘 다 적는다. 하나만 적으면 다른 쪽이 트리거되지 않는다.

### 3. 키워드

사용자가 쓸 말을 나열한다. 설명문이 아니라 목록이어도 된다.

```
AI슬롭, AI 티 나는 글, AI 느낌 지우기, 밋밋한 글, 뻔한 글,
영혼 없는 글, 퇴고, 글 다듬기, 문장 다듬기, 초고 고치기,
사람 글처럼, slop, AI slop, AI-sounding text, sounds like ChatGPT,
humanize writing, edit my draft, make this less generic
```

**한국어와 영어를 같이 넣는다.** 한국어로 쓰인 스킬이라도 사용자가 영어로 요청할 수 있고, 그 반대도 있다. 한국어 환경에서는 같은 뜻의 표현이 여럿이라 더 중요하다 — 퇴고, 다듬기, 윤문, 교정, 손보기가 다 같은 요청이다.

### 4. 밀어붙이는 지시

에이전트는 스킬을 보수적으로 건너뛴다([1.5](../part1/05-triggering.md)). 중립적으로 쓰면 "참고 자료가 있다"로 읽히고 건너뛴다.

그래서 설명이 아니라 지시로 쓴다.

```
블로그, 뉴스레터, 소개글, 보고서, 에세이 초안을 쓰거나 고쳐 달라는
요청에는 사용자가 '슬롭'이라는 말을 쓰지 않아도 반드시 적용한다.
```

공식 `pdf` 스킬이 같은 방식이다. `Use this skill whenever the user wants to do anything with PDF files`로 시작하고 `If the user mentions a .pdf file or asks to produce one, use this skill`로 끝난다. 양쪽 끝에 지시를 박았다.

### 5. 제외 조건

가장 많이 빠뜨리는 항목이다.

```
반대로 코드, 로그, 명세서, 번역처럼 문체가 아니라 정확성이 목적인
글에는 쓰지 않는다.
```

제외 조건이 두 가지 일을 한다. 과잉 트리거를 줄이고, 비슷한 스킬과의 경계를 그린다. 스킬이 여러 개 설치된 환경에서 어느 쪽이 불릴지는 겹치지 않는 범위가 결정한다.

## 전체 예시

위 다섯 요소를 한 필드에 담은 모양이다.

```yaml
description: AI가 쓴 티가 나는 밋밋한 글(AI슬롭)을 줄인다. 글을 새로 쓸
  때는 독자와 재료를 먼저 확보하고, 이미 쓴 글은 슬롭 문장을 찾아 근거와
  함께 고친다. AI슬롭, AI 티 나는 글, AI 느낌 지우기, 밋밋한 글, 뻔한 글,
  영혼 없는 글, 퇴고, 글 다듬기, 문장 다듬기, 초고 고치기, 사람 글처럼,
  slop, AI slop, AI-sounding text, sounds like ChatGPT, humanize writing,
  edit my draft, make this less generic. 블로그, 뉴스레터, 소개글, 보고서,
  에세이 초안을 쓰거나 고쳐 달라는 요청에는 사용자가 '슬롭'이라는 말을
  쓰지 않아도 반드시 적용한다. 반대로 코드, 로그, 명세서, 번역처럼 문체가
  아니라 정확성이 목적인 글에는 쓰지 않는다.
```

읽기에 매끄럽지 않다. 그래도 된다. **이 필드는 사람이 읽는 산문이 아니라 트리거 신호의 집합이다.** 매끄럽게 다듬으려고 키워드를 빼면 트리거가 약해진다.

## 길이를 어디까지 쓸 것인가

1,024자를 꽉 채워야 하는 건 아니다. 비용이 있다.

`description`은 **설치된 모든 스킬에 대해 항상 로딩된다**([1.3](../part1/03-progressive-disclosure.md)). 스킬 20개를 설치하고 각각 1,000자를 쓰면 20,000자가 상시 점유된다.

판단 기준은 이렇다.

| 스킬의 성격 | 권장 길이 |
|---|---|
| 트리거 조건이 자명함 (`xlsx`, `pdf`) | 200~400자 |
| 사용자 표현이 다양함 (글쓰기, 리뷰) | 500~900자 |
| 비슷한 스킬과 경쟁함 | 제외 조건까지 포함해 길게 |

공식 스킬들을 보면 실제 길이가 갈린다. `webapp-testing`은 짧다.

```
Toolkit for interacting with and testing local web applications using
Playwright. Supports verifying frontend functionality, debugging UI
behavior, capturing browser screenshots, and viewing browser logs.
```

트리거 조건이 명확한 영역(Playwright, 로컬 웹앱 테스트)이라 키워드를 나열할 필요가 없다. 반면 `pdf`는 작업을 열 가지 나열한다. PDF로 할 수 있는 일이 많고 사용자가 그중 아무거나 말할 수 있기 때문이다.

## 쓰지 말아야 할 것

### 본문 내용

`description`은 **언제 쓰는지**를 적는 자리다. 어떻게 하는지는 본문에 있다. 절차를 요약해 넣으면 길이만 먹고 트리거에 기여하지 않는다.

```
# 나쁨 — 절차를 요약함
3단계로 진행한다. 먼저 독자를 정하고, 다음에 초안을 쓰고,
마지막에 3문항 테스트를 돌린다.

# 좋음 — 트리거 조건
글을 쓰거나 고쳐 달라는 요청에 적용한다.
```

### 자기 홍보

"가장 강력한", "완벽하게 해결하는" 같은 표현은 트리거에 기여하지 않고 과잉 트리거를 유발한다. "완벽하게"라고 적으면 완벽할 수 없는 영역에도 불린다.

### 모호한 범용 표현

"다양한 작업에 유용한", "여러 상황에서 쓸 수 있는"은 범위를 넓히는 게 아니라 지운다. 넓히려면 구체적인 상황을 많이 적는다.

## 트리거를 측정하는 방법

`description`은 추측으로 고치지 않는다. 측정한다.

### 1. 평가 질의를 만든다

걸려야 할 질의 8~10개와 걸리면 안 되는 질의 8~10개를 만든다.

```json
[
  {"query": "사용자 요청 문장", "should_trigger": true},
  {"query": "다른 요청 문장", "should_trigger": false}
]
```

질의 품질이 결과를 결정한다. 추상적인 질의는 아무것도 측정하지 못한다.

```
# 나쁜 질의 — 너무 추상적이고 단순함
"글 고쳐 줘"
"이 데이터 포맷해 줘"

# 좋은 질의 — 구체적, 맥락 있음, 실제 사용자가 쓸 말
"팀 뉴스레터에 보낼 글인데 어제 쓴 거 다시 읽어 보니까 영 남이
쓴 것 같아요. drafts/2026-10-newsletter.md 좀 봐 주세요"
```

구체적인 파일 경로, 상황, 사연이 들어가야 실제 트리거와 비슷해진다. 오타나 반말이 섞여도 된다. 실제 사용자가 그렇게 쓴다.

### 2. 반례를 아슬아슬하게 만든다

걸리면 안 되는 질의에서 **전혀 무관한 것은 가치가 없다.** PDF 스킬의 반례로 "피보나치 함수 써 줘"를 넣으면 통과하지만 아무것도 알아내지 못한다.

좋은 반례는 키워드가 겹치는데 실제로는 다른 처리가 필요한 경우다.

```
# 글쓰기 교정 스킬의 좋은 반례
"커밋 메시지 좀 다듬어 줘" — '다듬다'가 겹치지만 기술 문서다
"이 영문 계약서 번역해 줘" — 글 작업이지만 정확성이 목적이다
"README 오타 좀 고쳐 줘" — 교정이지만 문체 문제가 아니다
```

### 3. 여러 번 돌린다

트리거는 결정적이지 않다. 같은 질의를 세 번 돌려 트리거율을 낸다. 한 번 걸렸다고 통과로 기록하면 측정이 흔들린다.

### 4. 과소와 과잉을 따로 본다

통과율 하나로 합치면 어느 방향으로 틀렸는지 안 보인다.

| 지표 | 뜻 | 고치는 방향 |
|---|---|---|
| 걸려야 할 질의의 트리거율 | 과소 트리거 정도 | 키워드 추가, 지시 강화 |
| 걸리면 안 될 질의의 트리거율 | 과잉 트리거 정도 | 제외 조건 추가 |

둘을 같이 올리는 것이 목표다. 한쪽만 올리면 다른 쪽이 내려간다.

## 자동화

이 측정을 반복하면서 `description`을 고치는 루프를 자동으로 돌릴 수 있다. 공식 `skill-creator` 스킬이 이 루프를 스크립트로 제공한다.

작동 방식은 이렇다. 평가 질의 집합을 훈련용 60%와 검증용 40%로 나눈다. 현재 `description`으로 각 질의를 세 번씩 실행해 트리거율을 재고, 실패한 질의를 근거로 개선안을 만든다. 새 `description`을 훈련과 검증 양쪽에서 다시 재고, 최대 다섯 번 반복한다. 최종 선택은 **훈련 점수가 아니라 검증 점수**로 한다.

검증 점수로 고르는 이유가 중요하다. 훈련 점수로 고르면 그 질의 집합에만 맞는 `description`이 나온다. 질의 20개에 과적합된 설명은 실제 사용자 요청에서 더 나쁘다. **평가 집합에 맞추는 것과 트리거가 좋아지는 것은 다르다.**
