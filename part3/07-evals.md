# 3.7 평가 만들기

평가 없이 만든 스킬은 좋아졌는지 알 수 없다. 고칠 때마다 느낌으로 판단하게 되고, 느낌은 마지막에 본 결과에 끌려간다.

이 장은 평가 설계를 다룬다. 3부에서 가장 긴 장이고, 생략하면 나머지 일곱 장이 검증되지 않는다.

## 구조

평가 한 번은 네 부분으로 된다.

| 부분 | 내용 |
|---|---|
| 테스트 프롬프트 | 실제 사용자가 할 만한 요청 |
| 입력 파일 | 요청에 딸린 파일 (필요하면) |
| 어서션 | 결과가 만족해야 할 검증 가능한 조건 |
| 기준선 | 스킬 없이 같은 요청을 돌린 결과 |

네 번째가 핵심이다. **기준선 없는 평가는 평가가 아니다.** 스킬을 붙인 결과가 80점이어도, 안 붙인 결과가 80점이면 스킬은 비용만 추가한 것이다.

## 테스트 프롬프트

### 실제 사용자의 말로 쓴다

가장 흔한 실패는 프롬프트를 깔끔하게 쓰는 것이다.

```
# 나쁨 — 테스트용으로 다듬은 문장
"문서를 교정해 주세요"

# 좋음 — 실제 사용자가 쓸 말
"블로그에 올릴 글 초안인데 읽어보니까 영 AI가 쓴 티가 나요.
서두가 특히 걸립니다. intro.md 파일 좀 봐주고 고쳐주세요."
```

아래쪽에 들어 있는 것들이 테스트를 테스트로 만든다. 파일 이름, 사용자가 이미 내린 판단("서두가 특히 걸립니다"), 구어체. 실제 요청에는 이런 것이 섞여 있고, 스킬은 이런 요청을 받는다.

### 세 종류를 섞는다

케이스 3개로 시작한다면 이 구성이 좋다.

| 종류 | 무엇을 재나 |
|---|---|
| 전형적인 성공 케이스 | 스킬이 제 일을 하는가 |
| 재료, 정보가 부족한 케이스 | 스킬이 멈추고 묻는가, 지어내는가 |
| **스킬이 개입하면 안 되는 케이스** | 과잉 적용을 하지 않는가 |

세 번째가 가장 설계하기 어렵고 가장 값이 나간다. 스킬은 "하라"는 지시로 가득하므로 무언가 하려 든다. 할 일이 없는 입력을 주고 아무것도 안 하는지 보는 것이 그 성향을 측정하는 방법이다.

실제 사례로, 글 교정 스킬의 세 케이스는 이렇게 설계했다.

1. 전형적인 AI 블로그 서두를 주고 점검 요청 → 슬롭을 찾아내는가
2. "신제품 소개글 써 줘"만 주고 정보는 안 줌 → 재료를 묻는가, 제품을 지어내는가
3. **이미 사람 느낌이 나는 글**을 주고 점검 요청 → 과하게 고치지 않는가

### 입력 파일을 직접 만든다

3번 케이스를 위한 입력은 직접 써야 한다. "이미 사람 느낌이 나는 글"을 자동으로 구할 수 없다. 만들 때 의도적으로 넣는다.

- 구체적인 숫자와 장면
- 사용자 특유의 구어체
- 실제 대화 인용
- 패턴에 걸리지만 의도적인 표현 (스킬이 봐주는지 테스트)

마지막 항목이 영리한 설계다. 금지 패턴에 해당하는 문장을 일부러 하나 넣되, 그 문장이 글의 논점이라서 지우면 뜻이 무너지는 구조로 만든다. 스킬이 패턴을 기계적으로 적용하면 걸리고, 예외 판단을 하면 통과한다.

## 어서션

### 검증 가능해야 한다

어서션은 **제3자가 결과를 보고 합격, 불합격을 판정할 수 있는 문장**이다.

```
# 어서션이 아니다
"글이 자연스럽다"
"결과가 좋다"

# 어서션이다
"인사말형 서두('안녕하세요! 오늘은 ... 알아보겠습니다')가
 수정본에서 사라졌다"
"출처 없는 통계를 수정본에 그대로 남기지 않았다"
"답변 끝에 한 줄 체크리스트가 붙어 있다"
```

### 셀 수 있으면 센다

애매함을 없애는 가장 확실한 방법이다.

```
# 애매함
"뭉뚱그린 형용사가 줄었다"

# 셀 수 있음
"뭉뚱그린 형용사(다양한/효과적인/핵심적인/전략적인/체계적인/
 적절한)가 수정본에서 5개 이하로 줄었다"
```

목록을 명시하고 상한을 숫자로 적으면 채점이 기계적으로 된다. 스크립트로 세면 재현도 된다.

### 주관적 스킬에서는 금지선을 잰다

글쓰기나 디자인처럼 품질이 주관적인 영역에서는 품질을 재려 하지 않는다. **지켜야 할 선을 어겼는지**를 잰다.

```
# 품질을 재려는 시도 (측정 불가)
"문장이 매끄럽다"

# 금지선 위반을 잰다 (측정 가능)
"원문에 없던 숫자, 통계, 인용, 개인 경험을 새로 지어내지 않았다"
"사용자의 구어체 말투를 격식체로 통일하지 않았다"
"수정 제안이 5건 이하다"
```

아래쪽은 객관적으로 판정되고, 통과 여부가 실제 품질과 연결된다. 품질을 직접 재지 않으면서 품질을 보호한다.

### 과잉 적용 케이스의 어서션은 반대로 쓴다

스킬이 개입하면 안 되는 케이스에서는 어서션이 "**적게 했을 때 통과**"하는 모양이 된다.

```
"고칠 것이 적다는 판단을 명시했다"
"수정 제안이 5건 이하다"
"구체적 재료(대화 인용, 숫자, 장면)를 삭제하거나 뭉개지 않았다"
"전체 글을 다시 쓰지 않았다 (문단 구조와 분량이 원문과 대체로 유지됐다)"
```

## 변별력 — 가장 중요한 품질

어서션을 다 통과했는데 아무것도 알아내지 못하는 경우가 있다. **기준선도 똑같이 통과할 때**다.

실제 측정 사례다. 글 교정 스킬의 세 케이스를 스킬 있는 쪽과 없는 쪽으로 각각 돌리고 채점한 결과다.

| 케이스 | 스킬 사용 | 기준선 |
|---|---|---|
| AI 블로그 서두 점검 | 8/8 | 5/8 |
| 재료 없는 작성 요청 | 6/6 | 3/6 |
| 이미 사람 느낌 나는 글 | 6/6 | **6/6** |

세 번째 케이스는 양쪽이 만점이다. 이 어서션 집합은 **스킬의 가치를 구분하지 못한다.**

원인을 보면 설계 결함이 드러난다. 어서션 6개가 전부 "~하지 않았다" 형태의 부정형이다. 그러면 **아무것도 하지 않은 답변도 만점을 받는다.** "고치지 않았다", "삭제하지 않았다", "추가하지 않았다"를 다 만족하는 가장 쉬운 방법은 아무 일도 안 하는 것이다.

고치는 방향은 양성 어서션을 섞는 것이다.

```
# 기존 (부정형만)
"구체적 재료를 삭제하지 않았다"
"구어체를 격식체로 통일하지 않았다"

# 추가 (양성형)
"그대로 둔 표현에 대해 왜 두었는지 설명했다"
"실제로 고칠 가치가 있는 항목을 최소 1건 찾아냈다"
```

양성형은 아무것도 안 하면 실패한다. 부정형과 섞으면 "적게 하면서도 할 일은 한" 상태만 통과한다.

### 변별력을 확인하는 방법

채점이 끝나면 어서션별로 본다.

| 상황 | 뜻 | 조치 |
|---|---|---|
| 양쪽 다 통과 | 변별력 없음 | 어서션을 강화하거나 폐기 |
| 양쪽 다 실패 | 어서션이 너무 어렵거나 틀림 | 어서션을 재검토 |
| 스킬만 통과 | 변별력 있음 | 유지 |
| 기준선만 통과 | 스킬이 해를 끼침 | 스킬을 고친다 |

마지막 줄이 가장 중요한 발견이다. 스킬 때문에 결과가 나빠지는 경우가 실제로 있다.

## 기준선 설계

| 상황 | 기준선 |
|---|---|
| 새 스킬을 만든다 | 스킬 없이 같은 요청 |
| 기존 스킬을 개선한다 | 고치기 전 버전 |

두 번째의 경우 **고치기 전에 스냅샷을 떠 둬야 한다.** 고친 뒤에는 이전 버전이 없다.

기준선을 돌릴 때 주의할 점이 있다. 스킬 파일에 접근하지 못하게 해야 한다. 기준선 실행이 스킬 디렉터리를 읽으면 기준선이 아니다.

## 측정에 쓰이는 숫자

통과율만 보면 비용을 못 본다. 세 가지를 같이 기록한다.

| 지표 | 왜 보나 |
|---|---|
| 통과율 | 스킬이 기여하는가 |
| 소요 시간 | 스킬이 느려지게 하는가 |
| 토큰 | 스킬이 비싸게 하는가 |

실제 측정 예다.

| 지표 | 스킬 사용 | 기준선 | 차이 |
|---|---|---|---|
| 통과율 | 100% ± 0% | 71% ± 26% | +29%p |
| 시간 | 84.3초 | 69.6초 | +14.7초 |
| 토큰 | 30,438 | 18,450 | +11,988 |

통과율만 보면 완승이다. 비용을 보면 시간이 21% 늘고 토큰이 65% 늘었다. **이 교환이 받아들일 만한지는 통과율 차이가 어디서 왔는지에 달렸다.**

이 사례에서 기준선 실패 9건 중 6건이 **창작**이었다. 없는 제품의 성능 수치를 만들고, 원문에 없던 경험담을 지어냈다. 그런 실패를 막는 대가로 토큰 65%를 더 쓰는 것은 타당하다. 반대로 통과율 차이가 출력 형식 같은 사소한 항목에서 왔다면 그 교환은 나쁘다.

## 표준편차를 본다

위 표에서 기준선의 통과율 표준편차가 26%다. 스킬 쪽은 0%다.

**이 차이가 평균 차이보다 중요할 수 있다.** 기준선은 케이스에 따라 50%에서 100%까지 흔들렸다. 스킬은 세 케이스 모두 100%였다. 평균이 같아도 분산이 작은 쪽이 쓸 만하다. 쓸 때마다 결과가 달라지면 신뢰할 수 없다([2.1](../part2/01-criteria.md)의 재현성).

그래서 같은 케이스를 여러 번 돌리는 것이 좋다. 한 번만 돌리면 분산을 모른다.

## 채점을 누가 하나

스킬을 만든 사람이 채점하면 관대해진다. 내가 의도한 것을 알고 있으니 출력에서 그 의도를 읽어낸다.

대안 두 가지다.

**독립적인 채점자.** 별도 에이전트에게 어서션과 출력만 주고 판정하게 한다. 스킬 내용을 모르는 상태로 채점한다.

**스크립트.** 기계로 확인할 수 있는 어서션은 코드로 센다. 형용사 개수, 특정 문장의 존재, 제안 건수는 다 셀 수 있다. 스크립트는 빠르고, 일관되고, 이터레이션마다 재사용된다.

채점자에게 한 가지를 더 시키는 쪽이 좋다. **어서션 자체를 비판하게 하는 것**이다. 통과했는데 변별력이 없는 항목, 중요한 결과를 아무 어서션도 검사하지 않는 경우를 찾아 보고하게 한다. 실제로 앞의 사례에서 채점자가 이렇게 지적했다.

> 이 어서션 집합은 거의 전부 부정형이라, 아무것도 하지 않은 답변에도 6/6을 줄 것이다.

> 어떤 어서션도 수정본을 그대로 발행할 수 있는지 검사하지 않는다. 수정본에 미작성 플레이스홀더 3곳이 남아 있다.

두 지적 모두 평가 설계의 구멍이고, 만든 사람은 보기 어려운 것이다.

## 트리거는 따로 측정한다

출력 품질 평가와 트리거 평가는 다른 측정이다. 섞으면 안 된다.

품질 평가는 스킬을 **강제로 적용한 상태**에서 돌린다. 트리거되는지는 보지 않는다. 트리거 측정은 별도 질의 집합으로 한다([3.2](02-description.md)).

섞으면 "스킬이 안 불려서 결과가 나쁜 것"과 "불렸는데 결과가 나쁜 것"이 구분되지 않는다. 고칠 자리가 `description`인지 본문인지 알 수 없게 된다.
