# 4.4 메타스킬

스킬을 대상으로 하는 스킬이다. 두 축([4.2](02-three-types.md), [4.3](03-scale.md))으로 깔끔하게 안 잡혀서 따로 다룬다.

형식상으로는 방법론형이다. 대상이 스킬 자체여서 성격이 다르다.

생태계가 자기 참조 단계에 들어섰다는 신호다. 스킬을 만드는 일 자체가 반복 작업이 됐고, 반복되면 스킬로 올라간다([2.6](../part2/06-promotion.md)).

## 네 갈래

메타스킬이 푸는 문제가 네 가지로 갈린다.

### 1. 만들기 — 설계와 평가

스킬을 처음부터 만드는 절차를 담는다. `skill-creator`와 `one-skill-to-rule-them-all`이 여기 속한다.

`skill-creator`의 구조를 보면 이 범주가 무엇을 다루는지 보인다. 본문 485줄에 번들 18개 파일, 225KB다.

```
skill-creator/
├── SKILL.md           (485줄 — 의도 포착부터 배포까지)
├── references/        (JSON 스키마)
├── agents/            (채점자, 비교자, 분석자 지시문)
├── scripts/           (평가 실행, 집계, description 최적화, 패키징)
└── eval-viewer/       (결과 리뷰 HTML 생성)
```

눈여겨볼 점은 **번들의 대부분이 평가 도구**라는 것이다. 스킬 만드는 법을 가르치는 스킬에서 비중이 가장 큰 부분이 "만든 것이 작동하는지 재는 법"이다. [3.7](../part3/07-evals.md)이 3부에서 가장 긴 장인 이유와 같다.

`agents/` 디렉터리가 있는 것도 특징이다. 채점을 별도 에이전트에게 맡기는 구조다. 만든 사람이 채점하면 관대해지기 때문이다.

### 2. 최적화 — 이미 있는 스킬을 개선

`microsoft/SkillOpt`(17,979)와 `alibaba/skill-up`(1,131)이 이쪽이다. 빅테크 두 곳이 같은 문제를 각자 다룬다는 점이 흥미롭다.

`SkillOpt`의 설명은 "자연어 스킬을 **텍스트 공간에서** 훈련하는 최적화기"다. 모델 가중치를 건드리지 않고 지시문 텍스트를 개선한다는 뜻이다. 프롬프트 최적화와 같은 계열이고, 대상이 스킬 파일이다.

`skill-up`은 "에이전트 스킬 평가, 진화 도구"다. 평가와 개선을 묶었다.

`skill-creator`에도 같은 기능이 있다 — `description` 최적화 루프다. 작동 방식이 지도학습과 닮았다. 질의 집합을 훈련 60% / 검증 40%로 나누고, 개선안을 만들고, **검증 점수로** 최종안을 고른다.

검증 점수로 고르는 이유가 이 범주의 핵심 문제를 드러낸다. **평가 집합에 맞추는 것과 실제로 좋아지는 것은 다르다.** 훈련 질의 12개에 과적합된 `description`은 실제 사용자 요청에서 더 나쁘다. 메타스킬이 자동으로 돌아갈 때 이 함정이 커진다. 사람이 중간에서 보지 않으면 과적합이 진행되는 것을 모른다.

### 3. 변환 — 자료를 스킬로

기존 자료를 스킬 형식으로 바꾼다. 가장 스타가 많이 붙은 갈래다.

| 저장소 | 입력 |
|---|---|
| `virgiliojr94/book-to-skill`(33,430) | 기술서 PDF |
| `yusufkaraaslan/Skill_Seekers`(15,097) | 문서 사이트, 저장소, PDF |
| `microsoft/skill-recorder`(4,185) | 화면 작업 녹화 |
| `titanwings/distilly`(25,269) | 작업 방식 |

왜 이 갈래가 인기 있는지는 분명하다. **빈 파일에서 시작하는 것이 어렵고, 변환은 쉽다.** 이미 있는 책이나 문서를 스킬로 바꾸면 분량이 바로 나온다.

문제도 같은 데서 나온다. 변환으로 만든 스킬은 **지식형**이 되고, 지식형은 수명이 짧다([4.2](02-three-types.md)). 책 한 권을 스킬로 바꾸면 그 책의 내용이 그대로 들어가는데, 그 내용에 유효기간이 있으면 스킬도 같이 낡는다.

더 구조적인 문제가 있다. 변환은 **선별을 하지 않는다.** 책 300쪽을 스킬로 바꾸면 300쪽이 참조 파일이 된다. 좋은 스킬은 "항상 필요한 것"과 "조건부인 것"을 가르는 작업의 결과인데([1.3](../part1/03-progressive-disclosure.md)), 자동 변환은 그 작업을 건너뛴다.

`skill-recorder`는 다른 접근이다. 작업 **과정**을 녹화해서 스킬로 만든다. 문서가 아니라 행동에서 뽑기 때문에 "실제로 하는 일"이 들어간다. 입력이 다르면 결과물의 성격도 다르다 — 이쪽은 실행형에 가깝다.

### 4. 측정 — 스킬이 좋아졌는지 재기

`taneltaluri/evolve-skill`(2)이 명시적으로 이 문제를 다룬다. 설명이 "3단 게이트 측정 규율 기반 최적화기"다. 스타 2개로 거의 안 알려졌지만, 생태계의 빈 곳을 가리킨다.

그 빈 곳이 무엇인지는 수집 데이터가 말해 준다. **스킬을 평가하는 공통 벤치마크가 없다.** 그래서 이 책도 순위 축으로 스타수를 쓸 수밖에 없었다([0.2](../part0/02-why-stars.md)).

## 메타스킬의 공통 함정

### 자기 적용 문제

스킬을 만드는 스킬은 자기 자신에게 적용될 수 있다. `one-skill-to-rule-them-all`의 설명이 이걸 명시한다 — "모든 스킬을 만들고 개선하는 메타스킬, **자기 자신을 포함해서**".

재귀가 멋있어 보이지만 검증이 어려워진다. 스킬 A를 고치는 메타스킬 M이 자기를 고치면, M이 나아졌는지 판정할 기준이 M 안에 있다. 외부 기준이 없으면 평가가 순환한다.

### 평가 없는 메타스킬

가장 흔한 문제다. 스킬 품질을 올려 준다고 주장하면서 정작 그 주장을 뒷받침하는 평가가 없는 경우다.

리뷰에서 이 점을 본다. **메타스킬은 평가를 포함해야 할 책임이 가장 큰 범주다.** "스킬을 개선한다"는 주장은 개선 전후를 비교하지 않으면 확인할 수 없다.

### 자동화와 과적합

최적화 루프를 자동으로 돌리면 평가 집합에 과적합된다. 사람이 중간에서 보지 않으면 진행 중에 알 수 없다.

`skill-creator`가 이 문제를 처리하는 방식이 참고가 된다. 자동 루프를 돌리면서도 **출력물을 사람에게 먼저 보이는 단계**를 절차에 못 박았다. 어서션은 설계자가 생각한 것만 검사하고, 생각하지 못한 문제는 사람이 출력을 봐야 보인다.

## 메타스킬을 쓸 때

실무적인 판단이다.

| 상황 | 쓸 만한가 |
|---|---|
| 스킬을 처음 만든다 | ○ 절차와 평가 틀을 얻는다 |
| 기존 스킬의 트리거가 약하다 | ○ `description` 최적화는 자동화 효과가 크다 |
| 책, 문서를 스킬로 바꾸고 싶다 | △ 선별을 건너뛴 결과가 나온다. 변환 후 직접 깎아야 한다 |
| 스킬 품질을 올리고 싶다 | △ 평가 집합이 먼저 있어야 한다 |
| 스킬을 자동으로 진화시키고 싶다 | ✕ 사람이 보지 않으면 과적합을 모른다 |

세 번째와 네 번째가 △인 이유가 같다. **메타스킬이 대신해 줄 수 없는 작업이 앞에 있다.** 무엇이 항상 필요하고 무엇이 조건부인지 가르는 일, 무엇을 측정할지 정하는 일은 사람이 한다.
